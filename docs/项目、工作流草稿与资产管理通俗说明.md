# 项目、工作流草稿与资产管理通俗说明

## 1. 这套设计要解决什么问题

用户制作一条营销视频时，会经历上传资料、AI 提炼、生成 Prompt、渲染素材、混剪和导出等多个节点。

如果每修改一次内容就创建一份正式资产，会出现很多问题：

- 用户每经过一个节点都要手动保存，操作很烦。
- 同一份内容修改几次，就出现很多真假难分的资产版本。
- 用户临时退出时，不清楚应该保存草稿还是归档资产。
- 上游资料变化后，下游结果是否还能继续使用很难判断。
- 不同项目的素材、草稿和结果容易混在一起。

因此系统把数据分为四个阶段：

1. `WorkflowNodeState`：节点页面正在编辑的状态。
2. `WorkingArtifact`：节点已经产生、可供下游使用的最新工作副本。
3. `ProjectAsset`：工作流完成后归档的正式项目资产。
4. `GlobalAsset`：用户明确发布、允许其他项目复用的全局资产。

最简单的理解是：

```text
正在填写的页面
    ↓ 自动保存
工作流草稿 WorkflowNodeState
    ↓ 文件上传成功、提炼完成、生成完成
工作区产物 WorkingArtifact
    ↓ 完成工作流并归档
正式项目资产 ProjectAsset
    ↓ 用户主动发布
全局发布资产 GlobalAsset
```

这四层不是重复保存四份相同数据，而是代表同一项业务内容从“编辑中”到“可复用”的不同阶段。

## 2. 项目中心展示什么

项目中心是一个统一查看入口，不是另外复制一套数据。一个项目建议展示以下五个区域：

```text
项目中心
└─ 广式腊肠夏季投放
   ├─ 项目资料与项目状态
   ├─ 工作流草稿
   ├─ 工作区产物
   ├─ 已归档资产
   └─ 全局发布资产
```

### 2.1 项目资料与项目状态

这里回答的是：**这是什么项目，现在做到哪一步了？**

主要展示：

- 项目名称、项目 ID。
- 客户、产品、项目简介和 Brief。
- 项目绑定的工作流类型。
- 当前执行轮次 `workflowRunId`。
- 当前节点、整体进度和运行状态。
- 创建时间、最后自动保存时间和交付时间。

例如：

```text
广式腊肠夏季投放
PJT-FOOD-001 · 效果类 · 进行中

当前节点：Prompt 生成
工作流进度：3/6
当前轮次：RUN-EFFECT-001
最后保存：今天 14:32

[继续工作] [查看项目资产]
```

这一部分保存的是项目身份和进度，不直接保存图片、Prompt 正文或视频文件。

### 2.2 工作流草稿

这里回答的是：**用户上次在每个节点编辑到了什么状态？**

数据来自 `WorkflowNodeState`，例如：

```text
工作流草稿
├─ 导入：已完成 · 今天 14:05 自动保存
├─ 提炼：已完成 · 今天 14:15 自动保存
├─ Prompt 生成：编辑中 · 今天 14:32 自动保存
├─ 渲染：未开始
├─ 混剪：未开始
└─ 导出：未开始
```

它用于恢复页面，不是资产，因此：

- 不显示在资产选择器中。
- 不能跨项目复用。
- 不产生正式资产版本。
- 可以是不完整的内容。

### 2.3 工作区产物

这里回答的是：**当前工作流已经生成了哪些最新结果？**

数据来自 `WorkingArtifact`，例如：

```text
工作区产物
├─ 广式腊肠原始资料包 · revision 2 · 最新
├─ 营销洞察 · revision 1 · 最新
└─ 抖音 Prompt 批次 · revision 3 · 尚未归档
```

工作区产物可以被后续节点直接读取，但它仍然是工作中的内容：

- 同一个逻辑产物只维护一份最新副本。
- 修改后增加 `revision`，不创建正式资产版本。
- 可以删除、覆盖、重新生成。
- 上游变化后可以被标记为“待更新”。
- 默认不能被其他项目直接选择。

### 2.4 已归档资产

这里回答的是：**这个项目已经正式沉淀了哪些成果？**

数据来自 `ProjectAsset`，例如：

```text
已归档资产
├─ 广式腊肠商品资料包 · v1
├─ 夏季投放营销洞察 · v1
├─ 抖音 Prompt 批次 · v1
├─ 视频渲染素材 · v1
└─ 夏季投放成片 · v1
```

它与工作区产物的区别是：

- 有正式资产 ID。
- 有正式版本号，例如 `v1`、`v2`。
- 记录来源工作流、执行轮次、节点和工作副本 revision。
- 不会因为用户继续编辑工作区而自动变化。
- 可以作为跨项目导入的来源。

普通退出、刷新页面和切换项目都不能自动归档。只有用户明确执行“完成工作流并归档”时，系统才把有效工作副本转换为正式项目资产。

### 2.5 全局发布资产

这里回答的是：**本项目有哪些正式资产允许其他项目复用？**

数据来自 `GlobalAsset`，例如：

```text
全局发布资产
├─ 广式腊肠电商白底产品资产 · G1
├─ 老广厨房场景 · G1
└─ 食品带货混剪模板 · G2
```

全局资产必须由用户从已归档资产中明确选择发布。发布后仍要保留：

- 来源项目 ID。
- 来源项目资产 ID。
- 来源正式版本。
- 发布人和发布时间。

其他项目使用时，复制指定版本的快照，不能直接修改来源项目的资产。

## 3. 每个节点都有 WorkflowNodeState 吗

原则上，每个被访问或编辑过的工作流节点都有一条独立的 `WorkflowNodeState`。

它由下面几个字段共同确定：

```text
projectId + workflowRunId + nodeId
```

例如效果类工作流包含六个节点：

```text
RUN-EFFECT-001
├─ import       导入
├─ extract      提炼
├─ prompt       Prompt 生成
├─ render       视频渲染
├─ remix        模板混剪
└─ export       成片输出
```

不需要在创建项目时就向数据库插入六条空记录。推荐按需创建：

- 用户第一次进入节点时创建。
- 用户第一次修改节点内容时创建。
- 从未访问过的节点可以没有记录，查询时按“未开始”展示。

### 3.1 WorkflowNodeState 保存什么

它只保存恢复节点页面需要的信息，例如：

- 表单输入。
- 当前选择的产品和素材。
- 生成参数。
- 尚未提交的修改。
- 当前页码和筛选条件等有恢复价值的 UI 状态。
- 节点运行状态和最后保存时间。

导入节点的状态可能是：

```json
{
  "nodeId": "import",
  "status": "editing",
  "formData": {
    "importMode": "single-product",
    "productId": "PRODUCT-SAUSAGE-001",
    "selectedFileIds": ["FILE-001", "FILE-002"],
    "tags": ["食品", "腊味"]
  },
  "uiState": {
    "activeTab": "local-upload",
    "currentPage": 1
  },
  "lastSavedAt": "2026-08-24T14:32:00+08:00"
}
```

Prompt 节点则可以保存生成数量、渠道、画幅、卖点选择和当前页码。不同节点的具体内容不同，但它们都属于页面恢复状态。

### 3.2 常见节点状态

```text
not_started  未开始
editing      编辑中
ready        已准备，可以执行
running      运行中
completed    已完成
stale        上游有变化，当前结果待更新
failed       保存或执行失败
```

### 3.3 什么时候保存

- 文本停止输入约 1 秒后自动保存。
- 输入框失焦后立即保存。
- 上传、删除、排序成功后立即保存。
- 切产品、切节点、切项目和退出项目前强制刷新保存。
- 内容哈希没有变化时，不重复写入数据库。

不能只依赖浏览器关闭事件，因为浏览器崩溃或进程被终止时，关闭事件可能不会执行。

## 4. WorkingArtifact 什么时候产生

不是用户一进入节点就产生工作副本。只有节点产生了**已经成功持久化、可以继续维护的业务结果**时，才创建或更新 `WorkingArtifact`。

导入节点需要特别处理：文件写入对象存储、建立 `FileObject` 并通过基础格式校验后，就应立即创建或更新资料包工作副本。资料是否已经完整，只决定能否进入下一节点，不决定工作副本是否存在。

例如导入节点：

```text
选择本地文件
    ↓
上传中
    ↓ 记录 UploadSession，更新 WorkflowNodeState
对象存储写入成功并通过基础校验
    ↓
创建 FileObject
    ↓
自动创建或更新产品资料包 WorkingArtifact
    ↓
用户继续填写标签、补充或删除文件
    ↓
通过节点完整性校验后才允许进入下一节点
```

导入节点的工作副本可以是：

```text
artifactKey：source-package:PRODUCT-SAUSAGE-001
名称：广式腊肠原始资料包
revision：1
内容：10 张商品图片
来源节点：import
```

其他节点的工作副本例如：

```text
提炼节点  → marketing-insight:PRODUCT-SAUSAGE-001
Prompt节点 → prompt-batch:PRODUCT-SAUSAGE-001
渲染节点  → render-clip:SHOT-001
混剪节点  → timeline-project:CUT-001
导出节点  → final-video:VIDEO-001
```

### 4.1 一个节点有几个工作副本

一个节点通常只有一条 `WorkflowNodeState`，但可以有零条、一条或多条 `WorkingArtifact`。

例如渲染节点：

```text
渲染节点
├─ 一条 WorkflowNodeState
└─ 多条 WorkingArtifact
   ├─ render-clip:SHOT-001
   ├─ render-clip:SHOT-002
   ├─ render-clip:SHOT-003
   └─ render-batch-summary:BATCH-001
```

节点状态用于恢复页面，工作副本用于保存业务结果，两者不能混为一张表或一类数据。

### 4.2 导入节点按什么粒度维护工作副本

导入节点不是“所有图片共用一个节点 revision”，而是“同一个逻辑资料包里的文件共用该资料包 WorkingArtifact 的 revision”。

推荐采用两层结构：

```text
WorkingArtifact：每个产品一条资料包工作副本
└─ FileObject：每个文件一条独立文件记录
```

例如广式腊肠导入 10 张图片：

```text
source-package:PRODUCT-SAUSAGE-001 · revision 1
├─ FILE-001 · 产品正面图
├─ FILE-002 · 产品侧面图
├─ FILE-003 · 包装特写
└─ ...共 10 张
```

每个 `FileObject` 独立保存文件 ID、对象存储地址、文件名、类型、大小和内容哈希。资料包工作副本保存产品 ID、文件 ID 集合、业务标签、排序和完整性状态。

如果是多产品批量导入，必须按产品拆分工作副本：

```text
导入节点
├─ source-package:PRODUCT-SAUSAGE-001 · revision 3
├─ source-package:PRODUCT-SERUM-001   · revision 1
└─ source-package:PRODUCT-TENT-001    · revision 2
```

修改广式腊肠图片时，只增加腊肠资料包 revision，不能让精华液和帐篷的工作副本一起变化。

不同业务类型的内容也应拆开维护，例如项目 Brief、参考视频和产品图片不应共用同一条工作副本。

### 4.3 全局视频配置单独维护

全局视频配置会影响提炼、Prompt、渲染和混剪，应单独维护为一条工作副本：

```text
导入节点
├─ source-package:PRODUCT-SAUSAGE-001
│  └─ 产品图片、视频和资料文件
└─ global-video-config:PRODUCT-SAUSAGE-001
   └─ 视频时长、画幅、风格、渠道和禁用元素
```

这样删除图片只增加资料包 revision；修改时长、画幅或投放渠道只增加全局视频配置 revision。下游可以准确判断是哪类输入发生变化。

全局视频配置在首次有效保存后创建为 `revision 1`。确认后再次修改并保存成功，例如从京东改为抖音、从 3:4 改为 9:16，配置工作副本应增加 revision，并把依赖旧配置的下游结果标记为待更新。

## 5. artifactKey 和 revision 是什么

### 5.1 artifactKey

`artifactKey` 是一个逻辑产物在当前工作流执行轮次中的稳定名字。

例如：

```text
source-package:PRODUCT-SAUSAGE-001
marketing-insight:PRODUCT-SAUSAGE-001
prompt-batch:PRODUCT-SAUSAGE-001
```

即使用户把“广式腊肠原始资料包”重命名为“腊肠夏季投放资料”，`artifactKey` 也不变。系统依靠它找到同一个逻辑产物并原位更新，而不是重复创建新卡片。

工作副本推荐使用以下组合唯一定位：

```text
projectId + workflowRunId + nodeId + artifactKey
```

### 5.2 revision

`revision` 表示工作副本在编辑阶段发生了多少次有效变化。

例如：

```text
一次上传 10 张图片并成功持久化 → revision 1
删除 3 张图片                  → revision 2
修改影响下游的标签             → revision 3
```

以下操作不会改变工作副本 revision：

- 只打开页面。
- 只切换分页。
- 修改搜索关键词。
- 内容保存前后完全相同。
- 删除图片后又恢复成与原来完全相同的业务内容。

系统通过规范化内容的 SHA-256 哈希判断是否真的发生变化。

以下有效业务变化会增加 revision：

- 文件新增、删除或替换。
- 会影响下游的文件排序变化。
- 业务标签、产品归属或素材关联变化。
- 全局视频配置中的时长、画幅、风格、渠道或禁用元素变化。
- 人工修改节点生成结果。
- 重新生成成功并产生不同结果。

以下操作不会增加 revision：

- 上传进度从 10% 变为 90%。
- 只改变生成中、保存失败或待更新等状态。
- 重新生成失败，旧结果继续保留。
- 上游变化后，下游工作副本仅被标记为待更新。
- 修改 `WorkflowNodeState` 中的搜索、分页、展开状态等 UI 信息。

同一批上传的多个文件应在整批处理完成后合并更新一次资料包，避免选择 10 张图片就连续产生 10 个 revision。不同时间发生的独立上传操作可以分别产生 revision。

### 5.3 revision 和正式 version 的区别

```text
revision：工作过程中最新副本的内部修订号
version：归档后正式资产的版本号
```

例如工作区里的 Prompt 修改了 8 次：

```text
WorkingArtifact revision 8
```

第一次完成并归档后：

```text
ProjectAsset v1
来源：WorkingArtifact revision 8
```

后续重新工作并再次归档，才会产生正式的 `v2`。

## 6. workflowRunId 是什么

一个项目绑定一种工作流类型，但同一项目可能分多轮执行。

例如“广式腊肠夏季投放”是效果类项目：

```text
项目：PJT-FOOD-001
工作流类型：effect

第一轮：RUN-EFFECT-001
第二轮：RUN-EFFECT-002
```

用户临时退出后继续工作，不创建新 `workflowRunId`，仍恢复原来的执行轮次。

通常只有以下情况才创建新轮次：

- 上一轮已经完成并归档。
- 用户明确发起新一轮生产。
- 需要保留上一轮完整工作记录。

第一阶段可以限制每个项目同时只有一个活动或暂停中的 WorkflowRun，避免用户不知道应该继续哪一轮。

## 7. 完整例子：上传图片后返回删除

假设用户正在制作“广式腊肠夏季投放”。

### 7.1 在导入节点上传 10 张图片

用户选择文件、文件正在上传时：

```text
WorkflowNodeState(import)
状态：editing
已选择：10 张图片
```

上传过程中可以只有 `UploadSession` 和 `WorkflowNodeState`。10 张文件全部写入对象存储、创建 `FileObject` 并通过基础格式校验后，系统自动创建工作副本：

```text
WorkingArtifact
artifactKey：source-package:PRODUCT-SAUSAGE-001
revision：1
内容：10 张图片
```

此时资料包已经能在当前项目工作区看到。即使必填资料尚未补齐，也可以标记为“工作中 / 未完成”，方便用户临时退出后继续操作。

用户点击“下一步”时再执行节点完整性校验。该操作只决定是否允许进入提炼节点，不负责首次创建工作副本，也不是“保存到项目资产库”。

### 7.2 切换到提炼节点

切换前系统会：

1. 强制刷新导入节点草稿。
2. 校验导入资料包可以被下游使用。
3. 保存当前节点状态。
4. 进入提炼节点。

提炼节点读取的是 `source-package` 工作副本，而不是重新读取导入页面上的临时表单。

### 7.3 提炼尚未执行，返回删除 3 张图片

此时提炼节点还没有生成 `WorkingArtifact`。

用户返回导入节点，删除 3 张图片并自动保存成功后：

```text
原始资料包 revision 1 → revision 2
图片数量 10 → 7
```

状态变化：

```text
导入：已完成，工作副本 revision 2
提炼：待执行，没有工作副本
Prompt：未开始
渲染：未开始
```

因为提炼结果还不存在，所以不需要给一个不存在的结果增加 revision，也不需要标记“旧提炼结果待更新”。下次执行提炼时，直接读取最新的 7 张图片。

如果提炼页面已经填写了一些参数：

- 与输入资料无关的参数可以保留。
- 基于旧图片生成的预览和临时校验结果需要清空。
- 节点恢复为“待执行”。

### 7.4 提炼已经完成，再返回删除图片

假设提炼已经生成结果：

```text
营销洞察 revision 1
依赖：source-package revision 1
```

用户返回导入节点删除图片，资料包变为：

```text
source-package revision 2
```

系统比较依赖关系：

```text
营销洞察依赖 revision 1
当前资料包已经是 revision 2
```

因此把营销洞察标记为“待更新”。旧结果可以保留给用户查看，但不能继续用于正式下游生成、归档或发布。

重新提炼成功后：

```text
营销洞察 revision 1 → revision 2
依赖更新为 source-package revision 2
状态恢复为最新
```

### 7.5 删除文件时是否立即删除存储对象

页面删除图片时，先删除工作副本中的引用，不建议立即物理删除对象存储文件。

推荐流程：

1. 工作副本移除文件引用。
2. 数据库事务提交成功。
3. 检查文件是否还被草稿、其他工作副本或任务引用。
4. 对无人引用的文件延迟清理。

这样可以避免保存失败、任务执行中或用户误操作时丢失文件。

### 7.6 确认后修改全局视频配置

假设导入节点已经保存以下配置：

```text
global-video-config:PRODUCT-SAUSAGE-001
revision：1
时长：120 秒
画幅：3:4
风格：温馨生活感
渠道：京东
```

用户返回导入节点，把画幅改为 9:16、渠道改为抖音。配置自动保存并通过校验后：

```text
global-video-config revision 1 → revision 2
```

图片资料包内容没有变化，因此：

```text
source-package revision 保持不变
```

如果提炼、Prompt 或渲染结果依赖配置 revision 1，它们应标记为待更新，但自身 revision 暂时不增加。只有重新执行成功并生成新内容后，对应下游工作副本的 revision 才增加。

只打开下拉框、修改后又恢复成完全相同的内容、校验失败或保存失败，都不能增加配置 revision。

## 8. 用户临时退出项目怎么办

用户临时退出不等于完成项目，也不等于归档。

退出前系统只做：

1. 刷新当前节点未保存的 `WorkflowNodeState`。
2. 保留已经生成的 `WorkingArtifact`。
3. 记录当前节点和最后活动时间。
4. 把 WorkflowRun 标记为活动中或暂停中。

例如用户在 Prompt 节点退出：

```text
项目状态：进行中
执行轮次：RUN-EFFECT-001
当前节点：Prompt 生成

工作流草稿：保留当前生成参数和文本修改
工作区产物：保留资料包、营销洞察和现有 Prompt 批次
已归档资产：不变化
全局资产：不变化
```

用户下次点击“继续工作”时：

1. 加载同一个项目。
2. 恢复同一个 WorkflowRun。
3. 回到上次节点。
4. 加载该节点的 WorkflowNodeState。
5. 读取项目当前最新的 WorkingArtifact。

后台任务如果仍在运行，应继续由任务系统执行，不能因为浏览器关闭而取消。

## 9. 项目之间怎么隔离

所有业务查询都必须携带当前 `projectId`，不能只在前端把其他项目的数据隐藏起来。

例如：

```text
项目 A：广式腊肠夏季投放
项目 B：修护精华液新品投放
```

切换到项目 B 后，系统必须同时切换：

- 项目资料。
- WorkflowRun。
- 每个节点的 WorkflowNodeState。
- WorkingArtifact。
- 已归档 ProjectAsset。
- 来源于该项目的全局发布记录。

项目 B 不能看到项目 A 的工作流草稿和工作区产物。

如果项目 B 想使用项目 A 的正式资产，应执行“从其他项目导入”：

```text
项目 A 的 ProjectAsset v2
        ↓ 复制快照
项目 B 新建自己的 ProjectAsset
        ↓
记录来源项目 A、来源资产和来源版本 v2
```

项目 B 后续修改自己的资产，不影响项目 A。

## 10. 项目中心应该如何显示

项目中心不应该把所有数据都画成相同的资产卡。建议明确区分状态：

```text
广式腊肠夏季投放
PJT-FOOD-001 · 效果类 · 暂停中

当前节点：Prompt 生成 · 3/6
工作流草稿：3 个节点有记录
工作区产物：18 项，其中 2 项待更新
已归档资产：26 项
全局发布资产：4 项
最后保存：今天 14:32

[继续工作] [项目资产]
```

进入项目资产详情后分区展示：

```text
工作中
├─ 节点草稿摘要
└─ 工作区产物（显示 revision 和依赖状态）

已归档
└─ 正式项目资产（显示 v1、v2 等版本）

已发布
└─ 来源于本项目的全局资产
```

必须明确使用这些提示：

- 正在保存。
- 已自动保存。
- 工作副本已更新。
- 尚未归档。
- 上游已变化，待更新。
- 已归档 v1。
- 已发布到全局资产库。

不要再出现：

- 保存当前节点产物。
- 保存到项目资产库。
- 每修改一次就创建一个正式版本。
- 退出项目时自动归档。

## 11. 当前实施边界

当前《工作流草稿与工作副本自动维护方案》主要实现：

- `WorkflowRun`。
- `WorkflowNodeState` 自动保存。
- `WorkingArtifact` 最新工作副本。
- revision、内容哈希和项目隔离。
- 当前项目中“工作中 / 尚未归档”的只读展示。

当前阶段不应假装已经实现：

- 完成工作流并归档。
- 将工作副本物化为 `ProjectAsset`。
- 正式资产版本链。
- 发布到 `GlobalAsset`。
- 跨项目复制正式资产。

这些能力可以在工作副本稳定后分阶段实现。未实现时，前端应该展示真实空状态或“暂未归档”，不能使用前端 Mock 冒充正式资产。

---

## 12. 最后记住这五句话

1. `WorkflowNodeState` 保存的是“用户在节点页面上编辑到了哪里”。
2. `WorkingArtifact` 保存的是“节点目前最新、可以给下游使用的结果”。
3. `revision` 是工作过程中的修订号，不是正式资产版本。
4. `ProjectAsset` 只有完成工作流并归档后才产生。
5. `GlobalAsset` 只有用户明确发布后，才能被其他项目复制复用。
