# Prompt 软时长四档真实付费验收

## 1. 验收范围

- 日期：2026-08-31
- 商品：同一份已提交的广式腊肠营销洞察
- 批次：5 秒、15 秒、22 秒、30 秒各 1 个真实批次
- 数量：每批目标 50 条，共检查 200 条最终 Prompt
- 链路：浏览器设置与启动 → 公共 API → Outbox/RabbitMQ → 真实 Ark Worker → 分片持久化 → API 结果保存 → 页面刷新恢复
- Seedance 视频调用：0 次
- WorkingArtifact 提交：0 次

本次只验证用户时长是否通过软提示影响创意容量、动作密度和评估结果，不用正文长度单独代替视频可执行性判断。

重要限制：5 秒、15 秒和 22 秒使用同一冻结 Worker。30 秒任务执行中，工作区被另一项并行操作修改并重建了 Prompt Worker；重建前已完成 15 个生成分片，恢复后补跑剩余分片并执行评估。因此 30 秒只能作为“功能与租约恢复样本”，不能与前三档构成严格的冻结版本质量对照。

## 3. 确定性检查

四个批次均满足：

- 最终数量严格为 50 条。
- 每条 `targetDurationSeconds` 与所属批次时长完全一致。
- Prompt 正文没有出现时长、画幅、分辨率等渲染元数据。
- Prompt 正文没有复述批次共用提示词中的禁用内容。
- 每条正文均包含广式腊肠、腊肠或香肠等产品/品类表达。
- 模型评估未报告多场景时间线硬问题。

辅助文本检查发现，显式时间推进表达随时长增加：5 秒 3 条、15 秒 7 条、22 秒 12 条、30 秒 16 条。说明模型不仅改变文字长度，也会为较长时长增加动作阶段。

## 4. 结论

软时长方案部分有效：

- 5 秒到 22 秒呈现清晰的容量阶梯，平均字数、句数和动作标记逐档增加，画面可执行性同步提升。
- 22 秒表现最好，动作容量与时长较匹配，过密从 5 秒的 28/50 降至 6/50。
- 5 秒虽然明显缩短正文并减少动作，但仍有 28/50 条被评为过密，短时长提示力度不足。
- 30 秒没有继续增加平均字数和动作标记，但时间推进表达最多；样本表面上显示模型倾向用停留、缓慢运镜和前后阶段消耗时长，而不是机械增加动作。由于本批混用了重建前后的 Worker，只能把它作为待复验现象，不能据此证明 30 秒档稳定优于或弱于 22 秒档。
- 30 秒样本中出现少量从玄关移动到餐厅、从送礼延伸到上桌的连续家居段落。它们仍处在同一家庭时空，但已接近“多个独立素材片段”的边界，现有评估没有给出多场景提醒。

因此不建议把时长改成硬性的字数、镜头数或动作数配额。下一步优先优化两处软约束：

1. 4～8 秒进一步强调单一视觉事件，避免“切制后再下锅”“递礼后再展示”等双阶段动作。
2. 23～30 秒允许前后阶段，但限制为同一主空间内可连续拍摄的动作，避免从玄关、厨房再到餐桌的完整广告时间线。

在修改模板前，本次结果只支持“5～22 秒的机制生效、短时长仍需优化，30 秒已跑通但需要冻结版本复验”，不支持宣称所有 4～30 秒时长都已经稳定适配。

复验使用的 4～8 秒确定性提醒阈值比首轮更严格，但过密数量仍从 28 条降到 16 条，说明下降不是放宽检测口径造成的。平均字数基本不变，而动作标记和时序连接词明显下降，表明修正主要压缩了动作阶段，没有简单把正文缩短成信息不足的句子。

本批执行过程中环境被外部连续重建 Prompt Worker 两次，API 通过租约恢复和分片检查点最终在第 3 次尝试完成；两次重建后的容器关键源码哈希均与当前修复代码一致。墙钟耗时 607 秒受重建影响，不作为性能结论。该批未调用 Seedance，也未点击“完成校验”，因此没有覆盖现有 `prompt-batch:{productId}` WorkingArtifact。

结论：单一视觉事件方案有效，5 秒过密问题得到明显缓解，但 16/50 仍不是理想终态。后续若继续优化，应优先处理仍被选中的“单一主动作内部描述过长”和少量“交接后继续寒暄/展示”的边界案例，不应把软提醒升级为硬淘汰，以免破坏 50 条精确数量。
