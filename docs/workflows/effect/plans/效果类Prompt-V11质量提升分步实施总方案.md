# 效果类 Prompt V11：质量提升分步实施总方案

## 1. 文档状态

- 状态：实施项一“提炼事实的视觉使用策略”已完成（自动测试通过，未执行新的真实 Ark 付费验收）
- 日期：2026-08-28
- 工作流：效果类
- 业务节点：第 3 节点“Prompt 生成”
- 实施原则：每一项单独确认、单独实现、单独测试，不默认连续实施

本文把真实付费测试暴露的问题和后续改造方向集中到一份文档中。实施项一已经完成编码与自动回归；实施项二～六仍未开始，也不代表已经确认实施。

## 2. 固定业务边界

### 2.1 直接上游

Prompt 节点只消费已经提交且为 CURRENT 的：

- `marketing-insight:{productId}` 营销洞察工作副本；
- 全局视频配置的具体工作副本 revision；
- 当前批次的一段式共用提示词。

每次运行必须记录实际消费的 `artifactId + revision + contentHash`，不能读取尚未确认的上游页面草稿。

### 2.2 当前节点输出与提交边界

- 模型生成、质量评估、人工编辑和重新分类只更新 Prompt 领域草稿及 `WorkflowNodeState`。
- 只有用户点击“完成校验”，且数量准确、全部条目已验证，才提交 `prompt-batch:{productId}` WorkingArtifact。
- 生成失败、短批次或 `NEEDS_REVIEW` 不得覆盖上一份有效工作副本。

### 2.3 直接下游

视频渲染节点只消费已提交的 Prompt 批次。一条 Prompt 对应一个素材片段，不是完整成片脚本。画幅、分辨率和时长继续作为结构化渲染参数传递；共用提示词只在视频请求编译时追加一次。

### 2.4 本方案不做什么

- 不恢复六类片段生成配额或六条独立 AI 生成分支。
- 不重新建立六维坐标池、正交组合或重型三轮门禁。
- 不修改效果类第 4～6 节点。
- 不实现 Seedance 视频渲染。
- 不新增 Prisma 表和生产依赖。
- 不把共用提示词复制进每条 Prompt 正文。

## 3. 真实测试结论

两次已授权付费测试使用同一个“广式腊肠”营销洞察 revision 2、目标 50 条、统一 15 秒：

1. 第一次测试成功生成 60 条候选，但每片 5 条的质量评估多次返回提前结束的严格 JSON，最终没有形成批次结果。
2. 将评估分片缩小为每片 3 条并通过非付费回归后，第二次测试成功从 60 条候选中选出 50 条。

第二次测试结果：

```text
最终数量：50 / 50
商品锚点：50 / 50
完全重复：0
定向补充：0
综合模型评分：93.90
平均正文 trigram：0.0406
最高正文 trigram：0.2037
实际 Ark 调用：37
输入 / 输出 / 总 Token：123000 / 51180 / 174180
端到端耗时：228 秒
```

与最近两批同配置 V2 基线相比，综合模型评分平均只提高 0.89 分。人工逐条复核确认：镜头与动作衔接有所改善，但没有达到“大幅提升”。主要问题是：

- 50 条中 30 条仍集中在厨房，27 条仍包含切制动作；六维文字不同不等于业务创意真正不同。
- `P003、P006、P014、P023、P041、P049` 仍通过切面、肉纤维或粉质感暗示“纯猪肉无淀粉”。
- `P039、P044` 仍把成品光泽或糖酒料汁摆拍与糖酒腌制工艺直接关联。
- `P009、P040` 出现未经烹制直接品尝腊肠，`P019` 出现隔着密封包装闻香。
- `P016、P021、P045` 在 15 秒内安排过长动作链或三种完整做法。
- AI 评估分数没有稳定识别以上客观问题，不能直接把 `PASS` 当成真实质量结论。

因此后续重点不是继续堆叠主 Prompt 约束，而是把确定的业务规则放到 Worker，把主观创意判断继续交给模型。

## 4. 目标子工作流

保持现有用户可见业务节点不变，Prompt Worker 内部逐步演进为：

```text
输入快照
→ 提炼事实准备
→ 事实视觉使用策略编译
→ 共用提示词编译
→ 轻量差异方向分配
→ 连贯六维创意生成
→ 客观业务错误检查
→ AI质量评估与用途分类
→ 业务语义差异择优
→ 必要时定向补充
→ 结果保存
```

模型仍在一次调用中共同生成创意主线、六维和完整正文。新增阶段只负责给模型更清楚的边界，并检查客观错误，不把六维重新拆成互相独立的词池。

| 当前提炼字段与原始值 | 内部策略 | 允许用于 Prompt 的方式 | 禁止推导 |
| --- | --- | --- | --- |
| `productName`：广式腊肠 | 产品身份锚点 | 明确画面主体 | 不替换成其他腊味产品 |

| `coreSellingPoints[0]`：三七肥瘦黄金配比 | `CONTEXT_ONLY` | 用确认的“肥瘦纹理清晰分明”视觉特征辅助表达 | 不声称肉眼可以精确证明三七比例 |
| `coreSellingPoints[1]`：广府糖酒腌制工艺 | `CONTEXT_ONLY` | 作为风味与创意背景 | 不摆拍糖酒料汁冒充真实生产过程，不用成品光泽证明工艺 |
| `coreSellingPoints[2]`：纯猪肉无淀粉 | `FORBIDDEN_VISUAL_PROOF` | 只作为营销信息背景，当前纯视觉 Prompt 不承担证明 | 不用切面、肉纤维、弹性或“没有粉质感”证明 |
| `secondarySellingPoints[0..2]`：肥瘦纹理、饱满色泽、油润质感 | `DIRECTLY_VISIBLE` | 使用切面、整根外观或蒸熟成品特写 | 不进一步推导精确配比、配方或产地 |
| `secondarySellingPoints[3]`：咸甜酒香回甘 | `CONTEXT_ONLY` | 指导家庭用餐、品尝后的自然情绪 | 不把人物表情当作具体风味证明，不允许未烹制直接品尝 |
| `secondarySellingPoints[4]`：真空锁鲜 | `ACTION_DEMONSTRABLE` | 展示密封包装、拆袋和储存取用 | 不证明保鲜时长，不虚构实验对比 |
| `secondarySellingPoints[5]`：适配煲仔饭、蒸、炒 | `ACTION_DEMONSTRABLE` | 一条 Prompt 选择一种烹饪方式 | 不在15秒片段中完整演示三种做法 |
| `targetAudience` | `CONTEXT_ONLY` | 选择合理人物身份 | 不把整段受众描述写入正文 |
| `corePainPoints`、`decisionDrivers` | `CONTEXT_ONLY` | 指导叙事动机和场景选择 | 不把担忧直接伪造成可见结论 |
| `usageScenarios`、`purchaseScenarios` | `ACTION_DEMONSTRABLE` | 家庭用餐、厨房加工、节日礼赠三类可信场景 | 不增加上游没有的实验室、办公室等场景 |

| `marketingGoal` | 内部规划信息 | 影响商业表达方向 | 不写成画面中的“营销目标”元数据 |
| `priceRange`：含“需结合品牌与渠道确认” | 排除 | 不进入生成任务 | 不出现45～75元或任何促销价格 |
| `trustBackings`：空数组 | 排除 | 不传给模型 | 不补造认证、销量或背书 |
| `durationSeconds`：60 | 上游背景 | 不覆盖 Prompt 节点设置的统一15秒片段时长 | 不写进 Prompt 正文 |
| `aspectRatio`、`resolution` | 结构化渲染配置 | 由 Prompt 批次 `renderProfile` 保存 | 不写进 Prompt 正文 |
| `deliveryChannels`：抖音 | `CONTEXT_ONLY` | 指导短视频商业表达 | 不写成“渠道：抖音”元数据 |
| `visualStyleBaseline`：烟火食欲感 | `CONTEXT_ONLY` | 指导光线、食物状态和生活氛围 | 不要求每条复述“烟火食欲感” |
| `disabledElements` | 共用提示词来源 | 沿用批次级一段式共用提示词 | 不复制进每条正文 |

字段名只能提供初步职责，不能可靠判断任意商品事实应该怎样进入画面。因此本阶段必须调用模型完成跨品类语义判断。Worker 不负责硬编码“香肠、护肤品、家电”等商品规则，只负责校验模型引用的 `factId` 必须来自当前营销洞察、排除不确定事实，并拒绝空策略、未知引用和对原始事实的篡改。无法确定的事实保守降级为 `CONTEXT_ONLY`，策略编译失败时不得静默伪装成功。

#### 实现位置

- 在现有提炼事实映射之后新增内部子流程节点“事实视觉使用策略编译”，先调用一次 AI 编译批次级策略，再由 Worker 校验并缓存。
- 现有事实分配器不再把语义含糊的 `primaryFact` 直接交给生成模型，而是把本条事实分成 `visualTask` 与 `businessContext`：前者必须成为可见画面，后者只影响商业方向且不得承担视觉证明。
- 创意任务只接收本条 `visualTask`、少量 `businessContext`、产品锚点和直接相关的禁止推导，不接收整张策略表或一大段通用警告。
- 评估阶段使用同一份策略检查事实证据，不维护第二套规则。
- 新数据只存入现有阶段 metadata 或分片计划，不修改 V6 公共结果 Schema。

#### 验收标准

- “纯猪肉无淀粉”不再通过纤维、切面或粉质感证明。
- “糖酒腌制工艺”不再通过成品光泽或临时道具证明。
- “油润透亮”等可观察事实仍可正常生成特写。
- 单元测试覆盖每种视觉使用策略。

#### 实际实现与测试结果

- 新图版本为 `V11_VISUAL_USAGE_STRATEGY`，在“提炼信息应用映射”与“共用提示词编译”之间新增内部节点 `FACT_VISUAL_STRATEGY_COMPILATION`。
- 策略模板版本为 `effect-prompt-v11-fact-visual-strategy-v1`；连贯创意模板升级为 `effect-prompt-v11-coherent-creative-v4`，评估模板升级为 `effect-prompt-v11-creative-evaluation-v3`。
- 同一项目、工作流、商品下，API 会读取此前成功的策略阶段；只有 `sourceFingerprint` 与当前营销洞察 `contentHash` 完全一致时 Worker 才复用。缓存不匹配、引用未知事实、遗漏可用事实、职责空缺或策略不合法时均拒绝复用或拒绝完成，不静默退回旧分配。
- 生成任务已把原主要事实拆为 `visualTask` 与 `businessContext`；抽象卖点可以继续影响商业表达，但不能占用可见画面任务。评估模型复用候选实际引用事实对应的策略片段，不维护第二套视觉边界。
- 公共 Prompt V6 结果、HTTP 路径、Prisma Schema、WorkingArtifact 提交边界均未改变；V8～V10 与原 V11 Run 继续按显式历史拓扑读取。

### 实施项二：产品动作状态与食品使用规则

状态：待确认

#### 解决的问题

广式腊肠的保守状态链：

```text
密封包装 → 拆封 → 切配 → 烹制完成 → 上桌 → 品尝
```

若上游没有可信的“开袋即食”信息，则任何品尝动作必须发生在烹制之后。

#### 实现位置

- 根据产品品类和已确认事实编译批次级使用规则。
- 生成模板只接收本条动作所需的前置状态。
- Worker 对明显状态冲突做确定性检查；AI 分数无权覆盖该结果。
- 首期只实现已确认食品规则，不建立一个无法维护的全行业知识库。

#### 验收标准

- 不再出现拆袋后直接品尝生腊肠。
- 不再出现隔着密封包装闻到香味。
- 动作状态按时间顺序推进。
- 无法确认是否即食时采用保守规则，而不是模型自行推测。

### 实施项三：轻量差异方向分配

状态：待确认

#### 解决的问题

避免模型自由生成时大量收敛到“厨房＋砧板＋切面特写”，同时不恢复六类生成配额和机械六维坐标池。

#### 内部数据设计

```ts
type CreativeDirection = {
  primaryFactId: string;
  priorityDimensions: Array<
    "NARRATIVE" | "SCENE" | "PERSONA" |
    "PRODUCT_RELATION" | "CAMERA" | "EMOTION"
  >;
  preferredSceneFamily?: string;
  preferredActionFamily?: string;
  avoidFamilies: string[];
};
```

每条任务只领取 2～3 个优先变化维度，例如：

```text
A：家庭备餐＋烹饪动作＋俯拍跟随
B：年货选购＋挑选动作＋人物视角
C：餐桌分享＋夹取动作＋食物微距
```

这只是创意方向，不是完整蓝图。模型仍一次生成互相连贯的六维和正文。

#### 实现位置

- Worker 根据可信场景、受众、购买场景和已分配事实生成方向。
- 不调用额外模型，不增加付费调用数量。
- 方向只能使用上游真实存在或业务上安全可推导的场景，不为了差异强行加入实验室、办公室或无关户外场景。

#### 验收标准

- 生成输入不包含六类配额。
- 每条仍只有一个主场景和一条连续动作。
- 批次不再主要收敛到单一厨房切片组合。
- 六维、创意主线和正文继续属于同一个创意。

### 实施项四：客观业务错误检查

状态：待确认

#### 解决的问题

AI 评估给高分时，仍可能放过事实视觉证明、食品状态错误和 15 秒动作过载。

#### 稳定问题码

首期建议只增加能够确定判断的问题：

```text
ABSTRACT_FACT_VISUAL_PROOF
PRODUCT_STATE_CONTRADICTION
SEALED_SENSORY_CONTRADICTION
ACTION_ARC_OVERLOAD
MULTI_SCENE_TIMELINE
FACT_FABRICATION
PRODUCT_UNRELATED
EXACT_DUPLICATE
```

普通相似、场景集中、人物集中和用途不均继续作为软提醒，不直接淘汰。

#### 实现位置

- 事实视觉证明检查复用实施项一的策略。
- 产品状态检查复用实施项二的状态规则。
- 动作过载只检查明显的多地点、多时间跳转或多条完整动作链，不按字数粗暴淘汰。
- AI 评估继续负责连贯性、商业价值、情绪和审美等主观判断。

#### 验收标准

- 确定性错误不能被高 AI 分数覆盖。
- 软相似不会被误判为硬失败。
- 每个问题码都有正例、反例和边界测试。

### 实施项五：按业务语义族群择优

状态：待确认

#### 解决的问题

当前六维字符串 50 条都不相同，但业务语义仍可能是同一个“厨房切片”。需要比较真正的场景、动作和镜头类别，而不是只比较文字。

#### 内部数据设计

```ts
type CreativeFamilySignature = {
  narrativeFamily: string;
  sceneFamily: string;
  actionFamily: string;
  cameraFamily: string;
  productRelationFamily: string;
};
```

选择分数建议调整为：

```text
70% 单条质量
20% 相对已选内容的新颖度
10% 批次场景与动作覆盖价值
```

同类内容过多时降低排序，不设置“一旦超过数量立即淘汰”的硬配额。

#### 实现位置

- 首选使用现有六维、创意主线和正文做确定性规范化。
- 若现有向量能力稳定，可用于语义近似比较；向量不可用时必须安全回退到规则与 trigram，不得阻塞生成。
- 不用“六维字段字符串唯一数”冒充真实差异化指标。

#### 验收标准

- 报告厨房、餐桌、购物、礼赠、储存、烹制等真实场景族群分布。
- 报告切制、拆袋、烹制、夹取、选购、装礼等动作族群分布。
- 高质量同类内容不会全部被硬淘汰，但不会挤占绝大多数最终名额。
- 最终仍严格满足用户设置的总数量。

### 实施项六：问题定向补充与质量报告

状态：待确认

#### 解决的问题

避免一条错误导致整批重跑，也避免补充模型在不知道失败原因的情况下重复生成同类问题。

#### 工作方式

```text
初次候选
→ 客观错误检查与AI评估
→ 保留合格候选
→ 汇总缺口、稳定问题码和过度集中的语义族群
→ 只补生成缺少的候选
→ 使用相同检查和选择流程
```

补充输入只包含：

- 缺少数量；
- 需要避开的稳定问题码；
- 已选场景、动作和镜头族群；
- 较少使用的可信事实及安全方向。

禁止使用规则模板拼接正文兜底。一次补充后仍不足则保存草稿并进入 `NEEDS_REVIEW`。

#### 质量报告

结果页和工作流详情只展示用户能理解的摘要：

- 目标、候选、合格、最终数量；
- 客观错误数量与类型；
- 场景、动作、镜头族群分布；
- 是否发生定向补充；
- 最多 3 条代表性问题样例。

不展示模型名称、原始响应、内部事实 ID、存储键或完整内部 JSON。

#### 验收标准

- 单个问题候选不会触发整批重新生成。
- 补充候选能明确避开上一轮主要问题。
- 仍不足时不伪造精确数量成功。
- WorkingArtifact 提交边界保持不变。

## 6. 推荐实施顺序

推荐顺序不代表自动授权：

| 顺序 | 实施项 | 原因 | 是否增加模型调用 |
| --- | --- | --- | --- |
| 1 | 事实视觉使用策略 | 先解决事实误导和合规风险 | 是；每个新的提炼内容哈希编译一次，批量生成复用 |
| 2 | 产品动作状态规则 | 解决生食、密封闻香等明显错误 | 否 |
| 3 | 客观业务错误检查 | 让前两项真正成为质量边界 | 否 |
| 4 | 轻量差异方向分配 | 从生成源头减少厨房切片集中 | 否 |
| 5 | 业务语义族群择优 | 在最终50条中控制真实同质化 | 否 |
| 6 | 定向补充与质量报告 | 用较低成本修复剩余缺口 | 仅缺口出现时增加 |

优先完成 1～3，可以先解决“内容错误”；再完成 4～5，解决“内容单一”；最后完成 6，补齐生产稳定性和用户可见解释。

## 7. 每项实施的统一流程
