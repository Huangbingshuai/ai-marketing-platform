# 混剪自动分支：去掉编辑会话，并修掉让包装必然失败的克隆绑定

## 目标与边界

用户真机跑了一遍「紫苏梅子酱 / 测试1模板」的智能成片包装，反馈两件事：

1. 混剪节点上出现了「编辑草稿中 · 模板混剪 / 修改会先保存在当前编辑副本；保存版本后才会发布，取消编辑会放弃本次修改」——**混剪节点根本没有进入编辑这一套**，智能成片包装成功之后直接新增分支就行，生成的成片等退出模板（精修工作台）时才同步到成片节点。
2. 包装完既没有新分支，成片节点也没有成片。

第 2 点不是同一个问题的表象，而是另一个独立缺陷：**包装本身失败了**。两个根因都要修，否则横幅消失了功能还是不通。

不在本次范围：分支时点语义（上一份计划已定：混剪填充/包装成功即新增分支、成片整批导出成功才新增分支）、成片局部更新、前四个节点的编辑会话。

## 根因

### 根因一：`always: true` 的分支仍然挂着编辑会话

`beginEffectEditInTransaction` 建子 Run 时无条件写 `editSessionNodeId: nodeId` / `editSessionPurpose: purpose`（`effect-edit-session.ts:131-138` 旧代码）。`always: true` 只是让它「首版也 fork」，没有区分「这次 fork 是编辑会话还是任务自己开的分支」。

于是包装 fork 出的子 Run 满足 `isTemporaryBranch = parentWorkflowRunId && !branchPublishedAt && editSessionNodeId`，画布横幅（`EffectImportNodePage.vue:167-172` 的 `editingCurrentNode`）就亮了，并且顺带禁用了「手动新建分支」（`forkCurrentBranch` 在 `isTemporaryBranch` 时拒绝）。

用户说得对：这类分支没有任何东西可保存、可发布、可取消，任务成功时自己就会发布它，它就不该是会话。前端不用改——横幅的判据是后端字段，字段空了横幅自然不亮。

### 根因二：克隆节点状态时没有重映射产物 id，包装必然失败

worker 日志：`packaging checkpoint rejected ... reason=源时间轴已改变，本条包装已过期`。

`workerItem`（`effect-packaging.service.ts:847-866`）会用 `repo.sourceArtifacts(projectId, run.workflowRunId, ids)` 按 **Run 维度**校验冻结快照里的每个依赖；`EffectPackagingRepository.sourceArtifacts` 是 run-scoped 的。

而 fork 时的顺序是：先 `remap(state.state, ids)` 克隆节点状态（`ids` 里只有 workspace/draft/product 的 id），**之后**才给产物分配新 id（`artifactIds`）。混剪草稿的 `bindings` 是 `slotId → materialId`，`materialId` 就是 `render-clip` 产物的行 id（`effect-template-mix.service.ts` 的 `materialFrom` 用 `id: artifact.id`）。所以子 Run 的草稿仍然绑在**父 Run 的**片段 id 上，包装快照就把这些父 Run 的 id 冻了进去，worker 在子 Run 里查不到 → 每一条包装都被判「源时间轴已改变」。

实测（紫苏梅子酱残留子 Run `6c25a779`）：48 条槽位绑定，能在本 Run 解析到的 **0** 条。父 Run `95c92da8` 自己则是 48/48 —— 也就是说这不是「父 Run 脏」，纯粹是克隆漏了这一步。

## 改法

- `apps/api/src/platform/workflow/effect-edit-session.ts`
  - 克隆节点状态**挪到产物 id 分配之后**，改用 `clonedIds = { ...ids, ...artifactIds }` 重映射；节点状态本身不引用 packaging 快照，所以只多这一处映射就够。
  - 建子 Run 时 `editSessionNodeId` / `editSessionPurpose` 只在**非** `always` 时写入（自动分支不带会话字段）。
  - `editBaselineHash` 只在非 `always` 时算——自动分支没有会话，也就没有基线可比。`exitEffectEditInTransaction` 里 `changed = publish && editBaselineHash !== digest` 因此对自动分支恒为真，落到「有产物就发布」。
  - 复用判定抽出 `isOwnSession` / `isOwnAutoBranch`：自动分支靠 `editSessionNodeId === null && forkNodeId === nodeId` 被认领（调用方仍然要传 `always`），其余调用方行为不变。
  - `exitEffectEditInTransaction` 的 `draft.editSessionNodeId !== nodeId` 改为同时接受 `draft.forkNodeId === nodeId`，否则 `publishEffectNodeEdit` 会对自动分支返回 null → 服务层抛 409，分支永远发不出去。
- `apps/api/src/workflows/effect/final-output/effect-final-output.service.ts` `publishEditBranch`：守卫从「必须是会话」放宽为「会话或本节点的 fork 点」，同样读 `forkNodeId`。

## 测试

- `effect-edit-session.database.spec.ts`「forks the first version…」用例扩写：断言自动分支 `editSessionNodeId` / `editSessionPurpose` / `editBaselineHash` 全空、`forkNodeId` 命中；把子 Run 的 `TEMPLATE_MIX` 草稿里所有 `bindings` 收集起来，断言**每一个都落在本 Run 的 `render-clip:` 产物 id 集合内**（这正是根因二的判据）；补一条 `mix-template:` 产物后调 `publishEffectNodeEditInTransaction`，断言 `createdBranch: true` 且 `branchPublishedAt` 落库（自动分支靠 forkNodeId 发布）。夹具补了一份 `TEMPLATE_MIX` 节点状态，否则 fork 无草稿可克隆。
- `effect-final-output.service.spec.ts` 新增「publishes a mix branch that was opened without an edit session」（`editSessionNodeId: null` + `forkNodeId: 'TEMPLATE_MIX'` 也要发布），既有「不相关的 Run 不动」用例补上 `forkNodeId`。
- **DB 夹具不再依赖「哪个 Run 恰好是活动 Run」**：`effect-edit-session.database.spec.ts` 与 `effect-segment-render.branch.database.spec.ts` 原先按 `activeKey: 'ACTIVE'` 挑夹具，而真机上各项目的活动 Run 会随使用漂移（紫苏梅子酱的活动 Run 一度是那条残留子 Run），于是「挑到一条开不了编辑的子 Run → 断言 null」。改为挑「根 Run 或已发布分支」（`parentWorkflowRunId: null` 或 `branchPublishedAt != null`），再在回滚事务里把它设成活动 Run。

## 存量数据清理

旧代码在紫苏梅子酱留下的子 Run `6c25a779-f86b-4d85-9b24-47f68ef8617b` 是这次两个根因的产物：24 条克隆产物、4 份节点状态、2 条 `FAILED` 包装、1 个渲染批次、45 条产物依赖，**没有** `mix-template:` / 成片产物 / output run，即没有任何用户成果。它既是横幅的来源，也是「重试包装必定再失败」的原因（草稿绑定指向父 Run）。经用户确认后删除，并把项目活动分支交回已发布的 `95c92da8`；删除前确认没有其它 Run 以它为父（`parentWorkflowRunId` 是 `Restrict`），删后全库孤儿产物为 0。产物依赖表对「源产物」是 `RESTRICT`，且依赖与被依赖产物同在一个 Run 内，所以要先显式删依赖行再删 Run。
