# 时间轴音频片段重叠分行（字幕口播不再压在口播上）

日期：2026-09-25
需求原话（实测问题）：

> 为什么新生成的口播素材直接把下面的口播素材给叠加了啊，都是单独的啊，播放的时候看音频轨道那个时刻有多少一个音频素材就同时播放啊，现在把新生成的删除，旧的直接变成新的了

即：**同一时刻的两条音频片段被画在同一行、互相压住**。用户要的是「同一时刻有几条就都看得见、都同时出声」，而不是谁盖住谁。承接 `2026-09-24-精修工作台字幕生成口播.md`（字幕口播与槽位口播「并列新增」的口径不变）。

---

## 一、范围

| 现象                                                             | 本轮口径                                                                                                                                                                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 新生成的字幕口播压在原有口播片段上，删掉它下面那条又「变成新的」 | 时间轴音频区**同一时刻的片段不再共用一行**：片段实际落在哪一行，由「它想要的行 + 该行在这个时间段是否已被占」共同决定，被占则顺次下移。与视频轨既有的 `assignIntervalLanes` 同一套不变量。 |

**不改**：字幕口播与槽位口播仍然可以**时间上重叠**（`2026-09-24-精修工作台字幕生成口播.md` 决策 2），也仍然**同时播放**（`2026-09-25-字幕口播对齐与试听修复.md` 已经给字幕口播补了独立音频元素）。本轮只解决「画在一行上互相压住」。

## 二、现状与实测证据

### 2.1 两条片段确实被写成了同一行（本地 Postgres 实测）

成片 `71027be6-97a9-4770-8f02-42650a677b32`（项目 `65458686-034c-4258-b2dd-027d4ad15132`，变体 `50961c22-73cc-401e-b653-c862f2d536a7`）：

```
checkpoint.voices       slot-aa4006ff…@0+2.209  slot-e16580d5…@4+6.979  slot-8ae16e83…@14+6.767
                        slot-3a1c77d7…@24+7.559  slot-262f54e1…@34+6.767  slot-c544a158…@42+2.390
checkpoint.captionVoices caption-2183e9e9…@8.766+3.010
checkpoint.music        start 0 dur 46

variant.audioLanes = {
  "music": 1,
  "voice:slot-262f54e1960aa4d34c847513": 0,  … 另外五条 voice:slot-* 也都是 0,
  "capvoice:caption-2183e9e90838e91503c6b262": 0
}
```

字幕口播的区间是 `8.766 – 11.776`，`voice:slot-e16580d5…` 是 `4 – 10.979`，**重叠 2.21s**，而两者都被记在 **第 0 行**。另一条变体 `64e307ba…` 同样如此（`capvoice` 在第 0 行、与一条 `voice:slot-*` 重叠）。

### 2.2 为什么两条 VOICE 一定会同排

`apps/web/src/workflows/effect/template-mix/effect-template-mix-audio-lanes.ts`：

```ts
export type AudioClipKind = 'DETACHED' | 'MUSIC' | 'VOICE';
export const DEFAULT_AUDIO_LANE: Record<AudioClipKind, number> = {
  VOICE: 0,
  MUSIC: 1,
  DETACHED: 2,
};
export const rawAudioLane = (lanes, ref) =>
  Math.max(0, Math.round(lanes?.[ref.id] ?? DEFAULT_AUDIO_LANE[ref.kind]));
```

字幕口播在 `timelineAudioClipRefs` 里被登记成 `{ id: 'capvoice:<captionId>', kind: 'VOICE', source: 'PACKAGED' }`（`:90-92`），和 `voice:<lineId>` **同为 `VOICE`**，所以两者回落到**同一个默认行 0**。

而且这个 0 会被**写死进 `variant.audioLanes`**：`compactAudioLanes`（`:149-158`）对每个 ref 执行 `lanes[ref.id] = compacted.get(rawAudioLane(lanes, ref)) ?? 0`，`normalizeVariantAudioLanes` 在加载时（`EffectTemplateMixNodePage.vue:1261`）就会跑一遍。上面的实测数据正是这个结果 —— 一旦落成显式的 0，之后再改「默认行」也不会自愈。

时间轴画片段时按行给 `top`，行相同 → 同一个 `top`/高度 → **后画的（`capvoice` 在 `voices` 之后入列）正好盖住先画的**。删掉盖在上面的那条，露出来的还是同一个位置、同一个样子的片段，用户读作「旧的直接变成新的了」。

### 2.3 视频轨本来就不是这么做的

`EffectTemplateMixTimeline.vue:609-621` 的 `assignIntervalLanes`：按 `start` 排序，`laneEnds.findIndex((end) => end <= item.start + 1 / fps)` —— **时间不重叠才允许共用一条轨**。音频区缺的正是这条不变量。

## 三、设计

### 一、把「行」从「片段的属性」改成「排出来的位置」

在共享模块里新增 `resolvedAudioLanes(refs, lanes)`：按 `(想要的行, start, id)` 排序，逐个放到**第一个「当前结束时间 ≤ 本片段 start」的行**；想要的行已被占就顺次下移。想要的行 = 存过的行 ?? 该 kind 的默认行。

- 这是**纯函数**，输入是全部片段与存过的行，输出 `clipId → 实际行`。
- 排序键把「想要的行」放在最前：显式拖到高行的片段最后处理，不会反过来抢低行；同一 kind 的片段按时间依次落位。
- 对上面那条实测数据的结果：`行0 = 6 条口播`、`行1 = 字幕口播`、`行2 = 包装音乐`。字幕口播紧贴口播之下，音乐被让到下一行。

### 二、四个读行的函数改读「实际行」，签名全部不变

`occupiedAudioLaneValues` / `audioRowOf` / `audioRowCount` / `compactAudioLanes` **本来就都收 `refs`**，所以内部换成 `resolvedAudioLanes` 即可，`EffectTemplateMixNodePage.vue` 与 `EffectTemplateMixTimeline.vue` 的调用点**一处都不用改**。

`rawAudioLane` 保持原样（= 「想要的行」），因为它另外两处用途（`NodePage:1989` 落轨前把默认行落成显式值、`NodePage:3852` 读拖入行）语义是「用户的意图」，不是「最终排在哪」。

`compactAudioLanes` 改为把**实际行**压缩后写回，于是修正后的行会随下一次保存落到服务端；即使没保存，时间轴/静音/拖动读的也都是同一个实际行，三端不会漂。

### 三、`AudioClipRef` 带上自己的区间

`resolvedAudioLanes` 需要时间，所以 ref 增加 `start` / `duration`，由 `timelineAudioClipRefs` 从各自的数据源填：

| source                                    | 时间来源                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `PACKAGED` voices / captionVoices / music | `checkpoint.*[id].start` / `.duration`                                                                 |
| `LEGACY` voice / bgm                      | `variant.voice` / `variant.bgm` 的 `start` / `duration`（`EffectTemplateMixAudio` 本来就带这两个字段） |
| `DETACHED`                                | `variant.detachedAudios[i].start` / `.duration`                                                        |

区间缺失（历史数据）时按 `start 0 / duration 0` 处理：不会与任何片段冲突，行为退化成「按默认行」。

## 五、非目标

- 不改「字幕口播与槽位口播可以时间重叠、并且同时出声」的既有口径。
- 不让两条字幕重叠（服务端与渲染端的不变量，见 `2026-09-25-时间轴音乐落轨与字幕拖动修复.md`）。
- 不改视频轨的 `assignIntervalLanes`。
- 不碰 API / worker / 契约：行是纯前端编排，worker 渲染不看行号（契约 `effect-template-mix.ts:144-149` 已写明）。
- 不做数据迁移脚本：`compactAudioLanes` 在加载时就会把修正后的行写回本地状态，下一次保存即落库。

## 六、风险与边界

- **已有编排会被重新排**：某条片段原本与人重叠（例如变体 `64e307ba` 的 `capvoice` 与 `detached`），本轮之后会被下移一行，用户的视觉顺序会变。这是修掉「互相压住」的必要代价；不重叠的片段行号不变。
- **显式拖行不再绝对**：把片段拖到一条已被「同时刻的其它片段」占用的行上，它会被让到下一行。用户要的正是「不许两条压在一起」，所以这是不变量而不是取舍；拖到空行/不冲突的行仍按拖的那一行落。
- **`resolvedAudioLanes` 是 O(n log n)**，时间轴每帧对每个片段算一次全表（n≈10 条），开销可忽略。
- **与并行会话同文件**：`effect-template-mix-audio-lanes.ts` 是并行会话新建、尚未提交的文件；`EffectTemplateMixNodePage.vue` / `EffectTemplateMixTimeline.vue` 也在被其改写。本轮**不改这两个 `.vue` 的调用点**，改动集中在共享模块 + 新增一个独立 spec，冲突面最小。
