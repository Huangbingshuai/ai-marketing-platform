# 效果类全量更新：混剪与成片节点的隔离分支

> **已被后续改造取代**：本文里「完成校验即发布分支」的两处设计（混剪的完成校验按钮、成片的完成校验固化分支）在真机回归后被用户否掉，见 `2026-09-29-混剪成片自动入队与成片分支改造.md`——两个「完成校验」按钮都已移除，混剪包装成功即把成片放进成片节点待渲染区并发布混剪分支，成片分支改在整批导出成功后发布。本文其余内容（六节点隔离编辑、克隆性能优化、`always: true` 的前身语义）仍然有效。

## 目标与边界

需求把效果类工作流的更新分成两类：**全量更新**（上游变化后下游必须全部重新生成，因此新建分支，分支的下游为空）与**局部更新**（只覆盖变动信息，不新建分支）。本次只做全量更新。

改动前只有前四个节点（资料导入 / 信息提炼 / Prompt 生成 / 视频渲染）具备「隔离编辑 → 完成校验即发布分支」的能力：`EFFECT_WORKFLOW_EDITABLE_NODES` 与 `effect-edit-session.ts` 的 `stageOrder` 都只列了这四个节点。混剪节点与成片节点的三个「重新生成」入口（重新智能填充、重新成片包装、重新导出成片）直接写当前 Run，无法满足需求。

本次把隔离编辑扩展到六个节点，并让混剪、成片的三个入口自动进入隔离编辑态、在触发节点重新生成完成时发布分支（智能填充在填充完成时确认并发布，智能成片包装与重新导出成片在完成校验时发布）。分支内容 = 上游克隆 + 触发节点配置（节点草稿）+ 触发节点重新生成的结果，触发节点自己的已确认产物与下游一律为空。

不在本次范围：局部更新（画布「需要更新」标识、全局局部更新按钮、按原区间切割替换、口播字幕判断、新增素材暂存槽位、删除级联、成片选择性重导）；`editBaselineHash` / `createdBranch` 的既有判定语义；`EFFECT_WORKFLOW_BRANCH_NODES`、`listEffectRunBranches` 与版本树构建（已按六节点工作，不动）。

## 数据与接口

- 契约 `packages/contracts/src/workflow-working.ts`：`EFFECT_WORKFLOW_EDITABLE_NODES` 扩到六个节点。`workflow-working.service.ts` 的 `editNodeId` 校验与 `workflow-working.repository.ts` 的三处白名单（begin / publish / cancel）改为引用该常量——原先三处各写死一份四节点数组，扩契约不会生效。
- 契约 `packages/contracts/src/effect-template-mix.ts`：`EffectTemplateMixAiRun` 增加 `workflowRunId`，说明「重新生成会落到未发布子 Run，调用方必须先跟随」。
- 编辑会话 `apps/api/src/platform/workflow/effect-edit-session.ts`：
  - `stageOrder` 六个节点；`artifactPrefix` 改为多前缀（`TEMPLATE_MIX` → `mix-template:` / `timeline-project:` / `timeline-package:`，`FINAL_OUTPUT` → `final-video:` / `final-delivery:`），`stageDigest`、祖先游走的 `workingArtifact.count`、`exitEffectEditInTransaction` 的 `currentArtifacts` 三处消费点统一走 `artifactKeyWhere`。
  - 产物克隆收窄：`stageIndex >= 4` 时 `artifactStages = stageOrder.slice(0, stageIndex)`，不再复制触发节点自己的已确认产物；`stageIndex <= 3` 保持 `slice(0, stageIndex + 1)` 不变，隔离既有四节点的回归面。节点状态克隆仍是 `slice(0, stageIndex + 1)`——混剪的模板与槽位配置存在 `TEMPLATE_MIX` 草稿里，必须带过去。
  - `stageIndex >= 5`：克隆 packaging runs / items / files（混剪在成片分支里是上游，必须看起来完整）；每个模板克隆一条 `EffectFinalOutputRun` 但重置为 `PENDING_RENDER`、item 重置为 `QUEUED` 且 `fileObjectId` / `assetId` 置空，`snapshot` 保留作为上游快照。
- 克隆底座 `apps/api/src/platform/workflow/effect-branch-clone.ts`（新增）：`remapIds`（单趟正则替换）、`clonePackagingRunsInTransaction`、`remapClonedPackagingRunsInTransaction`。手动复制分支（`effect-manual-branch.ts`）改为复用同一份实现，本地不再各留一份 `replaceIds`。
- 混剪后端 `effect-template-mix.service.ts` `createAiRun`：读草稿前先 `beginEffectNodeEdit(projectId, sourceWorkflowRunId, 'TEMPLATE_MIX', 'BATCH')`，后续节点草稿、AI 快照与 `aiRuns.create` 全部用返回的 Run；DTO 带回 `workflowRunId`。`effect-packaging.service.ts` `create` 在幂等重放判定之后同样先 fork，再用子 Run 建 packaging run。
- 成片后端 `effect-final-output.service.ts`：新增私有 `publishEditBranch`（只在「未发布编辑子 Run 且 `editSessionNodeId` 命中」时发布，发布自身开事务，必须等写事务提交后再调）；`complete()` 提交 `TEMPLATE_MIX` 产物后按 `'TEMPLATE_MIX'` 发布，`completeOutput()` 提交 `final-delivery:` 后按 `'FINAL_OUTPUT'` 发布；`start()` 先由 output run 反查 `workflowRunId`，fork 后在子 Run 里按 `templateId` 找到克隆出的 `PENDING_RENDER` 批次作为导出目标。
- Web：混剪页与成片页比较响应里的 `workflowRunId` 与当前 Run，不同则 `emit('workflowRunChange')`，由 `EffectImportNodePage.vue` 的 `refreshActiveRunInPlace` 重挂载到新 Run（`load()` 会从新 Run 里恢复运行中任务的轮询）；成片包装面板新增 `runChange` 事件；混剪/成片两个子页面的 `@workflow-run-change` 接到画布。

### 为什么 fork 放在后端而不是 web

后端编辑接口的 `beginEffectNodeEdit` 默认 `purpose = 'MANUAL'`，而自动 fork 用 `'BATCH'`；`beginEffectEditInTransaction` 要求复用时的 purpose 完全一致（否则返回 `null` 让调用方 409）。若 web 先按 MANUAL 建子 Run，后端 BATCH 调用会拿不到子 Run 而报冲突。因此 fork 全部在后端完成，响应 DTO 回传 `workflowRunId`，前端只负责跟随。

## 性能：克隆必须批量写

DB 实测（紫苏梅子酱同项目最大 Run）：`FINAL_OUTPUT` 在真实数据上 fork 一次要 **122.9 s**，而隔离编辑的事务超时是 `120_000 ms`——功能在用户的大项目上会直接超时失败。原因是逐行 `create` / `update`：该 Run 有 24 条 packaging run、1113 条 item、4796 条 file、806 条 working artifact、200 条 output item，一趟 fork 约 4400 次数据库往返；叠加 `remap` 对每个键做一次 `replaceAll` 的二次复杂度（约 1100 个 id × 28 MB 快照 JSON）。

两处改动：

1. **单趟 id 重映射**：`remapIds` 用一个预编译的 UUID / 64 位十六进制正则对序列化 JSON 做一次替换。分支重映射的键只可能是行 id 或内容哈希，一趟足够。
2. **批量插入**：克隆 packaging run / item / file、working artifact / file / dependency、output run / item 全部改为客户端 `randomUUID()` 预生成 id + `createMany`；artifact 的依赖在 artifact 全部落库后再插，外键不依赖数组顺序。`effect-edit-session.ts` 里 packaging 快照在 artifact 全部克隆完之后才写，因此可以一次带全量映射（`ids + artifactIds + hashReplacements`），省掉原先的第二次逐行 `update`（packaging 快照引用的是 artifact 与内容哈希，不引用其它 packaging 行）。

结果：`FINAL_OUTPUT` fork 从 **122.9 s → 13.6 s**（7 倍），`TEMPLATE_MIX` fork 2.8 s，均远在 120 s 事务预算内。

## 不改动

- `effect-manual-branch.ts` 本地的四节点 `stageOrder` 保持不动。它只用来算「最高的已确认阶段」，手动复制本身会显式复制六节点的全部已确认内容并把 `forkNodeId` 覆写为 `MANUAL_COPY`；扩到六节点反而会让 `beginEffectEditInTransaction` 走到 `slice(0, stageIndex)` 的收窄分支，行为变化没有收益。
- `EFFECT_WORKFLOW_BRANCH_NODES`、`listEffectRunBranches`、版本树构建、`editBaselineHash` / `createdBranch` 判定。
- 局部更新全部内容。

## 验收

- 混剪「重新智能填充」「重新成片包装」：已确认的模板进入隔离子 Run，子 Run 有上游 `render-clip:` 产物、有 `TEMPLATE_MIX` 节点草稿、没有 `mix-template:` / `timeline-project:` / `timeline-package:` / `final-video:` / `final-delivery:` 产物；智能填充在填充完成时就把 `mix-template:` + `timeline-project:` 提交为版本并发布（分支树立刻显示版本号，不再「待校验」），重新成片包装在完成校验时发布，画布与版本树切到新分支。
- 成片「重新导出成片」：已确认成片的 Run fork 后，子 Run 保留 packaging（`COMPLETED`），每个模板一条 `PENDING_RENDER` 的 output run，item 为 `QUEUED` 且 `fileObjectId` / `assetId` 为空；重新导出在子 Run 排队，完成校验后发布分支。
- 首版（无已确认版本可保护）不 fork，仍在原 Run 内进行，`createdBranch: false`。
- API / Web 单测、类型检查、`git diff --check`；DB 级回归在真实项目数据上跑通且 fork 耗时在事务预算内。

### 智能填充完成即确认版本（补做）

> **已被后续改造取代（部分）**：本节解决的是「填充完不写产物 → 分支树一直待校验」的产物模型问题，仍然有效；但「完成校验」这一环已整体移除，智能成片包装成功即入队并发布混剪分支，见 `2026-09-29-混剪成片自动入队与成片分支改造.md`。

真机回归时发现两个连带问题：智能填充完成后分支树上混剪节点仍是「待校验」，且紧接着的智能成片包装不新建分支。

根因是产物模型而非 fork 逻辑：分支树的 `混剪模板` / `智能填充` 两格读的是 `mix-template:` 与 `timeline-project:` 产物（`workflow-working.service.ts` 的 `revisionKeyPrefix` + `effect-workflow-branch-layout.ts` 的 `fillRevision`）。智能填充此前只写 `workflowNodeState` 草稿，不写产物，所以这两格永远只能靠 `draftFillReady` 兜底显示「待校验」；同理 `EffectPackagingService.create` 的 `beginEffectNodeEdit(..., 'TEMPLATE_MIX', ...)` 在祖先链上找不到已确认混剪产物，`confirmed === false` → `created: false` → 包装写进当前 Run，永远不会出现可发布的分支。

改法与渲染节点完全同构（`effect-segment-render.service.ts` 的 `autoCommitCompletedBatch`：worker 回调里提交产物并发布隐藏分支）：

- `completeAiRun` 在 `completeWithDraft` 提交草稿之后调 `confirmFilledMix`：`prepareValidation(..., { partial: true })` → `commitValidatedArtifacts(..., 'TEMPLATE_MIX', inputs)` → `publishEffectNodeEdit(..., 'TEMPLATE_MIX')`。
- `partial: true` 让校验跳过用户还没改完的兄弟成片，只要求至少一条成片有效——智能填充刚写完的那条就是版本本身，不能被兄弟成片否决。
- 有已确认混剪版本的 Run 会先 fork，填充完成后 `publishEffectNodeEdit` 把子 Run 固化为新分支；首版（该分支里混剪节点还没有版本）按既有语义仍留在当前 Run，但产物落库后分支树显示 `版本01` 而不是「待校验」，下一步的智能成片包装也因此能 fork。
