# 提炼依赖快照跨分支素材 id 污染修复

## 现象与根因

**现象**：紫苏梅子酱项目（`40d1273a-e1cd-4cae-8f83-02fdaf324dc1`）的 AI 信息提炼节点，进入编辑态后新增 2 条卖点，点「保存版本」返回 409：

```json
{
  "success": false,
  "data": null,
  "message": "上游资料或提炼参数已经变化，请重新提炼后再校验",
  "code": "CONFLICT",
  "requestId": "b8537039-067f-47c0-bd0f-4fb545b50a2b"
}
```

**根因**：提炼任务的输入快照 `EffectExtractionRun.inputSnapshot.dependencies` 里，`sourceArtifactId` 指向了**另一个 Run 的素材行**，而 `sourceKey` / `sourceRevision` 都是对的。

克隆链路：

- `effect-prompt.repository.ts` 的 `forkValidatedPromptInTransaction`（Prompt 手动复制分支）克隆提炼任务时，`inputSnapshot: json(remap(extraction.inputSnapshot))`，其中 `remap` 只做 `oldProductId` / `draft.id` / `workspace.id` 的字符串替换，**不重映射素材 id**。于是快照里的 `sourceArtifactId` 保持指向父 Run（或更早的祖先 Run）的 source-package 素材行。
- `effect-edit-session.ts` 的隔离编辑克隆同源（只按 id 替换），所以一旦上一代克隆已经脏了，后续所有编辑克隆都会继承这个脏 id。
- 校验侧 `workflow-working.repository.ts` 的 `validateArtifactInputsInTransaction`：当依赖带 `sourceArtifactId` 时**只按 id 查候选**，查到的祖先行 `artifactKey` 与依赖的 `sourceKey` 对不上 → `keyMatches` 失败 → 抛 `WORKING_ARTIFACT_DEPENDENCY_CONFLICT` → 提炼服务翻成 409。

### 数据库实证

对项目 `40d1273a` 的全部 27 条 `effect_extraction_runs` 逐条比对「快照 sourceArtifactId」与「按快照 sourceKey 应命中的素材行」：

| 时间                        | idempotencyKey 前缀            | 快照 id  | 应有 id  | 一致                |
| --------------------------- | ------------------------------ | -------- | -------- | ------------------- |
| 09-10 06:31 ~ 07:48（6 条） | 裸 key（`startRun`）           | 586b4d1f | 586b4d1f | 是                  |
| 09-29 02:51 ~ 03:03（5 条） | `edit:<run>:extraction`        | 各自正确 | 各自正确 | 是                  |
| 09-29 03:14                 | `branch:954d854e-…:extraction` | 586b4d1f | 14cc6a73 | **否（首条脏行）**  |
| 09-29 03:17 ~ 03:22（7 条） | `edit:<run>:extraction`        | 各自正确 | 各自正确 | 是                  |
| 09-29 05:02 ~ 06:18（9 条） | `edit:<run>:extraction`        | 586b4d1f | 各自正确 | **否（继承脏 id）** |

结论：

1. 首个脏行是 `forkValidatedPromptInTransaction` 产出的 `branch:` 行，不是 `startRun`、也不是隔离编辑克隆。
2. 之后所有隔离编辑克隆都从脏行继承 `586b4d1f`，因为该 id 不在被克隆 Run 的素材集合里，`remap` 无从替换。
3. `sourceRevision` 全程正确（都是 2），所以冲突不是「上游真的变了」，纯粹是 id 指错行。
4. `git log -S "branch:\${child.id}:extraction"` 显示该行由 `9e09cba`（效果类前四节点隔离编辑）引入，与 `143d623` 无关。

**用户当前的直接解法（无需改代码）**：在编辑态点「重新 AI 提炼」跑完再「保存版本」——`startRun` 会按当前 Run 重新记录 `sourceArtifactId`，是干净的。不要取消编辑后重进（重进会再次克隆脏快照）。

## 设计

按用户选择「改克隆 + 校验兼底」两条一起做：克隆侧不再产生新脏数据（并能在重新克隆时**修复**已有脏行），校验侧让已经躺在库里的脏行也能保存。

### 1. 克隆侧重映射素材 id（`effect-prompt.repository.ts`）

- 新增 `artifactKeyToId: Map<克隆后的 artifactKey, 克隆行 id>`，在素材克隆循环里随 `artifactIds` 一起填充。
- 新增 `resolveClonedArtifactId(sourceArtifactId, sourceKey)`：先查 `artifactIds`（原 id → 克隆 id）；查不到再按 `sourceKey` 查 `artifactKeyToId`；都没有才回退原 id。**按 key 兜底是关键**——脏行的 id 不在 `artifactIds` 里，只有 key 能救。
- 三处调用点统一走它：素材自身 `dependencies` 输入、`workingArtifactDependency.createMany`、以及提炼快照的 `remapSnapshotDependencies`。
- 新增 `remapSnapshotDependencies`：`remap` 之后逐条改写快照依赖的 `sourceArtifactId`（`sourceHash` 维持原有「仅当有 sourceArtifactId 时按 `artifactHashes` 重映射」的写法，该字段在 WORKING_ARTIFACT 依赖上不参与校验）。

### 2. 校验侧加 `sourceKey` 兜底（`workflow-working.repository.ts`）

`validateArtifactInputsInTransaction` 的 WORKING_ARTIFACT 分支：

- 候选查询由「有 id 就只按 id / 没 id 才按 key」改为 `OR: [ {id}, {artifactKey in [...]} ]`，两种谓词同时下发。
- 把 `keyMatches` 折进 `lineage.find` 的谓词里（原来是在选中 source 之后再判），于是「id 命中但 key 对不上」的行会被跳过，继续按 key 找到真正匹配的那一行。
- `source.revision !== dependency.sourceRevision` 仍然照旧抛冲突。

安全性未放宽：候选查询依旧限定 `projectId` + `workflowRunId in allowedRunIds`，可见性依旧走 `inheritedEffectArtifactVisible`（祖先链上跨越 fork 的素材仍不可见），revision 依旧强校验。

### 3. 不改动

- 不动 `effect-edit-session.ts`：它的 id 重映射对「源 Run 内存在的 id」是正确的，脏 id 由第 1 条按 key 兜底解决。
- 不动 `startRun` / 提炼服务 / `packages/contracts`。
- 不动保存版本的分支语义（内容变化才开叉）。

## 实施与验证

### 落地内容

- `effect-prompt.repository.ts`：`artifactKeyToId` 与 `resolveClonedArtifactId` 定义在素材克隆循环之前；循环内新增 `const clonedKey = artifact.artifactKey.replaceAll(oldProductId, childProduct.id)` 并 `artifactKeyToId.set(clonedKey, cloned.id)`；素材依赖、依赖表、提炼快照三处 `sourceArtifactId` 统一改走 `resolveClonedArtifactId`。
- `workflow-working.repository.ts`：候选查询改为 `OR`，`keyMatches` 提为局部函数并折进 `lineage.map(...).find(...)` 的谓词，末尾只保留 `!source || source.revision !== dependency.sourceRevision`。
- `effect-prompt.branch.database.spec.ts`：在「克隆 prompt 分支工作区」用例里补断言；并把该用例的父 Run 选择由 `activeKey: 'ACTIVE'` 改为「拥有 PROMPT_GENERATION 素材的最新 Run」——本项目的活动分支恰好是**只含提炼产物的分支**，没有 Prompt 素材，原选择条件在该项目上无法定位。
