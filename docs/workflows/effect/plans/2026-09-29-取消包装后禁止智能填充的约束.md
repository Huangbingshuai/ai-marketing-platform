# 取消「智能成片包装之后不能重新智能填充」的约束

## 目标与边界

用户反馈：「现在请你取消智能成片包装之后不能智能填充的约束，因为我们现在智能填充是新增分支，你懂的」。

背景：上一轮改造后，智能填充/重新智能填充已经**必然是新增分支**的动作（`beginEffectNodeEdit(..., 'TEMPLATE_MIX', 'BATCH', { always: true })`），它不再原地改写已发布的包装结果。因此「包装已开始 → 此模板不能再智能填充」这条约束的理由已经消失，反而挡住了「先包装看一眼、再回去重新填充一版」的正常迭代。

本次只取消**智能填充**这一个动作在包装之后被挡住的部分。模板槽位配置锁、在途包装锁、删除模板门禁、`apply-variant`（改配置并同步）全部保留——它们保护的是「已包装结果与模板配置一致」这个不变量，与本次诉求无关。

## 约束现状（三层，均已核查）

| 层 | 位置 | 行为 |
| --- | --- | --- |
| Web 提示（实际拦门的人） | `EffectTemplateMixNodePage.vue:4551-4554` | `packagingLocked && !refreshAffectedSlots` → `showNotice('智能成片包装已启动或完成，此模板不能重新智能填充')` 直接 return |
| Web 按钮 | 同文件 `:5565-5570` | 智能填充按钮 `:disabled` 含 `packagingLocked` |
| API 服务 | `effect-template-mix.service.ts:1032,1043-1048` | `entry.packagingLocked = packagedTemplateIds(...)` 后 `throw 409 CONFLICT` |
| API 仓库 | `effect-template-mix-ai.repository.ts:285-300` | 事务内查到 **CURRENT AVAILABLE** 的 `timeline-package:<templateId>:` 且非 `trimOnly` → `{ kind: 'PACKAGING_LOCKED' }` |
| 文案 | `effect-packaging-progress.ts:182-199` | 终态文案写「模板槽位配置和智能填充已锁定，音色仍可切换」 |

`packagedTemplateIds`（`effect-template-mix-ai.repository.ts:122-147`）= 该 Run 内有 QUEUED/RUNNING 的 `effectPackagingRun`，**或**有 CURRENT AVAILABLE 的 `timeline-package:` 产物的模板。

## 实测：真机为什么是 Web 在拦

紫苏梅子酱项目 `40d1273a-e1cd-4cae-8f83-02fdaf324dc1`，`workflow_runs` 与 `working_artifacts`：

```
f12f4df6 | parent=95c92da8 | forkNodeId=TEMPLATE_MIX | editSessionNodeId=null | published=2026-09-29 11:05:30 | ACTIVE
95c92da8 | parent=46931fe7 | forkNodeId=INFORMATION_EXTRACTION | published=2026-09-29 06:37:21 |
```

```
f12f4df6  timeline-package:7ec78e67:52f7919f  CURRENT AVAILABLE rev=1
f12f4df6  timeline-package:7ec78e67:b3e3a005  CURRENT AVAILABLE rev=1
f12f4df6  timeline-package:7ec78e67:b273bdd0  CURRENT AVAILABLE rev=1
f12f4df6  timeline-package:7ec78e67:d0894242  CURRENT AVAILABLE rev=1
f12f4df6  mix-template:7ec78e67              CURRENT AVAILABLE rev=1
95c92da8  mix-template:7ec78e67              CURRENT AVAILABLE rev=1
```

活动 Run 就是包装分支 `f12f4df6`，它带着 4 条 CURRENT `timeline-package:`。用户在此时点「重新智能填充」：

1. Web 的 `packagingLocked`（来自草稿 `entry.packagingLocked`）为真 → `startAiFill` 第一行就 return，请求根本没发出。**这是当前实际生效的拦截点。**
2. 即使发出请求，`beginEffectNodeEdit` 也会 fork 一个**新子 Run**（`effect-edit-session.ts:87` 要求 `!parent.branchPublishedAt`，而 `f12f4df6` 已发布 → 不满足；`:99` `active.id === parent.id` → 继续往下建子 Run），子 Run 只克隆 0-3 阶段产物（`stageIndex>=4 → slice(0, stageIndex)`），**没有** `timeline-package:`。因此子 Run 里 `packagedTemplateIds` 为空，服务层与仓库层这两道 409 都不会命中。

也就是说：服务层/仓库层的 409 在**正常已发布路径上不可达**，它们只在「包装分支尚未发布」的退化态（例如上一次填充发布失败、自动分支被复用）才会命中。本次一并去掉，让三层口径一致。

## 改法

### 1. Web（`EffectTemplateMixNodePage.vue`）

新增一个只表达「包装在途」的 computed，让「在途」与「已完成」彻底分开：

```ts
const packagingInFlight = computed(
  () =>
    packagingLocked.value &&
    (!packagingRunStatus.value || ['QUEUED', 'RUNNING'].includes(packagingRunStatus.value)),
);
const projectEditLocked = computed(() =>
  Boolean(
    activeEntry.value?.aiFillLocked ||
    activeAiRun.value ||
    fillStartPending.value ||
    packagingInFlight.value,
  ),
);
```

`templateEditLocked` 不变（仍是 `projectEditLocked || packagingLocked`），模板配置照旧锁定。

- 删 `startAiFill` 里的 `packagingLocked` 拦截（`:4551-4554`），换成 `packagingInFlight`：在途时提示「智能成片包装正在进行，请等待完成后再重新智能填充」，避免在包装 worker 正在写同一个 Run 的产物时并发发起填充。
- 智能填充按钮 `:disabled` 用 `packagingInFlight` 取代 `packagingLocked`。
- 配置面板横幅（`:5498-5502`）与精修工作台横幅（`:5601-5603`）改文案：模板槽位配置仍锁定、音色仍可切换、**可重新智能填充（会新建分支）**。

### 2. API 服务（`effect-template-mix.service.ts`）

删 `:1043-1048` 的 409；随之 `entry!.packagingLocked = packagingLockedIds.includes(templateId)`（`:1032`）与 `Promise.all` 里的 `packagingLockedIds`（`:1017-1022`）都成了死代码，一并删除。`createAiRun` 只读 `entry.workspace` 建快照，不写回草稿，所以去掉该赋值不影响草稿 DTO。

`created.kind === 'PACKAGING_LOCKED'` 的映射（`:1480-1485`）保留——它现在只对应仓库的在途包装检查，文案改为「智能成片包装正在进行，请等待完成后再重新智能填充」。

### 3. API 仓库（`effect-template-mix-ai.repository.ts`）

删 `:285-300` 的 `currentPackage && !input.snapshot.trimOnly → PACKAGING_LOCKED`。保留 `:274-284` 的 QUEUED/RUNNING 包装检查（在途包装必须挡住，否则两个 worker 会同时写同一份产物）。

### 4. 文案（`effect-packaging-progress.ts`）

终态（COMPLETED/PARTIAL/FAILED/CANCELLED）与默认态去掉「和智能填充」，改为「模板槽位配置已锁定，音色仍可切换，仍可重新智能填充（会新建分支）」。保留 spec 钉住的两个词：`锁定`、`音色仍可切换`。QUEUED/RUNNING 两条保持「模板配置和成片工程暂时锁定」不变。

## 不改动（明确保留）

- **模板槽位配置锁**：`templateEditLocked`、`saveDraft` 的 `templateChanged || removedExistingVariant` 拦截（`effect-template-mix.service.ts:902-919`）、`mutate`/`mutateWorkspace` 的 `packagingLockedIds` 门禁（`:2409-2415`）、`deleteTemplate` 的 `entry.packagingLocked` 拦截（`EffectTemplateMixNodePage.vue:2805`）。包装结果依赖模板配置，配置仍不能在包装后原地改。
- **在途包装锁**：仓库 `:274-284` + 新增的 `packagingInFlight`。
- **`apply-variant`（更新并同步混剪模板）**：它是配置变更，仍受包装锁约束。
- **`trimOnly` 重算截取区间**：`refreshAffectedSlots` 路径行为不变（本来就被豁免）。
- **`mixForkStage`（`workflow-working.service.ts`）不做 `freshness === 'CURRENT'` 收窄**。曾考虑「包装分支重新填充后其 `timeline-package:` 变 STALE，若按 freshness 收窄则会被误判成 FILL 层，从而把父 Run 的 `MIX_TEMPLATE` 再画一遍」——正是 2026-09-29「混剪分支节点重复修复」要消灭的现象，因此**不加**这个收窄。

## 追加：真机点「重新智能填充」仍报 409（历史归槽结果找不到）

上一节放开 Web 拦截后，真机上点「重新智能填充」立刻收到：

```
找不到完整的历史归槽结果，为避免素材重新归类，请先恢复原始智能填充结果
```

### 根因：克隆分支会重映射素材 id，跨 Run 的历史永远匹配不上

拦截点在 `effect-template-mix.service.ts:1382-1391`：

```ts
const preserveExistingAssignments = Boolean(
  target && unlockedSlots.length > 0 && boundTargetSelections.length === unlockedSlots.length,
);
if (
  !refreshAffectedSlots &&
  preserveExistingAssignments &&
  reusableClassifications.length !== snapshot.materials.length
)
  throw new ApiHttpException('找不到完整的历史归槽结果…', HttpStatus.CONFLICT, 'CONFLICT');
```

`preserveExistingAssignments` 为真（目标成片工程每个槽位都还绑着素材），但 `reusableClassifications` 为 0 条。

**先验的猜测（错，已回退）**：以为只是「`listRecent` 只读当前 Run、祖先的 AI run 读不到」，于是加了 `listRecentWithAncestors` 沿 `parentWorkflowRunId` 上溯。真机仍报同样的 409，说明历史**读得到也匹配不上**。

真机核对（`40d1273a-…`，紫苏梅子酱）：

```
子 Run 6d10e9fc | parent=f12f4df6 | forkNodeId=TEMPLATE_MIX | createdAt 12:05:03（UTC）
```

子 Run 确实建出来了（说明请求打到的是新代码），链是 `6d10e9fc → f12f4df6 → 95c92da8 → …`，模板 `7ec78e67` 的 4 条 COMPLETED AI run 都在 `95c92da8`，所以祖先读是生效的。但：

```
95c92da8 的 AI run 快照首条素材 id = 367d0252-7ca5-4bad-a8da-386af9184938
  该 id 正是 95c92da8 的 render-clip 产物 id
6d10e9fc 的 render-clip 产物 id 是另一套（如 57818694-cd05-4139-aeda-fb159aa3ec75）
同一 fileObjectId（如 04aacf2b-…）在两个 Run 里对应不同 artifact id / artifactKey / contentHash
```

即**克隆分支会重映射素材 id**（`7f0d326 修正：克隆分支时重映射提炼快照的素材 id`；同一段视频 `fileObjectId` 相同，但 artifact id、`render-clip:<taskId>`、contentHash 都换成子 Run 自己的一套）。`cachedClassifications` 按 `material.id` 逐条比对 `workflowStateHash`，因此跨 Run 一条都匹配不上 → `reusableClassifications.length (0) !== snapshot.materials.length (20)` → 409。

结论：只要填充必然 fork，这个守卫就是必中——**跨分支「复用归槽」在现有 id 重映射下不可实现**，沿祖先链读历史救不了它。用户的要求也正是这一点：「我都是直接新增分支了，按道理说从头开始实现智能填充工作流不就行了」。

### 改法：删掉守卫，复用不了就从头填

`effect-template-mix.service.ts` 删掉 `:1382-1391` 的 409，把「复用当前归槽」降级为「复用不了就从头分类+从头分配」：

```ts
// Keeping the current slot assignment needs the classification that produced it. A fill always
// lands on a branch of its own, and cloning re-identifies the materials, so that history is
// normally gone by the time the fill runs. It then classifies and assigns from scratch instead of
// refusing: a fresh fill cannot overwrite the result the user already has — it is a new branch.
// The trim-only refresh is exempt, because it keeps the assignment on purpose and only recomputes
// the trims of the slots whose source material was replaced.
const reuseExistingAssignments =
  preserveExistingAssignments &&
  (refreshAffectedSlots || reusableClassifications.length === snapshot.materials.length);
const initialSelections = reuseExistingAssignments ? boundTargetSelections : [];
```

- 历史完整（同一条未发布分支内的重填）→ 照旧复用 `boundTargetSelections` + `reusableClassifications`，行为不变。
- 历史不完整（新分支）→ `initialSelections` 为空、`initialClassifications` 也为空 → worker 重新归类、重新分配全部未锁槽位；结果写进新分支的成片工程，**不覆盖**用户已有的结果。
- `refreshAffectedSlots`（「更新已替换素材」的仅重算截取区间）豁免不变，`initialSelections` 仍是 `refreshBindings`。
- `manualSlotIds` 锁定的槽位仍不动（`lockedBindings` 照旧排除在 `unlockedSlots` 外）。

### 测试

- `effect-template-mix.service.spec.ts` 新增「fills from scratch when a fresh branch cannot reach the assignment it forked from」三阶段：① 分支首次填充；② `listRecent` 提供匹配的 COMPLETED run → `initialSelections`/`initialClassifications` 各 6 条（复用路径不变）；③ `listRecent` 为空（新分支）→ 不再抛 409，`create` 收到的 `initialSelections`/`initialClassifications` 均为 `undefined`（从头填）。

## 风险与取舍

- **在途并发**：去掉「已包装」拦截后，唯一剩下的时点是「包装 QUEUED/RUNNING」。`packagingInFlight` 与仓库检查双保险；但若用户在包装完成的瞬间（run 状态刚落 COMPLETED、产物尚未提交）点填充，仍可能并发。此时填充在新子 Run 里跑，包装 worker 写的是父 Run，产物互不覆盖，最坏结果是多出一个填充分支。
- **复用退化态**：若上一次填充发布失败，自动分支未被发布，下一次包装会复用同一个 Run，该 Run 同时持有填充与包装产物；此时树的 `mixForkStage` 会判成 `'PACKAGING'`，该 Run 自己的填充版本不单独画节点（由父 Run 的填充节点代表）。这是「分支节点重复修复」取舍的延续，退化态下才出现，本次不引入跨 Run 版本号。
- **不做端到端付费回归**：智能填充会真实调用 AI worker，本次只做只读真机核对 + 单测/类型检查；真机点击「重新智能填充」留给人工回归。
- **新分支的重填不再保留原槽位归属**：删掉守卫后，新分支会重新归类并重新分配全部未锁槽位（用户已确认要「从头开始」）。要保留归属只重算截取区间，走「更新已替换素材」的 `refreshAffectedSlots` 路径；要完全钉住某个槽位，把该槽位加入 `manualSlotIds`。
