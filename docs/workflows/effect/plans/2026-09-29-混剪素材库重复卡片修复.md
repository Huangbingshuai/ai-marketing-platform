# 混剪素材库每个素材出现两次：分支克隆与祖先继承叠加

## 目标与边界

用户真机回归反馈：「进行智能成片包装的时候素材库中的素材直接被复制了一份，比如直接有两个 R01 视频素材」。实测确认：包装 fork 出的分支 Run 上，`GET /template-mix` 返回 **40 条**素材，每条 clip 出现两次（活动 Run 自己的克隆 + 祖先 Run 的原件），且两份都 `available: true`，用户看到的素材库因此每张卡片都是双份。

只改混剪素材库这一个枚举出口；fork 的克隆行为与 `inheritedEffectArtifactVisible` 的可见性规则都不动（理由见「为什么不动那两处」）。

## 根因

两件事各自都对，叠在一起就重复了：

1. **fork 会克隆上游四个阶段的产物**（`effect-edit-session.ts:379-387`）：`TEMPLATE_MIX` 的 fork 取 `stageOrder.slice(0, 4)`，把 `SOURCE_IMPORT`/`INFORMATION_EXTRACTION`/`PROMPT_GENERATION`/`SEGMENT_RENDER` 的产物整段复制进子 Run，并重映射 productId / taskId（`artifactKey` 里的 uuid 因此也变了）。这一步是必要的：智能成片包装的 worker 按 **Run 维度** 校验冻结快照的依赖（`EffectPackagingRepository.sourceArtifacts(projectId, run.workflowRunId, ids)`），草稿绑定必须指向本 Run 的 clip 才解得开 —— 这正是上一轮包装必然失败的原因。
2. **`listArtifacts` 同时会把祖先的产物合并进来**（`workflow-working.repository.ts:657-686`），按 `nodeId:artifactKey` 去重。对 `TEMPLATE_MIX` 的 fork，`inheritedEffectArtifactVisible` 判定 `SEGMENT_RENDER(3) < TEMPLATE_MIX(4)` 为真，祖先的 clip 全部可见。

于是同一条 clip 有两行：本 Run 的克隆（key 是新 taskId）与祖先的原件（key 是旧 taskId）。两者的 `artifactKey` 不同，`seenKeys` 去重失效，`materialsFromArtifacts` 又是**枚举**而非按 key 取值，重复卡片就露出来了。

实测（项目 `40d1273a` / 紫苏梅子酱，活动 Run `f12f4df6`）：

| 检查                                                         | 结果                                                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `GET .../template-mix?workflowRunId=f12f4df6` 的 `materials` | **40** 条（`available` 40），20 个名字各出现 2 次                                     |
| 父 Run `95c92da8` 与子 Run `f12f4df6` 的 R-001               | 两行 `payload.fileObjectId` 均为 `ff496f42-…`，`payload.contentHash` 均为 `4706cf41…` |
| 子 Run 内按名字计数                                          | 无重复（20 条 clip，每个名字 1 条）——重复只来自两 Run 的合并                          |

## 改法

`apps/api/src/workflows/effect/template-mix/effect-template-mix.service.ts`：

- 新增 `oneMaterialPerFile(artifacts, poolKeys, workflowRunId)`：按 `payload.fileObjectId` 归并（缺失时回落到 `artifact.id`，即不去重），**优先保留本 Run 的那一份**。归并放在 `poolKeys` 过滤之后，与 `currentMaterialKeys` 的池子收窄正交。
- `materialsFromArtifacts(artifacts, workflowRunId, keepIds)` 增加 Run id 参数并走上述归并；`toWorkspaceData` 增加 `workflowRunId` 参数，三个调用点（`workspace`、`saveDraft` 的 mutate 路径、`updateSettings` 路径）一并传值。

必须保留**本 Run** 的那一份而不是祖先的：草稿的 `variant.bindings[slotId]` 存的是 materialId，克隆时 `clonedIds` 已把绑定重映射到子 Run 的产物 id；若归并后留下祖先的那份，绑定就会指向一条不在列表里的 id，槽位会显示成未绑定。

### 为什么不动那两处

- **不改 fork 的克隆**：打包 worker 的依赖校验是 Run 维度的，去掉克隆就回到「包装 100% 失败」的老问题。
- **不放宽/收紧 `inheritedEffectArtifactVisible`**：该规则同时服务模板维度 fork（`forkTemplateId` 不同模板可见）与其他节点的读取，且 `workflow-working.repository.spec.ts` 已用两条用例钉住「只继承 fork 点之前的产物」「模板维度的 fork 互相隔离」。素材库的重复是**枚举出口**的问题，在枚举处收口最窄。

## 测试

`effect-template-mix.service.spec.ts` 新增「offers one card per rendered file when a branch inherits its ancestor’s clips」：祖先的 clip（`workflowRunId: 'parent-run'`）排在前面、本 Run 的克隆排在后面，两者共用 `payload.fileObjectId`，断言 `materials` 只剩本 Run 的那条 id。把祖先放前面是刻意的——`listArtifacts` 末尾按 `updatedAt desc` 排序，不能依赖「本 Run 一定在前」。

## 风险与取舍

- **归并按 `payload.fileObjectId`**：只有 `render-clip:` 会进素材池（`materialFrom` 对非 `render-clip:`/非 `FILE` 直接返回 null），而一条 clip 对应一个渲染输出文件，同文件即同素材，语义上没有误伤。同一 Run 内两条 clip 共用一个 fileObjectId 的情况不存在（重渲染会写新文件）。
- **其他枚举出口未动**：渲染节点的工作区返回的是 `promptCount` 与单个 `batch`，不枚举产物；成片节点枚举的是 output run 的 item。所以这次只有混剪素材库受影响。
- 若日后又有新的「枚举上游产物」的界面，同样需要按文件（或按本 Run）收口——根因是克隆与继承的重叠，不是素材库独有的。
