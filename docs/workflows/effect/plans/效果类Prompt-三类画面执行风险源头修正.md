# Prompt 三类画面执行风险源头修正

日期：2026-09-09；状态：本轮检查结束，内容验收未通过；按用户要求停止后续测试。

## 第八轮最终检查与停止记录

本轮通过正式浏览器生成并逐条检查全部 50 条 × 15 秒 Prompt。任务成功保存节点草稿，耗时 27 分 50 秒，共生成 72 条候选，最终 50 条；事实覆盖 26/26。系统显示近重复率 32%（16/50，不是完全重复率），AI 未报硬问题，画面可执行性均分 91.84。人工审查仍发现明确矛盾，因此不能把成功状态和模型评分当作质量验收通过。

相对第六轮，整组逐件操作更多改成“一次局部操作，其余内容已在首帧摆好”，例如 P002、P007、P015、P016、P017；本轮未发现明确要求长拉丝、连接细丝或弹性回缩的正文。但仍存在以下残留：

## 第六轮后的方案调整

第六轮浏览器逐条审查仍不通过：多人公勺接力（P002/P041）、持勺的手未放勺又拿食物（P004）、转盘中心物体却绕盘移位（P043）、两次翻动要求整组六块豆腐两面均匀挂酱（P040）、热气带着酱色升腾（P049）。没有明确拉丝，但不能宣称物性问题消失。结果 50 条、16% 重复度、22 分 38 秒；事实缺失 1 项。已用 6/20 次付费批次。

第七轮已运行新增生成内修订，部分请求约 22～42 秒。原始正文生成分片因 JSON 结构问题拆小后，单条 2,000 Token 上限触发真实截断，整轮停止，没有最终结果，不计为质量通过。修正为生成/修订请求在配置总上限内至少留 4,096 Token，并把实际任务数量、编号集合写入请求 JSON Schema；不增加正文长度要求、不做文本裁切。60 项 Provider/修订测试与 mypy、Ruff 通过，随后继续浏览器测试。第七轮已计入额度（7/20）。

原先仅修改模板、不增加调用的尝试不足以解决问题：现有执行修订由评分输出的 executionFindings 触发，而漏诊候选高分通过，不会进入修订。因此调整为生成内部的一次专注执行修订：生成分片先沉淀草稿，再由同一个生成模型在独立上下文中逐条修订拍摄方法；不依赖质量评分、不淘汰、不加业务节点。不更换模型、不修改评分提示词/算法。每个生成分片增加一次调用，计入现有 Run 调用预算和并发限制，不无限自检。

使用现有 CreativeCandidateDraftBatch 和阶段分片结构；修订可同步主线、六维与整个 shotPlan，不能只改 action 留下矛盾的目标/首帧/终帧。Worker 仅验证 ID、数量、事实引用集合、时长与结构，不判断修订是否语义正确。已完成的生成草稿保存在未完成分片中，修订失败不得静默当成功；同一 Run 恢复只重试修订，任务清单变化则不复用。人工 ITEM_EVALUATE 不改正文。历史成功分片仍原样读取。真实效果仍须浏览器逐条人工审查，不以模型自检结果冒充验收。

公共 HTTP、共享契约、八阶段图、队列与数据库结构不变，无数据迁移。历史结果原样保留；新任务使用新模板哈希，重试仍限同一 Run 检查点。

## 已确认根因

1. 正文一方面要求简化，另一方面又要求“必须以 executionRoute 为动作骨架、逐项落实 creativeUsage”。不合理的上游动作拥有事实级别的优先级，生成器不敢调整。
2. “一个主动作”被理解成一次集体任务：给六件物品依次操作仍写成一个节拍；事实中的多用途又被压进单条。
3. “有驱动”仅补一句手或转台，没有清楚决定相机与物体谁动、观察面如何变化。
4. 由“浓稠、黏附、柔软”等属性擅自扩展出长丝、回弹、均匀流线和精确停住，是物性推导而非已确认事实。

## 实施

以下为第一、二次模板迭代；第六轮后的生成内修订增量以本文前部“方案调整”为准，不再声称仅靠模板、不增加调用即可解决。

- 创意空间和方向只选择能在目标素材内完成的一次局部真实操作；多用途由兄弟方向分担，其他已完成物可作为首帧背景，不依次处理整组。
- 把已确认事实与 AI 执行建议分清：事实边界不变，executionRoute / creativeUsage 中的具体方法不是新事实。优先保持营销意图，允许模型改写风险动作并同步主线、六维和 shotPlan，不靠照抄路线制造冲突。
- 生成前采用三项拍摄决策：一个活动目标及必要支撑；明确唯一主要相对运动；只设计有事实支撑的材料行为。用简短正向方法替换分散重复的告诫，不新增结构字段或调用。
- 现有独立方向 AI 复核同时查看路线中的三个具体问题并用既有修订反馈纠正；Worker 只搬运模型结论、验证 ID/结构，不做语义或关键词筛选。
- 既有局部执行修订模板遵守同一优先级，不以“补驱动说明”保留不合理状态；不新增修复轮数或模型调用。

## 验收

新增模板契约测试，覆盖初始方向、补充、复核、正文、修订的一致口径；确认模型评分模板未改、Schema 未变、模板哈希能反映变化。执行 Worker 相关 pytest、源代码 mypy、现有 Ruff、diff 检查。

付费批次延续既有最多 20 次额度（已使用 2 次），每次由浏览器正式创建 50 条 × 15 秒，仅检查生成与最终正文，逐条诊断三类问题；后台日志、快照只作辅助证据。不把下载或视频渲染纳入本次验收。

成功口径是最终批次人工逐条审查未发现三类具体风险，并与前两轮对照数量、重复度和耗时；不能把 AI 高分、节拍减少或测试用例通过等同于内容通过，更不能宣称没有渲染验证的视频故障率为零。发现残留则继续修正源头并在剩余额度内验证。

并行工作区中存在其他 API/Worker 改动，原计划仅部署已验证运行基线与本次模板。实际第三轮 API 已切换为新增图片输入的快照契约，旧 Worker 在领取阶段报额外字段结构错误（尚未调用 AI），因此已重新构建当前 Worker 对齐契约，未删除字段或放宽校验。该轮同时启用了其他任务新增的图片事实视觉策略，不能将与旧批次的所有差异都归因于本次模板。所有完整正文、运行 ID 与日志保存在 Git 忽略的本地验收目录，仓库仅记脱敏报告。
