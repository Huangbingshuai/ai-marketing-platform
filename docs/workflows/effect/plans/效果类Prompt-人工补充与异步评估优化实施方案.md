# 效果类 Prompt：人工补充与异步评估优化实施方案

状态：已完成

## 一、目标

优化效果类第 3 节点中的“新增 Prompt”能力，让用户只需提供真正掌握的信息：Prompt 正文与片段时长。用户可以选择保存后立即使用现有 Prompt Worker 补齐创意主线、六维创意信息、提炼事实绑定和推荐用途，也可以只保存草稿、稍后手动分析。

本次同时修复两个正确性问题：

- 多页结果中，前端通过“当前页缺少的 ID”猜测新增条目，可能把旧条目送去评估。
- 单条评估发现硬问题时，条目仍可能被标记为“已验证”。

## 二、范围与非目标

### 实施范围

- 新增表单默认仅展示 Prompt 正文和片段时长。
- 新增与修改窗口提供“保存后使用 AI 分析”开关；关闭后不创建 Run、不发送模型请求。
- 六维信息不再要求用户填写，由异步评估器从用户正文中分析生成。
- 新增接口返回准确的受影响条目 ID，前端不得猜测。
- 保存后复用现有 `ITEM_EVALUATE` 异步任务，不新增 Docker 容器。
- AI 单次评估同时补齐六维、创意主线、事实绑定和推荐用途，用户正文保持原样。
- 硬问题落为“需修改”，并展示安全、可操作的问题说明。
- 待评估或需修改条目不能完成校验，也不能进入视频渲染。

### 非目标

- 不把“新增 Prompt”改成 AI 代写。
- 不新增批量导入。
- 不修改批量创意生成主流程，不新增工作流业务节点。
- 不改变 WorkingArtifact 的提交边界。

## 三、数据流与生命周期

```text
用户填写正文和时长
→ API 保存领域草稿并返回 affectedItemId
→ API 以该 ID 创建 ITEM_EVALUATE 任务并返回运行状态
→ 现有 Outbox/RabbitMQ/Prompt Worker 执行
→ AI 读取完整可信事实并分析正文
→ Worker 校验事实来源和结构
→ 无硬问题：VERIFIED
→ 有硬问题：NEEDS_REVISION
```

- 用户输入的正文是权威内容，AI 不得改写。
- 新增、评估和修订只更新 Prompt 领域草稿与 `WorkflowNodeState`。
- 只有用户点击“完成校验”，且数量正确、所有条目均为 `VERIFIED`，才提交 `prompt-batch:{productId}`。
- 上一次有效 WorkingArtifact 在重新完成校验前保持不变，下游不提前标记待更新。

## 四、契约与界面

- 单条状态扩展为 `PENDING | VERIFIED | NEEDS_REVISION`。
- 条目保存安全的问题代码和用户可读说明，不保存模型原始响应。
- 新增/修改响应增加 `affectedItemId` 和后端统一排序后的 `affectedItemIndex`，确保分页、筛选状态下仍能定位正确条目。
- 新增与修改表单不要求用户填写六维，统一交给异步评估器分析。
- AI 分析开关默认开启；关闭时按钮和说明同步切换为“仅保存草稿”，且不会要求设置 revision。
- 保存后立即显示“已保存，正在分析”，失败后保留正文并提供“重新评估”。
- 待评估与需修改内容优先可见，不因用途筛选而静默消失。

## 五、测试与验收

- 多页、带搜索和用途筛选时新增，评估目标必须是刚新增条目。
- 只填写正文和时长即可保存。
- AI 评估后正文逐字保持不变，六维、创意主线、事实绑定和用途被补齐。
- 可引用当前信息卡中排序靠后的可信事实，不限于前 12 条。
- 事实编造、产品无关、破损正文等硬问题进入 `NEEDS_REVISION`，不得显示为已验证。
- `PENDING` 与 `NEEDS_REVISION` 均阻止完成校验和 Seedance 请求编译。
- Worker/API/Web 刷新恢复、失败重试、并发 revision、历史草稿和 WorkingArtifact 生命周期不回归。
- 执行 Contracts、API、Web、Worker 相关测试、类型检查、生产构建、浏览器联调及 `git diff --check`。

## 六、实施结果

已完成以下改造：

- 新增与修改窗口只保留片段时长和 Prompt 正文，正文是不可被 AI 改写的权威输入。
- 用户可关闭“保存后使用 AI 分析”。关闭后 API 只保存 `PENDING` 草稿且不创建异步 Run；页面保留手动“开始分析”入口。
- 保存响应返回 `affectedItemId` 及后端统一排序后的 `affectedItemIndex`；页面清空搜索和用途筛选后跳转到准确页，不再通过当前页 ID 或未排序数组猜测新增项。
- 一次保存请求同时表达“保存并启动评估”的业务意图。保存成功后复用现有 `ITEM_EVALUATE`、Outbox 和 Worker；评估无法启动时仍保留已保存正文，并提示用户稍后重试。
- 单条评估读取信息卡全部可用事实，允许绑定排序靠后的可信事实；AI 同时推导创意主线与六维，但不能重写正文。
- 条目状态扩展为 `PENDING | VERIFIED | NEEDS_REVISION`。硬问题保存安全问题代码并在页面显示可操作说明；待评估和需修改条目均阻止完成校验与 Seedance 请求编译。
- 单条评估节点详情同步展示 `VERIFIED` 或 `NEEDS_REVISION`，不会与 Prompt 卡片状态不一致。
- `reviewIssues` 同步进入批次 Schema、Pydantic 模型和人工覆盖记录，任务恢复及后续批量生成不会丢失需修改原因。

实际验证结果：

- Contracts：3 个测试文件、20 项测试通过，类型检查与构建通过。
- API：Prompt 仓储、质量、服务、节点详情及 Seedance 编译器共 5 个专项测试文件、82 项测试通过；API 全量 31 个测试文件、256 项测试通过，类型检查通过。
- Web：Prompt 页面布局与服务共 2 个专项测试文件、24 项测试通过；Web 全量 29 个测试文件、163 项测试通过，类型检查通过。
- Worker：`ITEM_EVALUATE` 专项 3 项测试通过，覆盖正文保持、完整事实上下文和硬问题状态；mypy 与 Ruff 通过。
- 浏览器联调：新增窗口只显示时长与正文；AI 分析开关默认开启，关闭后说明和主按钮立即切换为“仅保存草稿”；修改窗口正确回填时长和原正文；ESC 可关闭并恢复焦点；390px 窄屏无横向溢出。用户已授权付费测试，但当前正式联调项目已有 100/100 条，继续新增会超出批次契约上限，因此未篡改现有设置或业务数据来强行产生费用；保存与异步启动分别由 API/Web 自动测试验证。

已知边界：保存领域草稿和创建异步 Run 是连续的两个持久化事务；若第二步发生可预期的并发冲突，接口会明确返回“已保存但评估未启动”，不会把已保存正文误报为丢失。用户可在条目卡片上重新发起评估。
