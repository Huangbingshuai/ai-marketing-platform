# 效果类 Prompt 第一阶段稳定性治理实施方案

## 状态

已完成。

## 目标

在不更换模型、不减少 Prompt 内容、不改变当前八阶段业务图的前提下，降低批量生成过程中因结构化输出过长、偶发格式异常和任务重试造成的失败概率。

本阶段只处理调用可靠性，不调整创意方向、质量评分、事实绑定和择优算法，因此生成质量与重复度不应发生业务性变化。

## 范围

1. 将候选生成和质量评估的分片大小改为由实际输出 Token 上限、时长和文本体量共同计算，不再依赖互相独立的固定数字。
2. 保留输出截断后的递归拆分，但每个逻辑分片仍只保存一份结果，避免对子分片建立第二套数据库状态。
3. 同一 Run 重试时恢复已经成功的分片，只重新执行失败或缺失的分片；用户重新批量生成会创建新 Run，仍从头生成。
4. Worker 启动时对 Token 上限、并发、分片大小和调用预算做确定性自检，错误配置在消费付费任务前直接失败。
5. 阶段元数据记录预计 Token、分片数量和恢复数量，只展示安全计数，不记录模型输入或响应正文。

## 非目标

- 不切换 Ark 模型。
- 不突破供应商支持的 Token 范围来掩盖超长输出；候选调用的本地默认上限由 6144 调整为 8192，为现有结构化镜头字段保留合理空间。
- 不增加 Provider 内部重复请求。
- 不改变 Prompt 正文模板、评分标准或语义判断职责。
- 不新增数据库表、公开 HTTP 路径或用户可见工作流节点。
- 不执行真实付费调用。

## 设计

### 1. 统一输出预算估算

候选生成按每条任务的目标时长估算结构化输出；评估按候选正文、六维信息和创意主线的实际文本量估算结构化输出。每个请求只使用配置上限的一部分作为规划安全容量，为模型的推理内容和 JSON 包装预留空间。

### 2. 动态分片

Worker 按顺序装箱：加入下一条后若预计输出超过安全容量，则结束当前分片并开启下一分片。单条任务永远允许独立成片，避免因估算偏差导致无法执行。

### 3. 失败隔离和恢复

若供应商明确返回输出截断、未完成或结构异常，多条分片自动二分并重试；单条仍失败时才交给任务层处理。已成功逻辑分片通过现有分片记录恢复，旧 attempt token 继续由 API 拒绝。

### 4. 启动自检

Worker 在连接 RabbitMQ 前检查：候选/评估输出上限必须能够容纳一条最长时长任务，分片和并发必须为正，单 Run AI 调用预算必须覆盖一个最小合法批次。自检只检查本地配置，不发起模型请求。

## 验收

- 4、5、15、20、25、30 秒任务均得到可解释的动态分片。
- 配置上限变化后，分片规划与实际请求 Token 上限保持一致。
- 多条候选或评估响应截断时自动拆小并汇总，单条截断明确失败。
- 同一 Run 恢复后不会重新调用已成功分片；新 Run 不复用旧分片。
- 错误 Token 配置在 Worker 启动、连接队列和消费任务前失败。
- 执行 Worker 单元测试、类型检查、Ruff 和 `git diff --check`。

## 结果记录

2026-09-05 完成：

- 候选生成和独立评估已共用 `reliability.py` 中的输出预算估算，不再由 Pipeline 与 Provider 各维护一套数字。
- 候选调用本地默认上限由 6144 调整为 8192；这仍在既有配置允许范围内，目的是容纳当前结构化镜头方案，不改变 Prompt 内容要求。
- 默认配置下的候选分片为：5 秒 4 条、15 秒 4 条、20 秒 2 条、25 秒 1 条、30 秒 1 条。配置上限降低时会继续自动缩小。
- 评估分片会根据候选正文与六维文本体量动态装箱；异常长文本不会再机械地与另外三条一起请求。
- 已确认现有候选和评估响应截断递归拆分逻辑继续有效；同一 Run 从持久化分片恢复，新 Run 不跨任务复用。
- 新增 Worker 配置安全下限和单 Run 初始调用预算自检，均在首次模型调用前执行。

真实执行结果：

- Prompt Worker：219 项通过，1 项显式付费集成测试跳过。
- Worker mypy：19 个源码文件通过。
- Worker Ruff：通过。

- Mock 端到端：5、15、20、25、30 秒各执行一轮，每轮均精确生成 10 条且时长一致。
