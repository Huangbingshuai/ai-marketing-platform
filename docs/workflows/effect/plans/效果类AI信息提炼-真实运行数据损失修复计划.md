# 效果类 AI 信息提炼：真实运行数据损失修复计划

## 状态

已完成。

## 背景与证据

2026-09-01 的真实“广式腊肠”提炼任务已验证结构化文档解析、确定性标准化和图片识别能够正常工作，但仍发现三处数据损失：

1. Docling 的“字段标题 + 项目列表”输出中，最后一个列表字段会把随后出现的“填写确认”说明误收为业务事实。
2. Worker 已允许保存最多 20 条次要卖点，但 Contracts 与 API 的历史生成上限仍为 6，导致已融合的图片建议在持久化前被静默截断。
3. 语义整理模型可能把同字段内主题不同的事实错误标为 `SAME_MEANING`，当前 Worker 会直接执行该合并。

## 修复范围

- 文档确定性解析器识别说明、确认和备注段落；项目列表开始后遇到普通说明段落立即结束当前字段，不把说明文字写入信息卡。
- 将次要卖点的生成与跨层适配容量统一为 20；核心卖点继续保持 1～3 项，用户可编辑列表的公共边界仍为 20。
- 语义整理只执行经过确定性保护的合并：
  - `PARENT_CHILD` 必须能由规范化文本的真实包含关系验证；
  - `SAME_MEANING` 必须具备较强的文本骨架重合；
  - `SAME_FAMILY` 继续只记录关系，不删除事实；
  - 无法确定时保留全部原始事实。
- 收紧语义 Prompt 的定义和反例，但不改变节点、接口、数据库或任务生命周期。

## 非目标

- 不改变来源优先级和图片识别字段范围。
- 不修改全局视频配置、人工覆盖、确认提交或 WorkingArtifact revision 语义。
- 不扩大核心卖点、场景、受众和信任背书的既有数量边界。
- 不修改 Prompt 生成及其他效果类节点。

## 验收

- “填写确认：……”等尾注不再进入情绪场景或其他列表字段。
- 8 条及以上、最多 20 条有效次要卖点能够完整通过 Worker、Contracts 和 API。
- “节庆采购需求”与“外观品质判断”等主题不同事实即使被模型误报，也不会被 Worker 合并。
- 真正近似重复的事实仍可合并；父子关系只有在文本包含可验证时生效。
- Worker、Contracts、API 相关测试、类型检查和 `git diff --check` 通过。

## 真实结果

- 文档解析新增项目列表终止规则与确认/说明/备注过滤，真实资料包中的“填写确认”不会再进入情绪场景。
- `EFFECT_EXTRACTION_MAX_SECONDARY_SELLING_POINTS` 已由 6 统一为 20，Worker、JSON Schema、Contracts 与 API 适配容量一致；8 条次要卖点回归用例完整保留。
- 语义 Prompt 升级至 `2.2.0`，并增加 Worker 确定性保护。真实故障样例“节庆采购需求”与“外观品质判断”即使被模型误报为同义也会保留两条。
- 修正了父子事实代表项排在原列表后方时无法正确归并的既有边缘问题。
- Worker 全量测试通过，4 项显式外部集成测试按门控跳过；变更文件 Ruff 与 17 个 Worker 源文件 mypy 通过。
- Contracts 17 项测试、类型检查与构建通过；API 信息提炼 63 项测试、类型检查与生产构建通过；本次文件 `git diff --check` 通过。
- 本地 `effect-extraction-worker` 镜像已重建，容器已重新消费 `effect.extraction.requested` 队列。
- Worker 全目录 Ruff 仍报告既有 `consumer.py` 未使用 `Any` 导入；该文件不属于本次修改，未扩大范围处理。
