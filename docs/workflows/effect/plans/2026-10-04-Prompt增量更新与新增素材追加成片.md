# Prompt 增量更新与新增素材追加成片

## 状态与目标

2026-10-04，已按用户确认规则完成代码实现及定向验证，尚未进行真实付费模型与最终视频质量验收。允许旧素材补齐，每个新增素材尽可能追加有实际观看差异的方案，不机械枚举；模板只要在当前可见来源链曾成功智能成片包装，就包装新增工程。实施及验证记录见第十节，第九节保留提示词元数据修改的边界说明。

沿用效果类固定六节点，不增加工作流节点。将上游变动分为两条路径：

- **修改已有提示词**：用户确认修改后，渲染节点提示对应素材待更新；用户局部更新，在当前分支替换这些素材。混剪随后按实际引用提示工程待更新，成片输出继续沿用既有局部更新链路。
- **新增提示词**：用户确认新增后，渲染节点提示有新增待渲染项；用户局部更新只补渲染新增项。新素材进入混剪的待归槽分类；已有成片的模板可以局部更新，归槽并追加使用新素材的成片工程，不重排、不覆盖已有工程。已包装与未包装的情况分别处理。

所有“完成修改”均指明确保存并提交已确认工作副本，不指输入中、自动保存草稿或未完成评估的提示词。检测变化只更新提示，不自动启动付费任务。

## 一、范围与不做什么

范围覆盖 Prompt 确认后的逐项差异、渲染节点同分支增量任务、混剪模板新增素材归槽和追加工程、按需仅包装新增工程、成片输出列表同步，以及对应状态、契约和测试。

不改变六槽位模板结构，不强制改写已有人工编辑，不自动渲染最终视频，不恢复已删除项目，不调整存储部署，不新增平行素材库或版本系统。删除提示词、商品资料整体更换、整批重新生成属于其他变更类型，不按“新增提示词”猜测处理。

“新增成片”在混剪节点表示新建时间轴工程；口播、字幕、BGM 属于包装职责；最终视频编码仍由成片输出节点在用户操作后执行。

## 二、实施前的实现与缺口（保留设计依据）

1. Prompt 已有单条新增、修改、评估及结果校验接口，必须复用现有草稿到工作副本的确认边界。
2. 渲染服务的 `promptTaskNeedsUpdate` 已按稳定 Prompt ID 比较正文哈希、目标时长和共用约束哈希。`regenerate` 可以重生成原批次中已有任务，但不能为没有任务的新 Prompt 追加渲染项。
3. 渲染服务 `present` 虽然计算了 `hasUnrenderedPrompts`，但当前 `stale` 未包含该条件：仅新增 Prompt 时可能仍显示无需更新；与已有修改同时发生时又可能被归为 `FULL`，无法准确提供增量操作。
4. 混剪已有轻量 `sources`、素材来源校验、待归槽分类、AI 归槽评分、去重组合、模型选区及工程提交能力。现有 `pendingProjectCount` 主要反映已有工程引用素材的变化，不能表达“素材池新增，但旧工程本身未变化”。
5. 智能填充快照已有 `existingVariantBindings`、`maxOutputVariants`、`reuseCounts` 和分类复用；当前每模板最多 100 条工程。需要增加“必须使用本次新增素材”的约束和 AI 差异化方案选择，不能直接把现有机械组合枚举当成增量追加，也不能直接复用普通完整填充入口。
6. 现有分类缓存校验包含整批 Prompt 依赖签名，新增一条 Prompt 可能使未变化素材的分类也失效。增量流程需按真实素材、关联 Prompt 和模板条件校验缓存，不因批次 revision 变化重做所有分类。
7. 已有渲染素材替换计划指定成片输出为已有成片局部更新的唯一入口。此次新增的混剪入口只承担“归槽并追加工程”，不另建第二套已有成片替换流程。

## 三、用户操作与联动规则

| 变更                           | 渲染节点局部更新                                     | 混剪节点                                                 | 成片输出节点                                           |
| ------------------------------ | ---------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 修改已渲染 Prompt              | 原分支只重生成变化项；成功后替换对应片段             | 素材库同步新片段；只给真实引用它的模板和工程提示待更新   | 对受影响成片提示待更新；用户局部更新后覆盖对应结果     |
| 新增 Prompt                    | 原批次只追加新增项任务，已有素材保留                 | 新素材先待归槽；用户局部更新后归槽并追加工程，旧工程不动 | 追加新工程的待渲染条目；旧成片不因素材池扩大变为待更新 |
| 同时修改和新增                 | 一次操作包含变化项重生成与新增项补渲染，分别展示进度 | 同时展示“已有工程需更新”和“新增素材待处理”，分开处理     | 已有结果覆盖更新与新增结果渲染分别关联自己的工程       |
| 完整重新智能填充或完整重新包装 | 不借局部更新改变其既有语义                           | 沿用独立新分支和最新可见素材快照                         | 父分支结果保持不变                                     |

联动按确认结果逐级发生：Prompt 草稿编辑不让下游抢先消费；渲染正在执行或失败时，不把尚未成功的新画面用于混剪；新工程或包装确认成功后，成片节点再识别新增或更新。每个节点由用户主动发起相应任务，不进行自动付费串联。

节点及模板卡片显示汇总待处理状态，具体条目区分“待更新”和“新增待处理”。已有成片不增加泛化的“口播过期”限制，用户仍可自由编辑。

## 四、权威来源、身份和版本

- Prompt 来源是当前项目、效果类 Run 与可见分支中的已提交 Prompt 批次；使用稳定 item ID，不按编号、文案相似度或名称判断新增/修改。
- 渲染以当前批次任务的已消费快照对比最新确认 Prompt。差异包括新增 Prompt ID、已存在 ID 的有效渲染输入变化，以及无法安全映射的异常项。
- 已有素材的渲染输入指纹包含实际供应商正文、编译后的共用约束、时长及相关输入来源；完整任务快照继续冻结模型、参考文件和渲染配置。仅修改渲染设置不自动重生成旧素材，沿用现有设置边界。
- 正文未变且只有编号等展示信息变化，不应额外支付重渲染。仅六维描述或用途发生变化时，应刷新其下游语义依赖；是否也要求重渲染见第九节，不能暗中把整批 revision 当成全部素材都变化。
- 输出复用 `render-clip:<taskId>` 与 `render-batch:<productId>`。未变化片段内容和 revision 不增加；变化片段验证成功才提交新 revision；聚合批次反映真实成员集合变化。
- 混剪继续读取同范围内最新可用 `render-clip`，绑定 `artifactId + revision + contentHash`。修改素材与新增素材按稳定来源区分，不能把已有 Prompt 的新文件误认为新增创意。
- 模板输出继续使用 `mix-template:<templateId>`、`timeline-project:<templateId>:<variantId>`；包装复用 `timeline-package:<templateId>:<variantId>`；输出和交付复用现有成片 item 及 `final-delivery:<templateId>`。
- 批次新增不等于原成员都失效。节点汇总可以提示待处理，但已有工程/成片的待更新必须由实际依赖差异判定；不可简单传播整批 `STALE` 到所有已有条目，也不可为清除提示篡改未处理项的消费版本。

## 五、实施设计

### 5.1 Prompt 确认与渲染待处理清单

复用 Prompt 保存/校验提交流程，基于最新已确认内容和渲染快照派生逐项差异。自动保存和取消编辑不发布新 revision。确认内容与上次一致时不增加 revision，也不出现新的待更新任务。

渲染工作区响应补充新增待渲染 Prompt 的 ID 和数量；已有任务继续使用自身 `needsUpdate`。`refreshScope` 不再把新增项一律解释为全量重建，且只新增时也能正确显示待处理。

用户点击“局部更新”时，服务端重新计算目标集，不能信任前端数量；冻结 Prompt 工作副本、当前批次及相关输入版本，检查该分支可编辑且目标输入已确认。整批重渲染仍使用原有独立分支入口。

### 5.2 当前渲染批次增量执行

扩展现有批次任务编排：对变化项复用对应任务身份和原有局部重生成能力；对新增 Prompt 在当前批次创建新任务和片段身份。复用 Seedance 请求编译、Outbox、Worker、轮询、文件校验和工作副本提交，不另起一种供应商任务系统。

新增项采用当前渲染设置；已有项重生成保持现有局部更新的渲染设置规则。幂等身份至少涵盖项目、Run、批次、稳定 Prompt ID 和冻结输入指纹，重复点击不能为同一新增项生成两份正式任务。

新素材验证、上传成功之前保留旧可用素材。局部失败不能清空旧素材或令全批不可播放；失败项保持可重试，成功检查点复用。发布时沿用现有明确确认边界，不把部分失败的批次伪装为全部完成。需要支持部分采用时必须显式确认其范围，不能把草稿素材放入权威池。

回写重新校验当前确认输入、批次版本、attempt token 和租约；任务期间输入二次改变时拒绝失效结果成为当前素材。不得因新的聚合来源 revision 把未更新素材的旧输入快照改写为已消费新内容。

### 5.3 混剪实时素材库与新增范围

复用 `sources` 轻量刷新及既有切换隔离，素材库读取当前分支最新确认成员，保持未保存编辑。旧工程仍绑定的素材继续可播放，不因新素材入库消失。

每个模板分别识别相对自身上次成功处理快照的新素材。不能用“未被任何工程选用”作为新增标准：旧素材可能一直未被选用，但并非本次新增。

新素材默认进入 `UNASSIGNED` 待归槽分类，这是素材库分类，不创建一个新的时间轴轨道或第七个模板槽位。用户已人工归槽的素材保留人工选择；不能直接把上游推荐用途当成混剪 AI 分类答案。

模板已存在成片工程时显示新增待处理数量和局部更新入口；无工程模板仍使用原有首次智能填充，不由轮询自动创建工程。一个模板处理完成不消除其他模板尚未处理的新增素材提示。

来源唯一性无法确认时，不把全部历史池判成新增；保留旧结果，说明无法自动确定新增范围，允许用户明确选择新增范围后再执行。

### 5.4 混剪局部更新：归槽并追加工程

在既有智能填充 Run、快照、评分、组合及模型选区流程增加增量追加操作标识，不新建平行填充管线。该操作在当前模板分支追加新 variant，不调用完整重做的自动分支逻辑。

输入冻结模板配置、已有工程集合及内容指纹、本次新增素材、其关联 Prompt 和版本、人工归槽编辑版本、当前剩余工程容量和包装策略。复用未变化素材的有效分类；对新增素材执行既有 AI 归槽。新素材选区由模型确定，不能固定旧 offset 或强行从零开始。

新增组合须满足六槽位结构、合法时长、单条工程素材不重复，且至少包含一个本次新增素材；允许复用旧素材补齐其他槽位。不得新增只由旧素材组成的工程或与已有工程完全相同的素材绑定组合。

用户已确认数量口径：**每个新增素材尽可能生成多条，但不要机械枚举造成高重复**。采用以下方式：

1. 优先让所有具备合法完整方案的新增素材至少参与一条；容量不足时明确展示未覆盖项，不能先把单个素材的组合填满上限。
2. 在剩余容量内，由 AI 阅读真实 Prompt、归槽评分及已有方案，围绕新增素材提出不同画面搭配和表达重点的完整六槽位方案。模板槽位顺序和时长不变，差异来自素材选择、实际可用观看事件及合理选区，不凭空杜撰素材内容。
3. 由 AI 判断候选与已有/本次候选是否高度同质，并选择有实际观看差异的方案；Worker 只校验来源、数量、六槽位、时长和完全相同绑定等结构约束，不用关键词或字符相似度代替创意判断。不能仅凭素材 ID 不同认定观看内容有差异。
4. 不生成所有排列组合后再凑数；复用已有评分和选区能力，以有界候选与补充轮次处理，最多占用现有 100 条总工程上限的剩余容量，不无限调用模型。具体机械执行上限在实施时纳入任务配置和测试，不作为必须达到的业务数量。
5. 同一新增素材可用于多条不同方案，但不能仅改几帧起点或换一个无实质差异的搭配充数。有可靠不同观看事件时，按方案保存模型选择的截取区间；需要时扩展现有选区结果的方案/槽位身份，避免当前按素材唯一缓存的起点抹平差异。
6. 达不到更多有差异的合法方案时少生成并说明原因；展示各新增素材参与条数和实际新增总数，不宣称每个素材都达到固定配额。AI 规划或差异评估失败时保留可恢复草稿，不静默退回机械枚举。

追加时生成新的工程 ID，保留原工程 ID、顺序、时间轴、截取、轨道、转场、音量、字幕和包装内容。不能为了均衡使用率重新分配已有工程。提交时比较原工程集合与冻结基线，服务端校验旧工程内容未被修改。

归槽成功但素材过短、槽位不足、无合法新组合或达到数量上限时，保留合法归槽结果并给出实际未生成原因，不补造素材、不伪装已生成工程。区分“已归槽”和“已追加工程”，以既有任务结果/检查点记录处理进度；尚未使用的新增素材不能因任务部分成功被静默视为全部完成。重复请求复用该任务结果，不反复追加同一批工程。

### 5.5 是否包装按成功历史判断

- 用户已确认：**只要该模板执行成功过智能成片包装，本次新增工程就包装**。该模板从未成功包装，则新增工程保持纯画面。
- 依据同模板、当前分支可见来源链中的成功包装任务/已确认包装工作副本，冻结本次任务的包装策略；不能仅看当前选中工程、是否存在音频或某张卡片状态。其他模板、项目或不可见历史分支的包装成功不计入。
- 同模板既有已包装和未包装工程混合时，新增工程仍生成口播、字幕及 BGM；旧的未包装工程也不被顺带包装，旧的已包装工程不重做。即使用户后来删除旧工程的口播或字幕，也不抹去已经成功包装过的事实。
- 从未包装成功、只有失败/取消任务的模板，新增工程保持纯画面；新增纯画面待渲染项。无需让用户每次重复选择包装开关。

为本次新增工程调用既有完整包装能力，不重新生成旧工程的音乐、配音或字幕。

扩展包装目标范围为本次新增 variant ID 集合，复用已有画面理解、口播策划、配音、BGM、字幕对齐及存储回写。在当前分支对新工程首次包装，不借用“旧工程完整重新包装”入口而意外创建分支或改写旧包装。

归槽、追加与包装由一次用户授权的增量操作编排，并在调用前说明按差异化方案追加、剩余容量及是否包装；规划完成后显示实际目标数量。包装失败时保留已确认新工程与可恢复检查点，旧工程和旧成片不受影响；重试只处理失败的新工程/步骤。新包装成功后升级其原待渲染条目，不能又追加第二份成片。

### 5.6 成片输出衔接与已有素材替换

新增工程在成片节点追加待渲染项；保留既有已完成视频、输出配置、资产和交付引用，不触发全页面重载。即使分支已有确认输出，也应支持按明确的新工程 ID 追加待渲染条目，不能整批覆盖既有交付。

已有素材变更仍复用 [渲染素材变更联动混剪局部更新计划](./2026-10-04-渲染素材变更联动混剪局部更新.md)：只标记真实引用工程，用户从成片输出局部更新，模型重新选择变更画面的区间，按需重做受影响槽位的口播和自动字幕，保持其他槽位与音乐；新视频成功后同步覆盖当前混剪工程、包装和成片。

新增工程与已有工程替换可以并存，但任务目标必须分离。任何一种失败都不能丢失另一类已成功结果。最终编码只由成片节点主动执行；混剪追加/包装成功不偷偷触发最终渲染。

## 六、契约、接口与兼容

优先扩展现有工作区响应、渲染批次任务编排、混剪 AI 快照和包装任务目标范围；字段只能定义在共享 Contracts，API/Web/Worker 共用，不复制 DTO 或建立第二套素材状态。

设计阶段的数据表达如下；实际落地字段与接口见第十节：

- 渲染差异：已有变化 task IDs、新增 Prompt IDs、不可安全处理原因、冻结确认版本。
- 混剪来源汇总：已有受影响工程数量、各模板新增待处理素材范围；两者不可复用同一个含义模糊的数量。
- 增量快照：操作类型、新素材依赖集合、已有工程基线、剩余容量、差异化方案及其 AI 评估记录、包装目标策略、操作幂等键。
- 增量结果：新 variant IDs、归槽结果、未采用原因、待包装/包装成功/失败范围，以及重试检查点。

新增范围优先从现有成功任务的素材池快照、模板草稿和任务结果确定性计算；不足时添加最小可选基线/操作字段。不要只靠前端内存或浏览器本地存储判断“哪些素材已经处理”。初步不要求新数据库表；若现有任务模型无法持久表达增量关系，先明确缺口再进行最小迁移。

历史结果缺失增量字段时保持读取兼容，不自动增加 revision、归槽、创建工程或发起付费任务。历史 Run 快照继承后的身份映射必须沿用已有可靠映射，不能按文件名推断。旧分支依旧独立；本次更新仅作用于当前可见来源链，不广播改写全部历史分支。

## 七、并发、失败与重试

复用项目/Run 隔离、Outbox、幂等键、attempt token、租约及 revision 检查。事务内只写业务状态和消息，模型、文件操作和最终编码在事务外执行。

用户可以编辑；任务不能覆盖执行期间用户新保存的工程、模板配置或人工归槽。提交时验证目标级基线，避免全局锁定整个模板。若输入变化无法安全合并，保留用户编辑和旧成片，提示重新确认任务范围，不自动改用最新输入继续支付。

重复请求返回同一任务/结果；失败重试复用相同冻结输入下成功的文件、选区、归槽和包装检查点。旧 attempt 的迟到回调不得发布，刷新与重试不得产生重复新增工程。输入变更后的重试需明确重新冻结并以新输入指纹区分。

原素材替换文件在新结果成功前保留；旧输出不因 pending 状态被清空。新增素材归槽、工程追加、包装完成和输出渲染分别记录真实状态，不把前一阶段成功当成后一阶段已经完成。

## 八、实施顺序与验收

### 实施顺序

1. 核对第九节确认记录与修改边界；补充逐项差异及增量快照契约。
2. Prompt 确认到渲染待处理识别，修复“仅新增未提示”，实现原批次增量任务及失败保留。
3. 混剪来源新增范围、每模板待处理提示，区分已有工程受影响与新增素材。
4. 既有填充流程增加归槽与受约束的追加工程模式，复用模型选区及缓存。
5. 包装按新增目标集合执行，成片输出仅追加/升级对应待渲染项。
6. 回归已有素材覆盖局部更新、完整重做独立分支与编辑自由度，完成跨层验收。

### 测试清单

- Prompt：单条修改、纯新增、多条修改加新增、确认无变化、草稿取消、评估未完成、共用约束变化、仅展示/语义元数据变化。
- 渲染：仅对应项提交任务；当前分支和批次不变；新任务 ID 唯一；原素材保留；新增设置与已有任务设置口径；并发、失败、重复点击、二次输入变化和迟到回调。
- 依赖：未使用变化素材的旧工程不待更新；仅素材池新增不使所有旧成片待更新；逐级确认后联动；跨项目、Run、产品、模板及历史分支不串数据。
- 混剪：新素材待归槽；各模板新增范围独立；人工归槽保留；只处理真正新增；分类缓存按真实输入复用；每个新增工程至少使用一个新增素材，六槽位去重且不重复旧组合。
- 差异化追加：允许旧素材补齐；优先覆盖新增素材；同一新增素材可产生多条明显不同方案；模型淘汰高度同质搭配；只有起点微调或换相近画面的伪差异不充数；不调用机械全排列作为兜底；按方案选区、容量和有界重试准确执行。结构测试不能冒充实际观看差异验收，另需人工审看输出方案及画面。
- 不改旧成片：操作前后逐项比较旧工程、包装和最终输出的内容指纹、ID、文件引用与人工编辑，确保追加没有改写任何旧项；素材替换则只允许明确目标变化。
- 包装：从未成功、曾成功、混合状态、旧工程后来删除音轨、仅失败/取消历史及其他模板成功历史；只有该模板可见成功历史启用包装；只为新增工程生成口播、字幕和 BGM；包装失败可恢复；成功只升级原条目，不复制旧成片或额外建分支。
- 边界：新增素材过短、无法归槽、素材不足、没有合法组合、达到 100 条上限、映射不明确、历史基线缺失，以及归槽成功但后续失败。
- 交互：节点/模板/工程准确数量，局部更新授权范围和进度，切换模板/Run 的迟到响应隔离，无刷新列表更新，主要宽度及加载/空/错误/完成状态。
- 完整重做：重新智能填充、完整重新包装仍使用最新素材创建独立分支；原父分支不变。
- 执行 Contracts、API、Web、相关渲染/混剪 Worker 定向测试和跨层类型检查、构建、数据库回滚集成测试、浏览器回归、`git diff --check`。已有测试失败与新增回归必须分别记录；没有执行的测试不写为通过。

上述清单为完整验收目标，并非全部已实测通过。已执行测试、既有失败及尚未进行的真实模型验收分别记录于第十节。不自动提交 Git。

## 九、用户确认记录与剩余问题

1. **已确认：旧素材补齐**。允许旧素材补齐剩余槽位；每条新增工程至少使用一个新增素材，单条内不重复。
2. **已确认：新增条数**。每个新增素材尽可能生成多条，但不要机械化枚举造成高重复；按第五节 AI 差异化方案规则执行，没有固定每素材配额。
3. **已确认：包装条件**。同一模板只要执行成功过智能成片包装，新增工程就包装；从未成功则保持纯画面。混合状态不需要再询问用户，不附带改变旧工程。
4. **修改边界说明**：本计划按有效渲染请求变化判断是否付费重渲染；仅展示编号变化不重渲染。六维/用途变化但正文与请求未变时，建议只刷新下游语义依赖；若希望所有业务字段修改都重渲染，需要明确这一额外规则。

未确认项中的推荐不作为额外授权。实现继续按有效渲染请求判断需要重渲染的范围，没有因展示元数据变化自动发起任务。

## 十、实施与验证记录

### 实际实现

- 渲染工作区返回 `pendingPromptIds`，新增与已有变化都进入 `SELECTIVE`。`POST .../segment-render/batches/:batchId/refresh` 冻结批次及 Prompt revision，复用现有幂等收据与隔离草稿合并，在当前批次追加任务及 Outbox；旧成功文件在替换成功前保留。
- 混剪工作区与轻量来源响应返回按模板隔离的 `pendingAddedMaterialIds`。依据稳定 Prompt 来源及该模板的已完成任务快照区分“素材替换”和“真正新增”，未采用的新增素材继续待处理。历史基线缺失时不猜测新增身份，不自动追加。
- 现有创建填充任务接口增加 `appendNewMaterials`，任务记录 `operation=APPEND`，快照冻结新增素材集合、旧工程 IDs 与包装策略。复用现有分类、抽帧及选区；分类缓存按单素材和真实 Prompt 内容核对，不因批次 revision 改变整批重做。
- Worker 以有界分页请求模型提出搭配，并交由独立模型评审观看差异。API 只校验六槽位、合法来源、时长、同片去重、至少一个新增素材、与旧组合不同及 100 条容量边界；无合法方案时失败并保留旧结果，不使用机械枚举兜底。
- 追加工程使用任务绑定的确定性 IDs；仅提交新增时间轴，不改旧工程、不发布新分支。APPEND 不全局锁定旧工程；执行期间输入发生变化时拒绝迟到覆盖，保留用户编辑。
- 当前可见祖先链中同模板成功包装历史决定 `packageNewVariants`；仅失败、取消或其他模板成功不算。包装快照记录 `incrementalFillRunId`，只生成新工程的口播、字幕和 BGM。
- 完成协调器幂等同步新增输出与包装，衔接失败记录 `APPEND_CONTINUATION_FAILED`，提供 `POST .../template-mix/ai-fill-runs/:runId/resume-append` 恢复入口。
- 输出快照记录 `appendOnly` 与 `appendPackagingRequired`。追加和包装同步保留旧输出的 ID、文件、资产和人工编辑；用户主动导出时只排队新增条目，不创建分支。包装必需而尚未完成时不能误导出纯画面。
- 沿用现有任务、工作副本、收据和 JSON 快照，无数据库 schema 迁移。完整重新填充/包装仍走既有独立分支入口；已有素材替换仍由成片节点局部更新。
