# 混剪模板删除范围误判修复

## 现象与证据

点击删除测试2时返回“此混剪模板已删除”，但测试2及其工程仍存在，未产生测试2删除回执。
只读计算发现：旧模板删除后，为兄弟模板保留的共享来源及历史 Run 容器，被旧分支归属推断再次纳入测试2删除范围；更新这些已有删除标记的 Run 时触发数据库保护，事务回滚。

## 范围与边界

- 效果类模板混剪节点，修正删除请求的分支范围计算；不修改渲染上游、素材 revision、填充、包装及成片生成逻辑。
- 以已有项目级删除回执为权威，排除其已删除 Run，再识别当前模板的有效分支与子分支。
- 保留数据库防复活保护、事务、幂等及异步清理；共享历史来源容器保持不可编辑。
- 不新增表或契约，不物理清理历史共享文件，不对真实测试2执行删除验证，不增加普通模板切换的加载。

## 验证

- 隔离 PostgreSQL schema 复现：先删模板A，保留模板B引用的旧分支来源；随后删除B，应正常接受，不重复写入A的已删除 Run。
- 保留原有重复删除、兄弟隔离、共享文件、迟到写入防复活和 Redis 清理测试。
- API 类型检查、构建及 diff 检查；确认运行中的开发服务已编译修正。
- 真实项目仅只读核对删除计算及模板仍存在，不调用付费任务。

## 实施与实际验证

- 删除归属推断及子分支遍历排除已有删除回执中的 Run；完整历史祖先仅用于定位导航回退，不再写入已删除容器。
- 新增隔离数据库回归，修正前复现 `workflowRun.updateMany` 的删除保护错误；修正后通过，且已删除容器仍拒绝写入。
- 运行删除数据库/Redis、删除服务与安全错误映射三个测试文件，共 13 项通过；API `typecheck`、`build` 及 `git diff --check` 通过。
- 运行中的 `dist-dev` 开发进程已自动重新编译并启动；只读 workspace 请求成功。浏览器检查删除确认及取消后测试2仍存在，未确认真实删除。
- 未执行真实项目删除、付费生成、Git 提交或外部部署。
