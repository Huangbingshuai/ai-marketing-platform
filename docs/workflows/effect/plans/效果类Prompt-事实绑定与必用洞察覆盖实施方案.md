# 效果类 Prompt：事实绑定与必用洞察覆盖实施方案

状态：已完成

## 一、问题与目标

当前批次能够严格生成用户要求的 Prompt 数量，但存在三类事实质量问题：

- 产品名称被自动绑定到每条 Prompt，掩盖了卖点、痛点、受众和场景的实际利用深度。
- 生成前的事实分配会直接影响最终绑定；部分证据与事实不匹配时仅记录提醒，错误绑定仍进入覆盖统计。
- 核心事实只获得一两个候选机会，最终择优可能把唯一承载该事实的候选淘汰，导致批次缺失必用洞察。

本次目标：

- 批次必须覆盖全部已确认的核心/次要卖点、核心痛点、目标受众和有效场景事实，并继续满足信息卡其他必用事实。
- 每条最终 Prompt 除产品身份外，至少正确使用一个深层业务事实。
- 计划分配与最终事实绑定彻底分离；只有经过证据和角色校验的事实才能进入 `insightBindings`。
- 保持用户设置的精确数量、当前八阶段拓扑、一段式共用提示词、V5 历史兼容和 WorkingArtifact 提交边界不变。

## 二、实现方案

### 1. 批次事实排班

在现有事实视觉策略之后建立批次级覆盖排班：

- 产品名称仅作为产品锚点，不计入深层事实覆盖。
- 核心/次要卖点、核心痛点、全部目标受众以及已确认的使用、购买、情绪场景进入深层必用事实集合；信息卡其他 `required` 事实继续参与批次覆盖。
- 每个必用事实至少分配给多个候选槽位，避免唯一候选被质量评估或去重淘汰后整批缺失。
- 单条任务只接收一个主要业务事实、最多两个辅助事实和产品身份锚点，不把完整信息表塞给单条生成模型。
- 抽象卖点、工艺、味觉和储存承诺必须遵守事实视觉策略，不得要求模型用普通画面伪造证明。

### 2. 计划事实与实际绑定分离

生成任务中的事实分配只表示“计划使用”，不得直接生成最终 `insightBindings`。

评估后由 Worker 根据经过校验的证据重新构造最终绑定：

- `EVIDENCE`：正文可以直接观察到的产品、动作、场景或视觉事实。
- `CONTEXT`：由人物、场景、创意主线或产品关联点准确承载，但不声称画面能够证明的抽象事实。
- `PRIMARY`：产品名称或品类等身份锚点。
- 证据不存在、证据与事实不匹配、事实职责冲突时不生成绑定。

继续复用现有三种公开绑定角色，避免制造第二套契约。产品名称可以保留为身份绑定，但不计入深层覆盖。

### 3. 证据验证

- 模型评估结果只作为候选，Worker必须验证证据文本确实存在于正文、创意主线或对应六维字段。
- 不允许用“真空袋装”证明肥瘦配比，不允许用“家庭厨房”证明传统工艺，不允许用普通烹饪动作证明味觉。
- `FACT_EVIDENCE_NOT_IN_CONTENT` 和 `FACT_EVIDENCE_MISMATCH` 对应的事实绑定必须被移除，不能只保留提醒。
- 与视觉策略冲突的抽象事实不得作为可见证据；必要时只能按创意背景角色使用。

### 4. 覆盖保护择优与定向补充

- 先从质量合格候选中为每个必用事实保留至少一条正确实现的 Prompt，再使用现有质量与新颖度策略填满剩余数量。
- 覆盖保护不得保留硬问题候选，也不得绕过食品逻辑、事实安全和结构校验。
- 某个必用事实没有合格候选时，定向补充只领取缺失事实、兼容方向和已有重复簇避让信息。
- 最终仍缺失必用事实时保留精确数量草稿并标记 `NEEDS_REVIEW`，不得伪造绑定或覆盖已提交 WorkingArtifact。

### 5. 页面与安全投影

- Prompt 卡片区分“画面已体现”“人物/场景体现”“创意背景”，不把计划事实显示成最终事实依据。
- 覆盖概览继续保持精简；节点详情展示必用事实数、已正确覆盖数、缺失数、错误证据剔除数和定向补充结果。
- 不展示内部事实 ID、模型输入模板、原始响应或存储信息。

## 三、兼容与边界

- 不新增数据库表或公开 HTTP 路径。
- 新字段保持向后兼容；V5 历史结果不原地伪造新角色。
- 生成、人工编辑和异步评估只更新领域草稿与 `WorkflowNodeState`。
- 只有用户完成校验且数量精确、全部条目已验证、必用事实覆盖通过时，才提交 `prompt-batch:{productId}`。
- 不修改效果类第 4～6 节点、定制类或裂变类工作流。

## 四、测试与验收

- 50 条结果中不得出现只依赖产品名称的条目。
- 每条至少存在一个经过验证的深层业务事实绑定。
- 全部核心卖点、核心痛点、目标受众和有效场景至少正确使用一次。
- 错误证据、证据缺失和事实职责冲突不得进入最终绑定与覆盖统计。
- 抽象工艺、味觉、比例和储存事实不得被普通画面伪造证明。
- 覆盖保护与向量 MMR、簇感知新颖度、精确数量和一次定向补充共同工作。
- 回归人工新增、人工修改、单条重生成、异步评估、共用提示词、历史结果和 WorkingArtifact 生命周期。
- 执行 Worker pytest、mypy、Ruff、Contracts/API/Web 相关测试、类型检查、生产构建和 `git diff --check`。

## 五、真实实施记录

已完成：

- 核心及次要卖点、核心痛点、目标受众和全部已确认场景进入深层业务事实集合；批次选择仍覆盖信息卡中全部 `required` 事实。
- 初始事实调度优先让必用事实获得多个候选机会；最终选集缺失事实时新增 `COVERAGE` 定向补充，并纳入现有候选总量上限与三轮恢复机制。
- 生成简报把每条任务的第一项业务背景标为必用，并指定写入 `scene / persona / productRelation` 中的一个字段；单条模型仍只看到本条小型简报。
- Worker 逐项验证证据是否真实存在于正文、创意主线或六维字段，并验证摘录与事实原文相符。错误摘录会删除绑定，产品名称或规格不能单独满足深层事实要求。
- 最终结果继续使用 `PRIMARY / EVIDENCE / CONTEXT`；可见证据与创意背景分别投影，不新增数据库字段或公开路径。
- API 完成校验增加 `MISSING_DEEP_BUSINESS_FACT`：在当前覆盖契约存在深层业务事实时，任何只绑定产品身份的条目都不能通过。
- 修复人工新增/编辑请求漏传 `targetDurationSeconds` 导致的 Web 生产构建失败。

真实验证结果：

- Prompt Worker：`pytest` 通过，111 项通过、1 项付费集成测试跳过；`mypy` 通过。
- API：31 个测试文件、231 项测试通过；TypeScript 类型检查和生产构建通过。
- Contracts：3 个测试文件、17 项测试通过；类型检查和构建通过。
- Web：29 个测试文件、155 项测试通过；类型检查和生产构建通过。
- `git diff --check` 通过。
- `uvx ruff check src tests` 能执行，但仓库当前存在 47 项既有 Ruff 规则问题，涉及多个本次未改模块；本次新增代码的未使用变量和导入问题已处理，没有用批量自动修复改写用户现有工作区。
