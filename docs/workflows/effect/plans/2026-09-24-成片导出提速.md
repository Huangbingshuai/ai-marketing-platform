# 成片导出提速

## 目标

把成片输出的单条渲染耗时从当前的 ~32–53 秒降到个位数秒级，100 条批次从 ~63 分钟降到 ~12 分钟量级，且**不改变成片的像素、音频、时长、分辨率、帧率与文件结构**。

## 现状与实测

2026-09-24 用真实素材复现：`.tmp/bench-real/`（已 gitignore）保存了「广式腊肠 · 测试3」的真实 `snapshot.json` 与 13 个真实源文件，直接调用 `effect_template_mix.final_output.render()`，多轮交错取最优值。机器为 20 线程 i7-13650HX。

数据库中唯一一次真实批次（`EffectFinalOutputRun 17917866`，100 条 `测试3 · 1..100`，每条 44 秒 / 720p / 30fps / 3:4 / 6 素材 / 6 口播）从 17:29:35Z 跑到 18:32:51Z，两条并发车道共 ~63 分钟，**~76 秒/条**。与本地复现的 32–53 秒/条量级一致（真实批次还叠加了下载与上传）。

### 根因

`final_output.py:244`（分段编码）与 `:356`（合成编码）把 `-threads 1` 写在了**输出选项**位置：

```python
# :244 分段
'-c:a', 'aac', '-ar', '48000', '-ac', '2', '-threads', '1', '-shortest', str(target)
# :356 合成
'-c:v', 'libx264', '-preset', 'fast', '-crf', '20', '-threads', '1', '-c:a', 'aac', ...
```

ffmpeg 的 `-threads` 是位置相关的：出现在 `-i` 之前是**解码**线程数，出现在输出编解码参数之后才是**编码**线程数。只有后者会把 x264 钉成单线程。`encode()`（`:119-121`）里那组 `-threads 1 -filter_complex_threads 1 -filter_threads 1` 拼在 `*args` 最前面，对两条调用路径都落在第一个 `-i` 之前，属于输入侧，**不限制编码**。

单条渲染共 7 次 ffmpeg 调用，耗时分布（现状）：

```
[2.8, 6.1, 6.3, 6.3, 3.8, 2.4, 25.0]   # 6 段分段 27.7s + 合成 25.0s
```

### 实测对照

`FINAL_OUTPUT_MAX_CONCURRENCY=2`（线上默认），两条并发为一个批次，两轮交错：

| 配置 | 批次 wall | 每条 | 吞吐 |
| --- | --- | --- | --- |
| 现状（shipped） | 63.7 s / 106.7 s | 31.9 / 53.3 s | 1.1–1.9 条/分钟 |
| 只去掉输出侧 `-threads 1`（noout） | 26.2 s / 26.2 s | 13.1 s | **4.6 条/分钟** |
| 连输入侧 / 滤镜 cap 一起去掉（nocap） | 26.5 s / 27.6 s | 13.1–13.8 s | 4.3–4.5 条/分钟 |

单条、无并发的对照（`run_variants.py`）：现状 55.4 s / 56.9 s，noout 15.5 s / 16.7 s，产物字节数完全相同（11.7 MB）。

### 结论

1. **只有输出侧的 `-threads 1` 是瓶颈。** 去掉它，2 并发下 4.6 条/分钟（现状 1.1–1.9），单条 13.1 秒。
2. **输入侧 / 滤镜 cap 没有可测收益**（26.2 vs 26.5 / 27.6，落在噪声内）→ 保留，它们仍承担资源上界的职责。
3. 现状在并发下抖动极大（63.7 与 106.7），因为单线程 x264 让每条渲染对机器负载极度敏感；去掉 cap 后两轮几乎一致。
4. 去掉 cap 后 6 段分段合计 6.6 秒、合成 6.1 秒——**合成那一次编码本身就占了近一半**，这是阶段二的动机。

## 阶段一：去掉输出侧线程上限（立即做，低风险）

改动仅三处，不触碰滤镜图：

- `workers/effect-template-mix/src/effect_template_mix/final_output.py:244`：删除 `'-threads', '1'`。
- 同文件 `:356`：删除 `'-threads', '1'`。
- 同文件 `:119-121`：输入侧 cap 原样保留，补一行注释说明「这些是输入侧选项，不影响编码线程数；输出侧不设 cap，整体并行度由 `FINAL_OUTPUT_MAX_CONCURRENCY` 控制」。

同时更新 `docs/workflows/effect/plans/2026-09-23-成片后端百条批量渲染可靠性.md:9`：该行「每个 FFmpeg 进程限制编码和滤镜线程数为 1」是当年未经验证的假设（同段自己也写了「实际消耗仍需在部署机器上测量」），改为本次实测结论。

线程与并发的边界，需要写进注释与本文件：

- 单进程 x264 默认按 `nproc` 取线程，`-preset fast` 下实际饱和点远低于核数（本机 20 线程实测约 8–10 线程即饱和，见下表）。
- 2 条并发 × ~10 线程 ≈ 吃满本机 20 线程；这正是默认并发 2 的合理区间。
- `FINAL_OUTPUT_MAX_CONCURRENCY` 默认值 2 与「4K 批次强制 1 条」（`:443-445`）**本次都不改**。

单条并发矩阵（`run_matrix.py`，2 并发，best-of-3，去掉全部 cap 后显式回填 `-threads N`）：

| 输出侧线程数 | 吞吐 |
| --- | --- |
| 2 | 2.7 条/分钟 |
| 4 | 3.2 条/分钟 |
| 8 | 4.1 条/分钟 |
| 不设 cap | 4.3–4.6 条/分钟 |

单调递增且在不设 cap 处收敛，说明默认行为已接近该机器的最优点；将来若要在并发上界内均分线程，再引入显式配置（本次不做，先验证无 cap 的实际行为）。

## 阶段二：单遍渲染（去掉中间分段文件）

**风险较高，且与正在进行的叠化导出验证改同一张滤镜图，必须排在 `2026-09-24-叠化预览连续播放修复.md` 落地之后再动。**

现状是两遍：先把每个可见区间编码成 `segment-N.mp4`（6 次），再把这些 mp4 当输入重新解码，走 concat/xfade、叠字幕、混音，二次编码。单遍则把源素材按 `-ss/-t` 直接喂进 `filter_complex`，在滤镜里做 `trim,setpts,scale,pad,setsar,fps,settb`，之后接**完全相同**的 concat/xfade + 字幕 + 音频图。

原型（`.tmp/bench-real/onepass.py`）已跑通真实快照：单次 ffmpeg 调用 **4.3 秒**（现状 noout 为 15.5–16.7 秒）。产物校验：44.000000 秒、720×960、30/1 fps、h264+aac、**恰好 1320 帧**（与现状一致）；音频均值 −25.1 dB、峰值 −9.2 dB 与现状一致；与现状输出的 SSIM 0.988992（单遍少一次有损编码，理论质量更高）。附带收益：省掉 6 次中间文件写入与 6 次 `probe`，临时盘占用从「全部区间」降到 0。

必须处理的风险：

- **每段编码后的 `validate_rendered_video_duration`（`:246`）会消失。** 该检查的语义是「源画面轨不足以覆盖区间」。同一条件已在源侧由 `validate_video_interval`（`:232`）用 `video_stream(info)` 的真实画面轨时长判定，守卫不丢。
- 最终产物校验（`:357-368`：容器时长、每路画面轨时长、分辨率、平均帧率、h264/aac）继续生效，是最后一道防线。
- 新增用例：源画面轨短于请求区间时，单遍路径仍抛 `PackagingError`。
- 回归：`test_real_h264_aac_render_has_exact_duration_audio_and_last_frame`、`test_confirmed_six_slot_package_renders_complete_timeline`、`test_dissolve_export_has_start_midpoint_and_end_blend_frames` 必须全绿。`capture_filters()`（`tests/test_final_output.py:385`）只抓带 `-filter_complex` 的那一次调用，而分段路径从来没有 `-filter_complex`，所以 `:401-447` 的口播/音乐/淡入淡出滤镜图断言**天然继续有效**，不需要改写。

预测：阶段一 + 阶段二后，单条的 ffmpeg 时间从 12.7 秒降到 ~4.3 秒；加上仍在串行的 14 次 `ffprobe`（约 2.5 秒），单条约 7 秒，2 并发下 100 条约 8–11 分钟。阶段三并行化探测后可再压缩。

## 阶段三：并行化 probe（可选，排在阶段二之后）

`render()` 目前串行探测：`media = {file_id: await probe(path) for ...}`（`:224`）13 次，加每段 6 次、最终 1 次，共 **20 次 `ffprobe` / 条**，实测合计 ~3.5 秒。改成 `asyncio.gather` 并发后单条可省 2–3 秒。

注意阶段二之后这一项的占比会显著上升（~7 秒里 ~2.5 秒），所以顺序是阶段二在前。

## 非目标

- 不改 `FINAL_OUTPUT_MAX_CONCURRENCY` 默认值与取值范围、不改「4K 批次强制 1 条」、不改租约 / 心跳 / 40 分钟超时语义。
- 不改转场映射、字幕排版、`amix` / `alimiter` / ducking 混音规则，不改变任何像素与音频结果（阶段二只少一次有损编码）。
- 不引入硬件编码器（NVENC/QSV）或外部渲染服务：部署机不保证有可用编码硬件，且 CRF 语义与 x264 不一致。
- 不改 `packaging_media.py` 与包装链路（该文件 `:13` 也有一处输入侧 `-threads 1`，属另一条链路，本次不动）。

## 风险

1. **线程超订**：无 cap 后单进程吃满核数，多进程并发会互相抢占。默认并发 2 已实测为该机器最优点；4 并发是否仍划算需在部署机复测。
2. **内存**：x264 线程数上升会增加帧缓冲。4K 下并发仍为 1，但单进程内存需在部署机测量（原文档已声明未测）。
3. **排期冲突**：阶段二改的正是叠化验证所在的滤镜图，两边同时改 `final_output.py` 会互相踩。
4. **像素差异**：阶段二改变生成代数，输出像素与现状有极小差异。自动用例覆盖时长 / 帧率 / 编码 / 转场，但**部署前需用真实素材人工看片一次**。

产物校验（从 MinIO 取回 `测试4 · 1` 与两遍基线逐帧比对）：时长 45.966667 s、720×960、30/1 fps、1379 帧、h264+aac 全部一致；音频三点差 ≤0.02 dB；逐帧 SSIM 均值 0.9752、最小 0.9544、低于 0.95 的 0 帧；五个叠化切点窗口内 SSIM 最小 0.9634–0.9705，无错位。100 条产物 11.2–18.0 MB，均值 14.1 MB。

注：容器是按当前工作区构建的，因此这批成片同时包含并行会话未提交的字幕边距改动（ASS `MarginV` 由 `height*.08` 改为 `height*.05`）。该改动只影响字幕纵向位置，与耗时无关。

### 结论

测试4 的收益（1 并发 4–5×，2 并发 4–9×）比测试3 更大，因为叠化多、两遍路径里「分段编码 + 再解码重编码」的重复开销被吃掉的比例更高。三阶段改动对叠化密集的时间轴同样有效且成片等价；真实 100 条批次 22 分钟跑完、零失败。
