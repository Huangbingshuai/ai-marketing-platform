# 混剪分支携带 AI 归槽填充结果（素材库不再退回包装前）

## 目标与边界

用户真机反馈：「智能成片包装的时候这个素材库为什么变回智能包装前的样子了，保持素材归入槽位不行吗」。

要的效果：**fork 出来的分支，素材库保留它继承来的 AI 归槽结果**——「AI 归槽素材筛选」的分类芯片、每张素材卡上的「AI 归槽分」、以及填充阶段的已完成状态，都跟父 Run 一致；用户在新分支里看到的是同一套归槽，而不是退回成「没填充过」的素材库。

不在本次范围：分支时点语义（上一份计划已定：混剪填充/包装成功即新增分支、成片整批导出成功才新增分支）、`oneMaterialPerFile` 的素材去重（并行会话的 `2026-09-29-混剪素材库重复卡片修复.md`）、成片局部更新。

## 根因

混剪工作台的 AI 归槽池**不是**从草稿重建的，而是从「当前 Run 的 COMPLETED 填充运行（`effectTemplateMixAiRun`）」读出来的：`EffectTemplateMixService.toWorkspaceData` 的 `classificationPools` 循环（`effect-template-mix.service.ts:2495-2553`）逐条校验冻结快照后，把分类芯片和每素材的匹配分发给前端；草稿里的 `bindings` 只是 `slotId → materialId`，没有槽位分类、也没有每个素材的分项打分，**无法**从草稿还原这个池。

而 fork 只克隆了 0-3 阶段的产物（`render-clip:` 等），**没有克隆填充运行**。于是子 Run 的 `listRecent` 返回空，`aiRuns: []`、`classificationPools: []`，工作台就退回成「填充前」的样子。

### 实测（项目 `40d1273a-e1cd-4cae-8f83-02fdaf324dc1`，模板 `7ec78e67`）

`GET /api/projects/:id/workflows/effect/template-mix?workflowRunId=<run>`：

| Run | fork 点 | 自己的填充运行 | `aiRuns` | `classificationPools` | `materials` |
| --- | --- | --- | --- | --- | --- |
| `95c92da8`（祖先，旧版就地填充 4 次） | INFORMATION_EXTRACTION | 4 | 4 | 1 | 20 |
| `f12f4df6`（包装 fork） | TEMPLATE_MIX | 0 | **0** | **0** | 20 |
| `6d10e9fc`（重新填充 fork） | TEMPLATE_MIX | 1 | 1 | 1 | 20 |
| `931d7abb`（包装 fork，当前活动分支） | TEMPLATE_MIX | 0 | **0** | **0** | 20 |

`f12f4df6` / `931d7abb` 有 20 条素材、却没有池——正是用户看到的「素材库变回包装前」。

## 改法

### 1. fork 时克隆填充运行（`effect-branch-clone.ts` + `effect-edit-session.ts`）

新增 `cloneMixAiRunsInTransaction(tx, projectId, sourceRunId, childRunId, ids)`：

- 取源 Run 最新 20 条 `status: 'COMPLETED'` 的 `effectTemplateMixAiRun`；
- `inputSnapshot` / `classificationResult` / `selectionResult` / `samplingResult` / `trimResult` 用**产物克隆的同一张映射表**重写（`{ ...ids, ...artifactIds, ...hashReplacements }`）——冻结快照按 id + contentHash 指名素材产物，两者必须一起改写，否则池子在子 Run 里解析不到；`nullableJson` 负责可空 Json 列要用 `DbNull` 而不是 `null`；
- `idempotencyKey` 写成 `inherit:<childRunId>:mix:<sourceRunId>`，保留 `createdAt` / `completedAt`，`status: 'COMPLETED'`、`progress: 100`。

调用点在 `beginEffectEditInTransaction` 的产物克隆之后（`effect-edit-session.ts:478-488`），条件 `stageIndex >= 3`，源 Run 取 `stageSources.get('SEGMENT_RENDER') ?? parent.id`：

- 只有 `stageIndex >= 3` 的 fork 才克隆 `render-clip:`，所以**有 render-clip 的那个祖先，正好就是填充快照里的素材 id 还能解析的那个 Run**；
- 于是不变式「持有 render-clip 的 Run 也持有这些 clip 的填充运行」在 渲染 → 混剪 → 包装 → 导出 的每一层 fork 上自我延续：填充后的每一次重新生成都带着池子，不需要回溯到更早的祖先。

`createdAt` 原样保留还有一个作用：`listRecent` 按 `createdAt desc, id desc` 排序，而 `classificationPools` 对同一 `templateId` 取**第一条**命中，所以分支自己新跑的填充（`createdAt` 更新）一定排在继承来的之上，池子显示的是最新一次归槽，而不是继承的旧结果。

### 2. 版本树不能把继承的填充算成一次填充（`workflow-working.service.ts`）

`fillChainVersion` 原先用「这个 Run 有没有该模板的 COMPLETED 填充运行」判定「这个 Run 真的填充过」。克隆进来的行会让包装/导出分支**看起来自己也填充过**——实测里 `931d7abb` 的 `fillRevision` 会从 2 变成 3（版本03），直接回退上一份计划 `2026-09-29-混剪分支节点重复修复.md` 的结论。

- `workflow-working.repository.ts` 的树查询给 `effectTemplateMixAiRuns` 补 `idempotencyKey: true`；
- `isInheritedFillKey(key)`（`effect-branch-clone.ts`）判定 `inherit:` 前缀，`fillChainVersion` 要求 `!isInheritedFillKey(...)` 才算这个 Run 自己的填充。

真实填充的 key 是前端 `crypto.randomUUID()`，`inherit:` 命名空间不可能撞上。

### 3. 读时回指：分支自己没有填充时，向最近的祖先借（`effect-template-mix-ai.repository.ts` + `effect-template-mix.service.ts`）

上面两条只在「fork 出来的那一刻」补数据，而 fork 只从 `stageSources.get('SEGMENT_RENDER')` 取填充——也就是**直接父 Run**。父 Run 有 clip 却从来没填充过时（本项目的 `f12f4df6` / `3d243481` / `931d7abb` 都是这种：它们由包装/重新填充产生，clip 是克隆来的、填充行没有），克隆源一行都取不到。真机探针（临时 spec，事务内 fork `931d7abb` 后回滚）实测：

```
PROBE_RESULT {"srcFills":0,"childFills":0,"child":"aabeea0e-…"}
```

即「持有 render-clip 的 Run 也持有这些 clip 的填充运行」这条不变式在存量数据里是假的，而且**不会自愈**：从 `931d7abb` 再 fork 一次，子 Run 依然是空池。更根本的是，池子守卫要求快照里的 `id` / `artifactRevision` / `contentHash` 全部落在**当前正在看的这个 Run 自己的产物**上，所以任何「往上传」的方案都必须把祖先的快照重新指到本 Run 的产物上。

于是新增读时回指，作为唯一能修好存量分支、且不需要重跑付费任务的手段：

- `EffectTemplateMixAiRepository.inheritedMixAiRuns(projectId, workflowRunId)`：沿 `parentWorkflowRunId` 往上走，收集每个祖先 `status: 'COMPLETED'` 且 `outputVariantId != null` 的填充，**每个模板取最近的一条**（近的祖先赢），走到根为止。
- `toWorkspaceData` 多收一个 `inheritedAiRuns` 参数（默认 `[]`，3 个调用点 `workspace` / `saveDraft` / `mutate` 传入），`classificationPools` 的循环改成 `[...aiRunRecords, ...inheritedAiRuns]`——**自己的填充排前面**，所以分支重新填充过就显示自己跑的，只有没碰过的模板才回落到继承的。`aiRuns`（DTO 里的填充历史）仍然只列本 Run 自己的行，界面不会冒出一个别的分支的运行记录。
- `remapInheritedFill(run, artifacts, activeMaterials)` 把祖先快照重新指向本 Run：
  - `materials[]` 按 **`fileObjectId`** 对齐（渲染文件是两个 Run 唯一共享的东西），`id` / `artifactId` / `artifactKey` / `artifactRevision` / `contentHash` 一律换成**本 Run 那一行**的值——守卫读的是产物行上的 `revision` / `contentHash`，不是 clip payload 里的；
  - `promptArtifacts[]` 换成本 Run 的 `prompt-batch:` 产物（每个 Run 只有一批；产品 id、`prompt-batch:` key、contentHash 都按 fork 重新生成，**join 不上**，所以只能整体替换）；
  - `classificationResult[].materialId` 跟着 `materials[]` 的映射改写；
  - 任何一条素材在本 Run 找不到对应文件，或快照缺 `prompt-batch:` 产物 → **整条丢弃**（半改写的快照会打分出一个不属于本 Run 的池子）。模板槽位签名不一致、分类不完整等继续由既有守卫拦下。

两条路径互补：fork 时能把填充带走就带走（分支自己的数据里就有池子），带不走（祖先没有填充、或分支建于该能力之前）由读时回指兜底。实测 `931d7abb` 的 `aiRuns` 仍为 0，但 `classificationPools` 从 0 变成 1 / 20 条。

## 测试

- `effect-edit-session.database.spec.ts` 新增「carries the fill runs that produced the pool into a mix branch」（真机库、回滚事务）：夹具挑一条**自己既有 `mix-template:` 又有 `render-clip:` 又有 COMPLETED 填充**的可分支 Run，fork 后断言
  - 子 Run 的填充行数 = 源 Run 的 COMPLETED 行数，且每行 `idempotencyKey` 以 `inherit:` 开头、id 与源行不重合、`COMPLETED` / `progress: 100`；
  - 快照 `materials[]` 的 `artifactId` / `contentHash` / `artifactRevision` 全部落在**子 Run 自己的** `render-clip:` 产物上（与工作台 `classificationPools` 守卫的三项判据一一对应）；
  - 快照 `promptArtifacts[]` 的 `id` / `contentHash` / `revision` 全部落在子 Run 的 `prompt-batch:` 产物上；
  - `classificationResult[].materialId` 全部落在快照 `materials[].artifactId` 集合内（分类与快照必须用同一张映射表重写）。
- `effect-template-mix-ai.repository.spec.ts` 新增 `inheritedMixAiRuns`：最近祖先的填充被带回、近的祖先没填充时继续往上走、同一模板近的赢、不同模板各自收集、根 Run 返回空且不查库。
- `effect-template-mix.service.spec.ts` 新增三条读时回指用例：祖先快照（产物 id / revision / contentHash 全是别人的）能读出池子且 `aiRuns` 仍为空；素材文件在本 Run 找不到对应 → 丢整条；祖先冻结的模板槽位布局与本 Run 不一致 → 丢整条。
- `workflow-working.service.spec.ts`：所有 `effectTemplateMixAiRuns` 夹具补 `idempotencyKey`（真实填充用客户端 key）；「keeps an inherited mix layer on its ancestor version…」的导出子分支补一条 `inherit:` 行，让守卫真正生效（去掉守卫会读成 2）；「numbers a re-filled mix layer…」「keeps an unpublished packaging child out of the tree…」的中间包装分支同样补 `inherit:` 行，覆盖「部分完成/整批完成的包装分支都不得算成一次填充」。
- `workflow-working.repository.spec.ts`：树查询断言补 `idempotencyKey: true`。

## 存量数据

`f12f4df6` / `3d243481` / `931d7abb` 这类「有 clip、没有填充行」的存量分支**不再需要任何回填或重跑**：读时回指在打开工作台的那一刻就把最近祖先的填充指回本 Run，池子直接出来（真机实测 0 → 20 条）。不写库、不改历史，因此也不会影响版本树的计数（`inherit:` 守卫仍然管着 fork 时克隆进来的行）。
