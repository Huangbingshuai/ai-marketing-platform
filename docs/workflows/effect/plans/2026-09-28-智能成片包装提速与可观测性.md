# 智能成片包装提速与可观测性

## 范围与依据

仅改造效果类模板混剪节点的智能包装链路，复用现有 Run、Outbox、队列和 Worker。直接上游仍是同项目、同工作流 Run 已确认的商品事实、素材与视觉时间轴；包装先保存草稿，统一完成操作才提交 `timeline-project:*` 和 `timeline-package:*` 工作副本，成片输出继续只消费已确认版本。本次不重做口播规则、不变更付费服务协议，也不自动发起真实付费批次。

2026-09-28 紫苏梅子酱 100 条热缓存批次执行 36 分 07.637 秒，100 条成功。普通条目平均约 71.6 秒；配乐任务等待 P50 21.89 秒，最后一份配乐文件约在条目启动后 63 秒入库，且 91 条普通条目中 83 条以配乐为最后资产。配乐查询成功至文件入库的下载、预处理排队、转码、上传和 API 校验尚未分项计时。两次 Run 中断仅记录 `ExceptionGroup`，无法识别内部故障。现有 Worker API 每次单条检查点会重复读取整批 100 条和完整展示状态，并逐份查询音频归属。

## 实施

1. 为音乐下载、预处理排队、转码、上传，以及口播上传、字幕生成和 API 写回记录脱敏分项耗时。保留现有耗时字段和旧检查点兼容；仅记时长，不记录文本、音频 URL 或密钥。将嵌套异常拆为安全的异常类型链及内部 API 状态码，便于查明整批中断原因。
2. Worker 单条读取改为数据库只取目标 Item 与 Run 元数据；当前视觉成片直接从经原规则校验的节点草稿读取，仅查询快照依赖的 artifact ID，避免构建完整素材池、UI 工作区及全部工作副本。仍按视觉 hash 和已确认上游 artifact revision 判断过期。检查点只做一次目标读取；音频归属改为同条件批量查询，并验证全部去重文件 ID，不能放宽项目、工作流、模板、成片和视觉来源隔离。写回仍由原事务的 attempt token/lease 更新栅栏保护。
3. 将包装条目并发、模型并发和 TTS 并发解耦为有界配置；默认条目池从 4 提至 6，但模型与 TTS 各自仍限制 4，音乐提交/查询继续使用独立限流，视频预处理保持最多 2 条。先用可控 Fake Provider 验证六条补位、断点恢复，再用真实分项指标检查 429/超时是否回升；只有稳定后才尝试 8 条，不能把理论吞吐当作 20 分钟实测结果。
4. 若分项数据确认配乐文件后处理占主导，再针对下载/转码/上传做有测试的局部优化，不提前删除 WAV 编码、时长、归属或失败恢复校验。

## 验证与非目标

- API 测试覆盖单条读取、过期、项目隔离、批量音频归属、旧 attempt 和完成/失败写回；Worker 测试覆盖新耗时字段、嵌套异常、并发上限、失败检查点恢复。
- 执行 Contracts/API/Worker 相关测试、类型或语法检查及 `git diff --check`。真实 100 条冷/热批次另行按用户主动触发执行，并报告墙钟耗时、P50/P95、缓存命中、供应商限流和中断。
- 不新增容器、队列、服务、缓存跨 Run 复用或改变字幕与口播的一对一对齐约束。
