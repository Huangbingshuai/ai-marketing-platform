# 混剪素材池收敛到「当前渲染批次」

## 范围

- 只改混剪节点读取素材池的组装：把 `render-clip:*` 的枚举范围从「该 workflow run 下所有 render-clip 产物」收敛为「当前渲染批次列出的片段 ∪ 仍然 CURRENT 的片段」。
- 不改 Prompt 失效粒度、不放宽 `freshness='CURRENT'` 过滤、不改智能填充（`sourceArtifacts`）、不改包装来源解析、不改前端、不加 Prisma 迁移。

## 现状问题

用户报：「都已经是最新素材了，还显示这个：100 条素材已过期（对应的 Prompt 已更新），智能填充不会使用它们；请先在视频渲染节点重新生成。」

实测（2026-09-25，项目 `40d1273a-e1cd-4cae-8f83-02fdaf324dc1`，run `65f5b90c-046c-4f28-92e1-0e867e9f4e5f`）：

| 观测                                                                                 | 值                                                              |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| `GET /template-mix` 返回 `materials`                                                 | **200** 条（`available` = 100 true / 100 false）                |
| 库里 `render-clip:*` 总数                                                            | 200（100 CURRENT/AVAILABLE + 100 STALE/AVAILABLE）              |
| `render-batch:2e31a4b1-…`（该 product 唯一一条，revision 2，CURRENT）payload `clips` | 100 条 taskId，**全部** CURRENT/AVAILABLE                       |
| 另外 100 条 STALE 片段的 `updatedAt`                                                 | 2026-09-14 05:43:10.322，且不在任何 `render-batch:*` payload 里 |

该 run 先后有 3 个批次（`1d83c7d0` / `e894d1f1` / `d689b4bc`），但 `render-batch:<productId>` 产物每个 product 只有一条、每次校验被覆盖写。于是**被取代批次的 100 条 `render-clip:*` 永远留在库里**（没有任何代码删除它们），而混剪素材池是按 key 前缀枚举全部 render-clip，就把这 100 条死片段一起算进池子；它们又被 Prompt 变更级联标成 STALE，前端 `expiredMaterialCount = materials.length - availableMaterials.length` 就报出「100 条素材已过期」。

即：**每重新生成一轮，池子就多出一整批永远不可用的死片段，并把它们计入过期条数**。用户看到的「100 条已过期」其实全是上一批的残骸，当前批次的 100 条全是好的。

## 根因

`effect-template-mix.service.ts` 两处按前缀枚举：

- `:2199-2201`（`mutate` 里给 `mutation(workspace)` 用的池子）
- `:2235-2237`（`toWorkspaceData` 里返回给前端的池子，并派生 `availableMaterialIds`）

```ts
const materials = artifacts
  .map((artifact) => materialFrom(artifact, promptSources))
  .filter((item): item is EffectTemplateMixMaterial => Boolean(item));
```

`artifacts` 来自 `working.listArtifacts(projectId, { workflowRunId })`，不区分批次。

对照：智能填充走的是 `aiRuns.sourceArtifacts()`（`effect-template-mix-ai.repository.ts:81-97`），过滤 `freshness='CURRENT' AND availability='AVAILABLE'`，所以**只看得见当前那 100 条**——功能上没问题，问题只出在池子的展示口径与它不一致。

## 设计

### 池子口径

```
当前批次片段 = 所有 render-batch:<productId> 产物 payload.clips[].taskId 映射成 render-clip:<taskId>
池子 = 当前批次片段
     ∪ { freshness='CURRENT' AND availability='AVAILABLE' 的 render-clip }
     ∪ { 已被现有成片工程绑定的 render-clip }
```

四点理由：

1. **当前批次的片段必须保留，包括 STALE 的**。Prompt 被改后，级联会把当前批次的片段标 STALE，但 `render-batch:*` payload 不变。保留它们，「N 条素材已过期（对应的 Prompt 已更新）」这条既有提示才继续成立（这是上一轮「混剪节点素材过期前置提示」要的行为）。
2. **仍然 CURRENT 的片段要保留**。同 Prompt 重新生成时，上一批片段仍是 CURRENT，`sourceArtifacts` 会把它们喂给智能填充，已有工程也可能绑定着它们；池子若丢掉，编辑页就解析不到绑定的素材。保留后 `availableMaterialIds` 恰好等于 `sourceArtifacts` 的集合，两边不再有口径差。
3. **被工程绑定的片段要保留**。工程可能绑着被取代批次的片段（Prompt 已改、已标 STALE）。这类片段本来就是「过期且需要重新填充」，池子丢掉它只会让编辑页槽位变空白；保留后它照常显示为「已过期」，与 `refreshAffectedSlots` 那条「请先单独处理这些素材位」的既有语义一致。
4. **既不在当前批次、又不 CURRENT、也没被绑定的片段（STALE 残骸）丢弃**。它们没有任何入口可以再被选中，留在池子里只会被算成「已过期」。

无法读到任何 `render-batch:*` payload 时（老数据/结构异常）**退回不过滤**，宁可多显示也不误删。

### 实现（`effect-template-mix.service.ts`）

新增三个模块级 helper（放在 `materialFrom` 旁）：

```ts
const boundMaterialIds = (variants: Iterable<EffectTemplateMixVariant>): ReadonlySet<string> => { … };
const currentMaterialKeys = (
  artifacts: WorkingArtifact[],
  keepIds: ReadonlySet<string>,
): ReadonlySet<string> | null => { … };
const materialsFromArtifacts = (
  artifacts: WorkingArtifact[],
  keepIds?: ReadonlySet<string>,
): EffectTemplateMixMaterial[] => { … };  // 内部自己取 promptSources，再按 currentMaterialKeys 过滤后 materialFrom
```

`promptSourcesFromArtifacts` 必须用**全量** artifacts 计算（它读的是 `prompt-batch:*`），所以过滤只能发生在取完 prompt 源之后——这也是把它收进 `materialsFromArtifacts` 内部的原因。

两处调用点改为 `materials: materialsFromArtifacts(items, boundMaterialIds(…))`：`toWorkspaceData` 取 `draft.templates.flatMap((entry) => entry.workspace.variants)`，`mutate` 取当前模板的 `entry.workspace.variants`。

### 为什么不动别处

- `createAiRun` 的 `renderArtifacts`（`:919-923`）走的是 `sourceArtifacts`，本来就是 CURRENT 集合，无需改。
- 应用 AI 结果时的 `currentClipIds`（`:1628-1636`）也用 `sourceArtifacts`，与快照同源，无需改。
- 包装来源解析（`:1968-1975` 的 `listArtifacts(...)`）**保持不过滤**：已绑定到旧片段的工程必须继续能解析出源文件才能包装。
- `fillVariant` 只吃 `material.available` 的素材，池子收敛不改变它的选择结果；`needsRefill` 依赖的 `availableMaterialIds` 收敛前后是同一个集合。

## 非目标

- 不删除/不标记被取代批次的产物（那是垃圾回收，另立需求）。池子收敛后它们不再出现在界面，但表里仍然留着。
- 不改 `sourceArtifacts`，智能填充的候选集合与行为不变。
- 不改前端（池子对了，`expiredMaterialCount` 自然为 0，既有横幅逻辑不动）。
- 不加 Prisma 迁移、不写存量数据。
- 不处理「同 Prompt 重新生成后新旧两批 CURRENT 片段同时出现在池子里」的重复展示（那是 `sourceArtifacts` 的既有语义，本次不动）。

## 验收

- 上述项目 `GET /template-mix` 的 `materials` 从 200 降到 **100**，且 `materials.filter(!available).length === 0`；前端不再出现「100 条素材已过期」。
- 构造「当前批次片段被标 STALE」的用例：该片段仍在池子里且 `available=false`，过期提示照旧能触发。
- 不落在当前批次、且非 CURRENT 的片段不出现在池子里。
- 相关单测与类型检查通过（对比既有失败集合只少不多）。

## 风险

- **误判「当前批次」**：只认 `render-batch:*` payload 里的 taskId。若某 product 的批次产物缺失，该 product 的片段只能靠「CURRENT」这一支保留；STALE 片段会消失（本来也不可用）。`sawBatch=false` 时退回不过滤兜底。
- **池子仍会因「同 Prompt 重新生成」而变大**：那批片段是 CURRENT、可用、且可能被绑定，属既有语义，本次不动。
- **并行会话**：`effect-template-mix.service.ts` 近期被多个会话改动（过期提示、时间轴延伸），落地前需重新读文件。
