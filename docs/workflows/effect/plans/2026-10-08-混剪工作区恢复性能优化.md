# 混剪工作区恢复性能优化

状态：第一阶段已实施并完成浏览器回归

## 范围与边界

- 流程：效果类。
- 节点：模板混剪。
- 直接上游：当前效果类 Run 已确认的 `render-batch:*`、`render-clip:*` 及其实际 revision。
- 编辑草稿：`WorkflowNodeState(nodeId=TEMPLATE_MIX)`。

- 直接下游：成片输出。
- 本次只优化读取、恢复和后台刷新，不改变智能填充、包装、草稿保存、工作副本提交、revision、分支选择或成片待更新语义。

## 已观察问题

2026-10-08 在本地项目 `紫苏梅子酱` 只读测量：

| 请求             | 观察结果                                         |
| ---------------- | ------------------------------------------------ |
| 当前混剪工作区   | 约 1.6 秒（主机繁忙时 13.5～21.6 秒），约 783 KB |
| 效果类版本树     | 约 2.6 秒（主机繁忙时 3.5～11 秒），约 35 KB     |
| 混剪素材来源刷新 | 约 4.1 秒，约 156 KB                             |

当前页面恢复顺序为：当前工作区 → 版本树 → 多个模板头节点完整工作区。页面只有全部完成后才退出全屏加载态。同一 KeepAlive 页面重新激活时也无条件执行完整恢复，素材来源还会固定每 5 秒刷新一次。

## 实施方案

1. 冷启动并行读取当前工作区与版本树，共用一个取消信号和 30 秒总截止时间。
2. 若当前模板仍属于当前 Run，先安装当前工作区并结束全屏加载；模板目录在后台补齐。
3. 若版本树表明当前模板应切到其他 Run，继续等待完整目录并沿既有作用域切换流程加载，禁止把历史目录快照安装为可写草稿。
4. 同一 `projectId + workflowRunId` 的 KeepAlive 页面恢复时复用已安装工作区；先刷新待保存编辑，再在后台刷新素材来源。只有服务端 `draftRevision` 变化时才执行完整重载。
5. 常驻素材来源轮询由 5 秒放宽到 15 秒。运行中的 APPEND 任务仍由既有任务轮询按约 1.2 秒刷新分类结果，不降低任务态实时性。
6. 后台目录或素材刷新失败时保留当前可用工作区并显示轻量提示，不把已经恢复的页面重新切成全屏错误态。

## 一致性约束

- 缓存命中必须同时匹配 `projectId + workflowRunId`、已安装 scope 和 READY 状态。
- 项目、Run 或模板路径变化必须取消旧请求并重新读取。
- 后台目录只能更新只读目录投影；可写草稿仍只由目标 Run 的新鲜工作区响应安装。
- `draftRace`、草稿 revision、请求控制器和页面作用域检查继续阻止旧请求覆盖新编辑。
- 页面隐藏时停止轮询并取消在途读取，重新激活后再恢复。

## 验收

- 同一 Run 切出再返回时不再次请求完整版本树和全部模板工作区，已有内容立即显示。
- 冷启动的工作区与版本树并行发起；当前 Run 可直接使用时不等待历史目录加载。
- 跨项目、跨 Run、历史模板显式导航仍读取目标 Run，不能串用缓存。
- 后台目录失败不清空当前草稿；目标 Run 本身读取失败仍显示可重试错误态。
- APPEND 运行期间分类素材仍能持续更新。
- 运行相关 Web 单测、类型检查、生产构建与 `git diff --check`，并在浏览器验证首次进入、同 Run 返回、跨 Run 跳转及错误恢复。

## 非目标

- 本次不修改数据库结构、WorkingArtifact revision、分支编号、智能填充或包装算法。
- 本次不清理历史 Run，也不以删除数据换取速度。
- API 专用轻量聚合查询和响应压缩可作为第二阶段；先以不改变 HTTP 契约的前端加载编排消除重复等待。
