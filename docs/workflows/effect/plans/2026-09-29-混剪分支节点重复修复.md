# 版本树把包装分支的模板/填充副本当成新版本，同一个混剪模板出现两个节点

## 2026-10-03 补充：兄弟分支草稿重复显示同一模板

紫苏梅子酱项目中，模板 `4592fa66-47ef-436a-84f6-76fe50f97ca9`（测试2）同时出现在最初创建它的混剪分支，以及测试4分支的模板草稿中。两份记录的模板 ID、创建时间一致，且共享同一个视频渲染来源。原绘图只检查直接父分支是否存在模板；测试4的直接父分支不含测试2，因而再次绘出模板节点。

绘图现在以「上游视频渲染路径所属 Run + templateId」确定唯一模板节点，按分支创建时间稳定选择最早的来源。节点绘制、活动路径标红和下游连线共同使用该归属。兄弟分支中的同一模板草稿不再生成第二个节点；已存在的填充、包装版本仍连接到原模板。不同上游渲染版本、手动复制分支和不同模板 ID 保持独立，不按显示名称删除或合并数据。

回归覆盖：兄弟分支携带相同模板、乱序 API 响应、活动路径与下游连线、上游渲染分叉；既有手动复制和新建模板用例继续验证。仅修正树的显示归属，不修改领域记录、工作副本 revision 或媒体文件。

## 目标与边界

用户真机看版本分支树后反馈：「混剪模板怎么有两个测试1节点，明显错误，一个混剪模板只能对应一个节点；智能填充也有两个版本01」。

实测确认：活动路径上同一列（`x=1476` 灰 / `x=1664` 红）并排出现

| 层       | 分支 A `95c92da8`        | 分支 B `f12f4df6`（活动） |
| -------- | ------------------------ | ------------------------- |
| 混剪模板 | 测试1（`7ec78e67`）rev=1 | 测试1（`7ec78e67`）rev=1  |
| 智能填充 | 测试1 rev=1 count=4      | 测试1 rev=1 count=4       |

即同一个模板、同一个版本被画了两遍。只改版本树对「混剪 fork 落在哪一层」的判定；fork 的克隆行为、`inheritedEffectArtifactVisible`、画布其余部分都不动。

## 根因

`getEffectBranchTree` 的 `forkMixStage` 是**从子 Run 自己的产物猜**出来的（`workflow-working.service.ts` 旧代码按 `mix-template:` → `timeline-project:` → `timeline-package:` 的顺序取第一个命中的 key）：

- 包装 worker 校验冻结快照是 **Run 维度**的（`EffectPackagingRepository.sourceArtifacts(projectId, workflowRunId, ids)`），所以 `upsertFromPackaging` 必须在子 Run 里**重提交**一份 `mix-template:` + `timeline-project:`（`effect-final-output.service.ts:184`）。
- 于是包装子 Run 也带着 `mix-template:`，按旧顺序被判成 `'TEMPLATE'`（fork 层 = 混剪模板），前端 `forkStageIndex` 得 4 → 子 Run 从第 4 层开始画，把父 Run 已经拥有的 `MIX_TEMPLATE`/`MIX_FILL` 又画了一遍。

这两份副本是**逐字节相同的拷贝**，不是新版本（实测 `md5(payload::text)`）：

| 产物                                 | 父 Run `95c92da8`                  | 子 Run `f12f4df6`                  |
| ------------------------------------ | ---------------------------------- | ---------------------------------- |
| `mix-template:7ec78e67`              | `22b92e78375ddb5ccbee3365418121af` | `22b92e78375ddb5ccbee3365418121af` |
| `timeline-project:7ec78e67:52f7919f` | `5673045745bb4ed599c8c18b71727c6b` | `83eb5f198e8fe84de8f7ff6ee734ead5` |

`mix-template` 的 payload 完全一致；`timeline-project` 只差在 `variant.bindings`（fork 时素材 id 重映射），所以只能拿 `mix-template` 的 payload 当判据。

## 改法

`apps/api/src/platform/workflow/workflow-working.service.ts` 新增 `mixForkStage(run, forkNodeId)`，按「这个分支到底改了什么」判层，而不是「它本地有什么 key」：

1. 本地有 `timeline-package:` → `'PACKAGING'`。包装只可能在每个变体都按当前模板重新智能填充之后才跑（`EffectPackagingService.create` 的 `needsAiFill` 门禁），所以它的父 Run 一定已经显示过这个模板，子 Run 里的 `mix-template` 副本不带新信息。
2. 本地 `mix-template:<id>` 的 `payload` 与父 Run 生效集里的同名产物**不同** → `'TEMPLATE'`（真的改了模板：新增模板或改了配置，父 Run 没有这个版本）。
3. 本地有 `timeline-project:` → `'FILL'`（只重新填充，模板没变）。
4. 其余 → `'TEMPLATE'`（保持旧行为，例如空分支）。

`workflow-working.repository.ts` 的 `listEffectRunBranches` 产物 select 补 `payload: true`（原先只取 key/revision，判据用不了）。

### 为什么判据用 payload 而不是 key 是否存在

「父 Run 有没有同名 key」不够：改了模板配置再重新填充时 key 不变、payload 变了，按 key 判会误判成 `'FILL'`，新模板版本就再也画不出来（正是 2026-09-28 计划里提过的「把新版本藏起来」的洞）。payload 比对能同时区分「拷贝」与「改配置」。

### 为什么第 1 步可以短路

包装 fork 的 `mix-template` 副本来自同一份草稿（父 Run 的填充子 Run 已提交过同样内容），payload 必然与父 Run 一致；即使不去比也会落到第 3 步。短路是为了让「包装分支只画包装层」这件事读起来更直白。

## 测试

- `workflow-working.service.spec.ts` 新增「classifies a mix fork by what the branch changed, not by the copies it re-committed」：同一个父 Run 下挂三个 `TEMPLATE_MIX` fork —— 重提交了模板+时间轴+包装 → `'PACKAGING'`；重提交模板+时间轴（payload 与父一致）→ `'FILL'`；模板 payload 与父不同 → `'TEMPLATE'`。
- 既有「shows inherited templates except the template replaced by a scoped fork」仍断言 `'TEMPLATE'`（该夹具的父子 payload 都是 `null`，按新规则等于「模板没变且没有时间轴」→ 落回 `'TEMPLATE'`），未改。
- `effect-workflow-branch-layout.spec.ts` 新增「draws one template node when a packaging fork re-committed the template it inherited」：`forkMixStage='PACKAGING'` 且 `forkTemplateId=null`（真机就是 null）时，全树只剩 1 个 `MIX_TEMPLATE`、1 个 `MIX_FILL`，包装节点两处。

## 风险与取舍

- **payload 比对依赖 jsonb 的规范化 key 顺序**：两侧都来自同一个 `payload jsonb` 列，`JSON.stringify` 结果可比。若日后 `payload` 改成 `json` 类型，键序不再归一，需要换成结构化比较。
- **只对「模板改没改」用 payload**：`timeline-project` 的副本无法用 payload 区分（差在重映射的绑定），所以「重新填充」的判层靠「本地有没有 `timeline-project`」+「模板没变」，而不是比对填充内容本身。若某次重新填充产出的时间轴与父 Run 完全相同，该分支仍会画一个 `MIX_FILL` 节点（rev 从 1 起算，显示同为「版本01」）——这是 Run 维度 revision 的固有表现，本次不引入跨 Run 版本号。
- **不改 fork 的克隆**：包装 worker 的依赖校验是 Run 维度的，去掉克隆就回到「包装必然失败」。
- **不改 `inheritedEffectArtifactVisible`**：它同时服务模板维度 fork 与其他节点读取，且已有数据库用例钉住语义；重复是**树的判层**问题，在判层处收口最窄。

## 后续补充：重新填充后又冒出一个「测试1」，且填充版本回到 01

上面「待人工回归」跑完后用户又反馈：**重新智能填充一次，版本树又多了一个「测试1 混剪模板」节点，新分支下的智能填充显示「版本01」**。期望是分支直接挂在已有的「测试1 混剪模板」下面，填充版本应该是 **02**（用户原话：「反正就是和前面的节点一样啊这个版本号，每重新生成一次就添加一次版本号啊」）。

两件事，两个根因，都在 `workflow-working.service.ts`。

### 根因 1：payload 里混进了「草稿保存版本」，纯重新填充被判成改了模板

上一节的 `mixForkStage` 拿 `mix-template` 的**整个 payload** 与父 Run 比对。但 payload 不只装模板配置：

```json
{ "schemaVersion": …, "templateId": …, "workspaceVersion": <entry.workspace.editVersion>, "template": {…} }
```

`workspaceVersion` 是**草稿的保存版本**，每次 `PUT /template-mix/draft` 都会 +1。而「重新智能填充」在提交产物之前会先落一次草稿，于是子 Run 重新提交的 `mix-template` 副本虽然模板一模一样，`workspaceVersion` 却比父 Run 大 1。实测三个 Run 的 `mix-template:7ec78e67`：

| Run                    | `revision` | `payload.workspaceVersion` | `md5(payload.template)` |
| ---------------------- | ---------- | -------------------------- | ----------------------- |
| `95c92da8`（填充）     | 1          | 13                         | `90694796…e354`         |
| `f12f4df6`（包装）     | 1          | 13                         | `90694796…e354`         |
| `6d10e9fc`（重新填充） | 1          | **14**                     | `90694796…e354`         |

模板配置逐字节相同（`md5(payload.template)` 一致），只有 `workspaceVersion` 从 13 变 14 → 旧判据认为「模板变了」→ `forkMixStage` 得 `'TEMPLATE'` → 前端从第 4 层开始画，把父 Run 已经有的 `MIX_TEMPLATE` 又画了一遍，就是用户看到的第二个「测试1」。

**改法**：判据只看模板配置。新增

```ts
const committedTemplate = (payload: unknown): string => {
  const value = payload as { template?: unknown } | null | undefined;
  return JSON.stringify(value?.template ?? value ?? null);
};
```

`mixForkStage` 的 `inheritedTemplates` 与本地比对都改用它。payload 里没有 `template` 的老数据回落到整个 payload，行为不变。改完 `6d10e9fc` 判成 `'FILL'`，`forkStageIndex` = 5，不再重画模板层。

### 根因 2：混剪 fork 不克隆时间轴，`revision` 在每个分支都从 1 重来

`timeline-project:` 是「这一层的版本号」来源，而**混剪 fork 不克隆它**（`effect-edit-session.ts` 的 `stageIndex >= 4 ? slice(0, stageIndex) : …`，TEMPLATE_MIX 的 index 是 4，只克隆 0-3 阶段）——填充产物是 fork 之后新生成的。于是每个分支本地都只有自己那一份 `revision = 1` 的时间轴：

```
95c92da8  timeline-project:7ec78e67:<4 个变体>  每个 revision=1
f12f4df6  timeline-project:7ec78e67:<4 个变体>  每个 revision=1   ← 包装时重提交的副本
6d10e9fc  timeline-project:7ec78e67:<4 个变体>  每个 revision=1   ← 重新填充
```

`sharedRevision` 在每列都只看到 `1`，所以三个分支全画「版本01」。

**改法**：填充版本改成沿分支链累加，判据是「这个 Run 到底有没有真的跑过一次成功的填充」，而不是「它手上有没有时间轴副本」。`effect_template_mix_ai_runs`（`status='COMPLETED'` 且有 `outputVariantId`，`listEffectRunBranches` 本来就查了）才是权威信号：

```ts
const fillChainVersion = (run, templateId): number | null => {
  const prefix = `timeline-project:${templateId}`;
  let version = 0;
  for (游标从 run 沿 parentWorkflowRunId 上溯) {
    if (!该 Run 有 templateId 的 COMPLETED 填充) continue;   // 包装分支只是重提交副本
    version += max(该 Run 本地 timeline-project:<templateId> 的 revision);
  }
  return version || null;
};
```

实测 `effect_template_mix_ai_runs`：`95c92da8` = 4 条、`f12f4df6` = **0 条**、`6d10e9fc` = 1 条。所以 `f12f4df6` 不加，`6d10e9fc` = 1 + 1 = **2**。

> 为什么不能用「本地有没有 `timeline-project`」当判据：`f12f4df6` 也有一份（包装必须重提交，冻结快照是 Run 维度校验的），会把它算成第二次填充，下一个真正的填充就被顶到「版本03」。为什么不能拿 `createdAt` 去重：一个模板有 100 个变体就有 100 个不同 `createdAt`，会把一次填充数成 100 次。

### 测试

- `workflow-working.service.spec.ts`「classifies a mix fork by what the branch changed…」的夹具补上 `workspaceVersion: 13 / 13 / 14`，重填充那份模板配置与父完全一致，仍断言 `[null, 'PACKAGING', 'FILL', 'TEMPLATE']`。
- 新增「numbers a re-filled mix layer along the branch chain instead of restarting at 01」：`first`（填充）→ `packaged`（只重提交时间轴+包装，无 AI run）→ `refilled`（再填充），断言 `forkMixStage` `[null, 'PACKAGING', 'FILL']`、`fillRevision` `[1, 1, 2]`。
- 新增「keeps an inherited mix layer on its ancestor version instead of inventing a new one」：`FINAL_OUTPUT` fork 克隆了混剪层，断言它沿用祖先的 `fillRevision` 而不是又数一代。
- `effect-workflow-branch-layout.spec.ts` 新增「draws one template node when a fill fork re-committed the template it inherited」。

### 风险与取舍

- **只修填充层**。`MIX_PACKAGING` / `FINAL_OUTPUT` 的版本号仍是 `sharedRevision`：没有用户反馈，且包装/交付的「真的做过」信号在当前查询里拿不到（手动复制会连带拷 `final-delivery:`，`FINAL_OUTPUT` fork 会克隆 `timeline-package:`，都没法干净地区分「拷贝」与「新生成」）。若日后要修，需要给这两层补上各自的权威信号。
- **包装分支显示「版本01」是正确的**：它确实没有自己填充过，沿用的是祖先那一次（`95c92da8` 的版本01）。用户看到的活动路径是 01 → 01 → 02，中间那个 01 属于包装分支，符合「每重新生成一次加一个版本号」。
- **`fillChainVersion` 是显示层计算**，不改产物 `revision`。改存储会牵动 `expectedRevision` 乐观锁与依赖的 `sourceRevision`，代价远大于收益。
- **累加语义依赖「每个 Run 对同一模板至多一次成功填充」**。若一个 Run 内对同一模板跑两次填充（目前不存在，`createAiRun` 每次都会 fork 出新 Run），会只算一次。
