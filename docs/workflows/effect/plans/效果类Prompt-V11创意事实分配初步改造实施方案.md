# 效果类 Prompt V11：创意事实分配初步改造实施方案

## 1. 状态与范围

- 状态：已完成
- 最后更新时间：2026-08-28
- 工作流：效果类
- 业务节点：第 3 节点“Prompt 生成”

本轮只解决 V11 连贯创意生成模型需要自行浏览全部提炼事实并决定每条重点的问题。上游已经提交且为 CURRENT 的 `marketing-insight:{productId}` 继续作为可信事实来源；Prompt 节点不重写、合并、质疑或修复提炼内容。

## 2. 生命周期边界

- 直接上游：已提交的营销洞察和全局视频配置具体 `artifactId + revision + contentHash`。
- 运行草稿：生成、评估和选择只更新 Prompt 领域结果与 `WorkflowNodeState`。
- 提交边界：仅用户点击“完成校验”且 V6 结果满足数量与分类要求后，更新 `prompt-batch:{productId}` WorkingArtifact。
- 直接下游：视频渲染只消费已提交的 Prompt 批次；本轮内部事实分配不会单独造成下游 revision。

## 3. 核心方案

Worker 在规划创意分片前，为每个候选任务确定：

```text
1 个主要事实
+ 0～2 个辅助事实
+ 1～2 个产品锚点事实
```

主要事实按上游字段角色和 REQUIRED/ADAPTIVE 优先级稳定轮转；辅助事实仅按字段兼容关系选择；产品锚点保证每条与当前商品直接相关。营销目标、制作参数和禁用元素继续作为批次指导或共用约束，不作为单条主要事实。

模型输入从“全部 usable facts + 完整共用提示词对象”收缩为每个 task 的轻量事实简报，只含 `factId + field + value`、统一时长和一段共用提示词正文。模型不得引用未分配事实，并且返回的 `declaredFactIds` 必须包含本任务主要事实。

本轮不增加用户可见节点，不修改 Prompt V6 公共结果 Schema、HTTP 路径、Prisma 表或第 4～6 节点。

## 4. 兼容与恢复

- 创意任务分片继续写入现有 `EffectPromptShardOutput.combinationPlan`。
- 新任务计划包含主要、辅助和锚点事实 ID；同一 Run 重试按稳定 slot 和事实顺序生成相同计划。
- 已成功的旧格式 V11 创意分片保持可读；新模板版本产生的新 Run 不与旧 Run 混合。
- ITEM_REGENERATE 优先使用原条目的事实绑定作为主要事实候选；ITEM_EVALUATE 不重新生成正文。

## 5. 验收

- 目标 50 条时仍先规划 60 个候选，事实分配稳定且核心事实得到优先轮转。
- 每条任务只有一个主要事实，最多两个辅助事实，并至少包含一个产品锚点。
- Ark 请求不再携带未分配事实、事实哈希、策略字段或完整共用提示词 JSON。
- 模型漏用主要事实或引用未分配事实时，Provider 明确拒绝该分片。
- 六维、正文、多用途分类、精确数量、补充轮次、检查点、Mock 隔离和 WorkingArtifact 提交边界保持正常。
- 执行 Worker pytest、mypy、Ruff 和 `git diff --check`；本轮默认不调用真实 Ark 或 Seedance。

## 6. 实施结果（2026-08-28）

- 新增确定性事实分配器。每条候选均持久化一个稳定的主要事实、最多两个辅助事实、一个或两个产品锚点及分配哈希。
- V11 创意模板升级为 `effect-prompt-v11-coherent-creative-v2`。模板明确每个 task 独立生成一个创意主线，先创作正文，再用六维概括同一画面。
- Ark 创意请求不再发送完整 `application.usable`，只发送逐条轻量事实简报和一段共用提示词正文。
- Provider 改为拒绝未分配事实、漏用主要事实或漏用产品锚点的响应；旧 V11 分片在恢复时通过兼容分配器补齐内部事实任务，不伪造公共结果字段。
- Mock Provider 同步遵守事实分配，保证自动测试不会绕过生产约束。

实际验证：

```text

mypy src：通过
Ruff src/tests：通过
```

自动验证阶段未调用 Ark 或 Seedance。随后在用户单独授权下执行了一次真实 Ark 创意分片冒烟：

```text

4 条结果均引用了各自分配的主要事实和至少一个产品锚点，没有跨任务引用事实，证明“Worker 先选事实、模型再创作”的结构可以被真实模型执行。该冒烟没有调用独立评估模型，也没有运行 50 条整批，因此不能据此宣称整体质量已经完成验收。

本次真实结果同时暴露一个后续优化点：`纯猪肉无淀粉` 等已确认但难以仅靠画面直接证明的事实，仍可能诱导模型把肉质纹理写成证明性画面。下一轮应把已有 `EvidenceMode` 转为事实分配简报中的表达边界，让抽象事实只指导创意、不被伪装成肉眼可验证的证据；该问题不属于上游提炼内容真假问题。

用户随后要求执行 50 条完整付费验收。首轮真实运行已经完成 60 条候选的 15 个创意分片，但分类阶段仍沿用每片 10 条的旧配置；其中一个分类响应输入 7145 Token、输出达到 3072 Token 后以 `status=incomplete / reason=length` 截断，批次未保存结果。该失败不是超时、限流或并发过高，重复同一请求不会自然恢复。

据此完成两项修正：

- V11 创意生成与分类共用一个 Worker 级滑动并发门限，生产默认取 `PROMPT_MAX_CONCURRENCY=6`；即使图一次规划 15 个分片，也只会同时调用 6 次 Ark，任一完成后立即补入下一个。
- 分类分片从每片最多 10 条收窄为 5 条，降低单次输入和结构化输出长度；节点间仍等待本轮全部分类分片完成后再统一择优。

以上修正先通过 Mock 并发与分片回归后才能再次执行付费批次。失败运行没有写入页面领域结果或 WorkingArtifact。

## 7. 50 条真实付费验收结果

在用户明确授权后，使用当前已提交且为 CURRENT 的“广式腊肠”营销洞察执行了一次目标为 50 条、统一 15 秒的真实 Ark 验收。验收使用独立的本地文件检查点和 trigram 去重，不调用 Seedance，也不调用“完成校验”接口，因此没有覆盖 Prompt 领域草稿或 `prompt-batch:{productId}` WorkingArtifact。

恢复测试过程中又发现并修正了两个实现问题：

- 旧逻辑只对“尚未评估的候选”重新从 `0` 编号分类分片；中途失败后会让新分片键覆盖之前成功的分片。现在始终按本轮全部候选的稳定顺序切片，只重新执行包含缺失候选的固定分片，并增加了“首轮分类失败、第二次恢复全部 12 条”的回归测试。
- Ark 的 `max_output_tokens` 同时包含结构化回答和推理 Token。5 条分类在 2600 Token 动态上限附近仍可能截断，因此分类默认上限调整为 4096，单批动态预算调整为每条 720 Token、最低 1536 Token。

```

本次可恢复验收累计记录 29 次 Ark 调用，其中创意生成 15 次、分类 14 次。分类比正常的 12 次多出 2 次，来自一次无效 JSON 和一次输出截断后的恢复验证；所有 Provider 调用自身重试次数均为 1。累计输入 / 输出 / 总 Token 为 `99762 / 49878 / 149640`。该调用数是本次故障恢复验收成本，不代表无故障生产批次的固定调用数。

模型评估均值为：产品相关性 97.96、创意连贯性 92.32、画面可执行性 93.00、商业素材价值 87.42、视觉表达清晰度 94.38。以上分数仅代表当前评估器口径，不能替代人工质量判断。

人工抽查确认“任务过重”的第一阶段改造有效：50 条都绑定产品名称，核心卖点绑定 15 次、次要卖点 19 次、购买场景 10 次、决策驱动 10 次、使用场景 9 次、痛点 6 次；没有再次出现书桌、长椅、通用遮挡等与商品无关的画面。正文和六维组合均无完全重复。

本次验收也明确暴露出下一阶段质量问题，不能因为批次为 PASS 而忽略：

- `纯猪肉无淀粉` 被写成“肉纤维、不见粉面感”等肉眼证明，`广府糖酒腌制工艺` 被写成通过表面光泽直接证明，抽象事实和可见证据的边界仍不够严格。
- 主用途分布为产品展示 33、卖点讲解 12、痛点 4、钩子 1；这符合 V11 不设六类配额的规则，但说明当前创意容易收敛到厨房切片和产品特写，营销素材结构仍偏单一。
- 评估器把自然语言建议直接作为 warning code，导致统计项碎片化；应在后续改为有限的稳定问题码，说明文字单独保存。

因此，本轮结论是：事实选择拆分、商品关联、精确数量、滑动并发及失败恢复已经完成真实验证；“抽象事实如何安全指导画面”和“在不恢复六类硬配额的前提下提高叙事用途多样性”仍是下一轮优化项。本轮没有虚构这些问题已经解决。

## 8. V6 队列入口与分片格式异常恢复修正

页面曾出现 V11 工作流全部节点长期停留“等待中”。真实链路确认 API 已创建 V6 Run 并发布消息，但 Worker 的 `PromptGenerationRequest` 队列信封仍限制为 `schemaVersion=5`，消息在 claim 前被拒绝，导致 RabbitMQ 已无消息、Run 仍为 QUEUED。

修正内容：

- Worker 队列信封同时兼容 V5/V6，新消息默认 V6；V5 历史消息继续可读。
- API 定时恢复超过 60 秒仍为 QUEUED、且 Outbox 已为 PUBLISHED 的任务，将其原 Outbox 恢复为 PENDING 重新投递，避免消息丢失后永久等待。
- V11 创意和评估分片遇到一次 `status=completed` 但 JSON 格式不完整时，只在该分片内部额外调用一次，不立即重跑整个批次。
- 并行分片仍失败时主动取消同批尚未完成的请求，避免旧 attempt 在新 attempt 启动后继续产生费用和 409 回写。

修复后恢复原 Run `54c8d18e-7885-41c8-a993-0aff90207548`，最终真实结果：
