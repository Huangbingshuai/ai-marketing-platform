# 时间轴末端跟随内容延伸

## 范围

- 音频、字幕片段可以自由向右拖到「所有素材末尾」的右边任意远，不再被拦截。
- 成片时长 = 全部内容末端的最远值（视频、分离原声、口播、纯音乐、字幕）。
- 播放针走到没有视频素材的位置直接黑屏，音频 / 字幕继续。
- **导出的成片同样变长**：尾部黑屏、音频 / 字幕完整（用户已确认）。

## 现状问题

- 拦截点在前端时间轴：`EffectTemplateMixTimeline.vue` 的 `timelineDuration` 只算 `props.duration` + 视频槽位末端，`canvasWidth` 跟着它 → 画布不涨、音频拖动的 `maxStart` 被 `timelineDuration - initialDuration` 夹死。视频拖动本来就无上界，所以只有音频和字幕被拦。
- `captionBounds` 把最后一条字幕的 `maxEnd` 设成 `timelineDuration.value`，同样被视频时长夹住。
- 后端也是视频时长：contracts 的 `packagingTimelineDuration(variant)` 只算「有素材的视频槽位」。它同时是 worker 的渲染时长、`packagingSnapshot.duration`、以及 `validatePackagingCheckpoint` 里 `interval()` 的上界 → 越过视频末尾的内容会被后端拒绝，渲染也会被截断。
- 组拖还有一条独立的右侧夹取（`Math.min(Math.max(delta, -earliest), timelineDuration.value - latest)`），单条放开后组拖仍被拦。

## 调研结论（决定了下面的设计）

1. **worker 不用改**：`packaging_media.visible_intervals` 已经对空隙输出 `clip=None`，`final_output.py` 把它渲染成 `color=c=black`，输出时长只由 `timeline['duration']` 决定。所以只要把 duration 算大，尾部自动是黑屏 + 音频继续。
2. **`packagingTimelineDuration` 必须保持不变**：它的语义是「视觉时间轴长度」，还被 `timeline-project` 的 `durationSeconds` 元数据用着，改它会污染那个 artifact 的元数据。新增一个 helper 而不是改它。
3. **分离原声 / 口播 / 字幕的越界校验不能拿内容末端当上界**：内容末端本身包含被校验的片段（最大值就是它自己），拿它当上界等于恒真。诚实的上界只剩 3600 容量上限。
4. **`stale` 不能动**：`stale` 会 gate 住 `editPackagingAudio`，拖动后翻它等于立刻把用户锁住，与需求相反。而且 final-output 的 `inputHash` 本来就由 checkpoint 参与计算，用户再点「完成校验」就会重新渲染。
5. **`effect-packaging.domain.ts:400` 的槽位围栏没有 `edited` 守卫**：它同时作用于编辑写入路径，不放开口播拖不过槽位末尾；字幕的 `:471` / `:475` / `:477` 同理。

## 设计

### 1. contracts 新增 helper（不动 `packagingTimelineDuration`）

`packages/contracts/src/effect-template-mix-packaging.ts` 新增并导出：

```
effectTemplateMixContentDuration(variant, checkpoint?) =
  max(有素材视频槽位末端,
      detachedAudios[].start + duration,
      checkpoint 传入时：voices[].start + duration, music.start + duration, captions[].end)
```

字幕取 checkpoint 优先、草稿兜底（与编辑页一致）。另有 `EFFECT_TEMPLATE_MIX_MAX_CONTENT_SECONDS = 3600`：长度跟随内容之后，这是唯一剩下的边界，防止一次误拖要求渲染一个无界任务。

### 2. 后端

- `effect-packaging.domain.ts`
  - `packagingSnapshot` 的容量守卫改用 `effectTemplateMixContentDuration(variant)`；分离原声的 `start + duration` 上界从 `timelineDuration` 改为容量上限（`duration: timelineDuration` 保持视频语义不变）。
  - 新增 `contentInterval(start, end)`：有限、`start >= 0`、`end > start`、`end <= 3600.001`；用于 checkpoint 的 `voices` / `music` / `captions`。`interval()` 保留给槽位绑定的 `vision` / `script`。
  - 槽位围栏加 `!edited`：`voices` 的 `slotLayout` 围栏、字幕的 `!segmentedCaptions` / `segmentedCaptions` / `slotLayout` 三条围栏只在 worker 写入路径生效。worker 路径仍然严格（`edited = false`），管线产物不会漂移。
- `effect-final-output.service.ts`：`timeline.duration` 与 `timeline-package` 的 `duration` 改用 `effectTemplateMixContentDuration(variant, checkpoint)`，旁边加 3600 守卫。
- 不改 `stale`，不加 Prisma 迁移。

### 3. 前端时间轴 `EffectTemplateMixTimeline.vue`

- 引入 helper；`timelineDuration` 加上 helper 结果，并新增 `draggedAudioEnd`（音频与字幕拖动共用同一个 `audioDrag`，所以一条就够）。
- 音频 MOVE 夹取去掉 `timelineDuration - initialDuration`，保留 `drag.maxEnd - initialDuration`（真实素材上界）；右裁剪同理去掉 `timelineDuration - initialStart`；组拖去掉 `timelineDuration.value - latest`。
- `captionBounds`：最后一条字幕的 `maxEnd` → `Number.POSITIVE_INFINITY`，前面几条的相邻围栏保留。
- `canvasWidth` 跟着 `timelineDuration` 自动变长，拖动时的自动滚动随之生效。

### 4. 前端编辑页 `EffectTemplateMixNodePage.vue`

- `currentDuration` = `max(variantDuration(variant), effectTemplateMixContentDuration(variant, selectedPackaging.value?.checkpoint))` → 播放针上界、seek、播放停止点、`:duration` 全部跟着变长。
- 音乐素材拖入的时间夹取从 `currentDuration` 放宽到内容末端。
- 黑屏无需改动：`previewSlot` 越界返回 null，模板已经有 `player-blackout`。

## 非目标

- 不改包装 Worker 的配音、音乐生成方式和成片输出契约（只改传进去的 `duration`）。
- 不改 `stale` 语义：换行 / 拖动不翻 `stale`，是否重出片仍由「完成校验」决定。
- 不做存量迁移：已确认工程的 `snapshot.duration` 是冻结 JSON，不会重算。

## 验收

- 拖音频 / 字幕 / 视频到所有素材末尾右边任意远：不拦截，时间轴与刻度延伸，松手后停在那里。
- 播放针走过最后一个视频素材：黑屏，音频 / 字幕继续。
- 成片时长 = 内容最远端；导出后尾部黑屏且音频完整。
- 相关单测与类型检查通过（对比既有失败集合只少不多）。

## 风险

- **分离原声会触发重新包装**：`detachedAudios` 在 `packagingVisualTimeline` 里，拖它越过视频末尾会改 `visualHash` → 需要走「完成校验」重新出片。这是既有语义。
- **口播越界只在编辑路径放开**：worker 写入路径（`edited = false`）仍然要求口播线落在槽位内、字幕贴合其配音，管线产物保持规范。

## 后续：两个上报缺陷（2026-09-24 18:00 前后）

用户实测后报了两个「每次都出现」的提示，各自根因不同，都已在本次修掉。

### 1. 「包装结果结构、来源或时间边界无效」（400）

来源唯一：`effect-packaging.domain.ts` 的 `fail()`。编辑路径是 `updateAudio` → `validatePackagingCheckpoint(snapshot, next, true, true)`，`edited = true`。放开末端之后仍有三类围栏**没有 `!edited` 守卫**，于是任何离开管线位置的拖动都被拒：

- 口播槽位围栏（原 `slotLayout && (audio.start < line.start || audio.start + audio.duration > limit)`）：向右拖出口播槽位末尾、或向左拖到槽位起点之前即被拒。
- 字幕 V2/V3 相邻卡片围栏（`captionsV2 && parts.some(... Math.abs(part.start - parts[index - 1].end) > 0.001)`）：管线把一句拆成卡片时首尾相接，编辑把其中一张拖走就开了缝，被当成破坏结构。
- 字幕贴合其配音围栏（`!segmentedCaptions && (c.start !== audio.start || ...)`）、字幕落在分段内围栏（`segmentedCaptions && (c.start < audio.start || c.end > ...)`）、字幕落在槽位内围栏（`slotLayout && (c.start < script.start || c.end > script.end)`）。

全部加上 `!edited &&`：worker 写入路径（`edited = false`）仍然严格，管线产物不漂移；编辑路径只保留形状与 `contentInterval`（`0 <= start`、`end <= 3600.001`）检查。

**另一处独立缺陷**：`validatePackagingCheckpoint` 的**允许键白名单**（`Object.keys(checkpoint).some(k => ![...].includes(k)) → fail()`）漏了 `captionVoices`。只要 checkpoint 带这个键（`effect-packaging.service.ts` 生成字幕口播后就会写入），**任何一次校验都直接 `fail()`**，报的就是这句话。已补上。实测证据（临时删掉该键后重跑 domain spec）：

```
× accepts an editor-generated caption narration without giving it a script line
× keeps a generated caption narration through a component redo and rejects forged entries
AssertionError: expected [Function] to not throw an error but
  'BadRequestException: 包装结果结构、来源或时间边界无效' was thrown
```

### 2. 「节点内容已在其他页面更新，请刷新后重试」（409）

来源唯一：`workflow-working.service.ts:230`，即 `PUT /draft` 的 `expectedRevision !== current.revision`（`workflow-working.repository.ts:258`）。只有 `TEMPLATE_MIX` 节点的写入才会冲突，而它的写入方只有 `PUT /draft` 与 `POST /empty-variants` / `apply-variant`（后两者 web 端都会 `installWorkspaceData` 装回新 revision）。GET 也会返回真实 revision，所以客户端手里的 revision 不会凭空的旧。

剩下的一种：**两次 `PUT /draft` 并发、带同一个 revision**。`scheduleSave()` 只是 `clearTimeout` + 重新起 450ms 定时器，`persist()` 之间**没有任何串行化**——一次保存还在路上时定时器再响，第二个请求仍带着旧 revision，而它的内容已经变了，服务端于是判冲突。拖拽天然会触发：拖动中不断 `bump()` 重置定时器，松手 450ms 后开始保存，用户接着拖 → 又 450ms → 第二次保存与第一次重叠。草稿里有 101 个成片工程时一次 PUT 超过 450ms 很常见，所以表现为「每次」。

修法：`persist()` 串行化（`EffectTemplateMixNodePage.vue`），与 `EffectImportNodePage.vue` 已有的 `writeQueue` 同一思路。

```ts
const persist = (keepalive = false): Promise<boolean> => {
  clearTimeout(saveTimer);
  const previous = pendingSave ?? Promise.resolve(true);
  const next = previous.then(
    () => persistNow(keepalive),
    () => persistNow(keepalive),
  );
  pendingSave = next;
  return next;
};
```

链式等待也让每个请求读到上一个请求返回的新 revision；`flushPendingEdits()` 仍 `await pendingSave`，语义不变。
