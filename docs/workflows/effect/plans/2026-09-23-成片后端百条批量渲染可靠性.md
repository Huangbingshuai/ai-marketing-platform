# 成片后端百条批量渲染可靠性

## 范围

沿用第六步既有的按模板 `EffectFinalOutputRun`、每条 `EffectFinalOutputItem`、Outbox、租约和 FFmpeg 合成链路。渲染输入只取该模板已确认的视觉、包装和文件依赖；用户点击“导出成片”时冻结分辨率与帧率。输出继续逐条归档到 `final-video:<templateId>:<variantId>` 和项目成片资产。

本次改善最多 100 条成片在同一个消息内的长时间运行：消息在 API 成功领取并持久化租约后确认，Worker 中断由租约过期恢复；实际 FFmpeg 并发可配置且有上限；运行时继续逐条保存、跳过已成功成片。修正截取和渲染时长校验使用所选帧率，并确保分离音轨的源文件在依赖校验和下载集合中。

`FINAL_OUTPUT_MAX_CONCURRENCY` 默认为 2，可设 1–4；4K 批次强制最多 1 条。每个 FFmpeg 进程限制编码和滤镜线程数为 1，实际 CPU、内存和临时盘消耗仍需在部署机器上测量。

## 非目标与数据接口

不替换现有 FFmpeg 滤镜图，不引入新的任务表、队列、供应商或跨层 DTO。保留当前 480p、720p、1080p、2K、4K 和 24、25、30、50、60 fps 枚举。内部 API 的 claim、heartbeat、逐条 progress/upload、finish 不改形状；失败恢复沿用已有租约扫描和队列投递。

## 迁移与验证

无数据库迁移。验证 100 条任务的并发上界和完成补位、消息确认与租约恢复边界、取消后停止、成功项跳过、分辨率/帧率及分离音轨校验。运行 Worker 聚焦测试、Python 类型检查、API 聚焦测试与类型检查、`git diff --check`。本地合成测试仅用合成素材，不调用付费供应商；实际 4K 吞吐需部署环境压测。

## 本地验证记录

- Worker 成片输出测试（含真实本地 FFmpeg 转场和 100 条模拟调度）及 Consumer 测试通过；Python mypy 通过。
- API 成片输出 Service 聚焦测试与类型检查通过，Compose 配置校验和 `git diff --check` 通过。
- 未连接真实商品素材、对象存储或付费供应商执行 100 条真实 4K 压测，实际吞吐、内存和磁盘峰值仍取决于部署机器。

## 六槽位成片复核（2026-09-23）

模板混剪确认的是同一模板下多条相互独立的时间轴工程，每条通常有六个 4–15 秒槽位；包装工作副本为每个槽位保存一条口播及分段字幕，另有整片配乐，视频源的自然声可拆成独立音轨。第六步的一个 Item 对应其中一条工程，并非将模板的 100 条工程拼成一条长片。

新增 API 包装结构用例，验证六槽位、分段字幕、逐槽口播和分离源音频能够通过完成门禁；新增 Worker 本地 FFmpeg 用例，用 24 和 60 fps 合成完整六槽位 H.264/AAC 成片并检查时长、编码、输出帧率和分离自然声是否仍进入最终混音。两层用例均通过。已有逐转场合成用例仍覆盖各 FFmpeg 转场映射。

这些本地用例不能证明所有用户源素材与浏览器预览像素一致。翻页、立方体、故障等效果目前仍使用 FFmpeg 近似映射；部署前还需以真实模板素材检查画面、声音、字幕和 4K 性能。
