# 渲染批次「完成校验」并发冲突 500 修复

## 范围

- 只改视频渲染节点 `POST /batches/:batchId/validate` 的提交事务：给它一个显式的超时预算、对瞬时锁冲突做一次有界重试，重试仍失败时返回 409 可重试提示，而不是裸的 500「服务器内部错误」。
- 不改 `validate()` 的校验项、不改 `commitValidatedBatch` 的判定逻辑、不改前端、不加 Prisma 迁移。
- 附带一处可观测性补丁：`HttpExceptionFilter` 对非 `HttpException` 的 500 补一条带堆栈的日志（本次排查全程被它挡住）。

## 现状问题

用户报：「渲染节点无法完成校验，直接报服务器内部错误」。

复现（2026-09-25 04:53，直连本机 API `localhost:3100`，项目 `40d1273a-e1cd-4cae-8f83-02fdaf324dc1`，批次 `d689b4bc-6942-4716-aacd-049463c1da44`）：

| 施加条件 | 结果 |
| --- | --- |
| 无竞争 | `HTTP 201 valid:true`，`total=0.15s` |
| 另一会话持有该批次行锁约 4 秒 | `HTTP 201 valid:true`，`total=4.27s`（等锁后成功） |
| 另一会话持有该批次行锁约 20 秒 | **`HTTP 500`**，`{"message":"服务器内部错误","code":"INTERNAL_ERROR","requestId":"bd133bbd-…"}`，`total=29.03s` |

持锁方式（只加锁不改数据，结束即 `ROLLBACK`）：

```sql
BEGIN;
SELECT id FROM effect_segment_render_batches WHERE id = '<batchId>' FOR UPDATE;
SELECT pg_sleep(20);
ROLLBACK;
```

即：**只要提交事务在等行锁时超过约 5 秒，就必然 500**，且用户看到的是一句无信息量的「服务器内部错误」。用户那次点击就是撞在这个窗口上（同一进程 04:44:57 启动、含 stale 死锁修复，04:44–04:48 之间点击失败，04:48:59 我手动调用同一接口即成功）。

## 根因

`effect-segment-render.repository.ts` 的 `commitValidatedBatch()`：

```ts
return this.prisma.$transaction(async (transaction) => { … });
```

没有传第二参数，于是吃 Prisma 的默认值（`apps/api/src/generated/prisma/internal/prismaNamespace.ts:5284`）：

```
maxWait ?= 2000   // 从连接池取连接的等待上限
timeout ?= 5000   // 交互式事务的总时长上限
```

这个事务要写 101 个产物（100 条 `render-clip:*` + 1 条 `render-batch:*`），每个都要跨 `working_artifacts` / `working_artifact_file` / `working_artifact_dependency` / `file_objects` 四张表读写，并在开头 `SELECT … FOR UPDATE` 锁住批次行。任何并发写者（另一页面的草稿提交、返修决策、单条重新渲染、第二个校验请求）持有所涉行锁时，本事务就会卡在锁等待上；一旦总时长越过 5 秒，Prisma 判定事务过期并抛错，该错误不是 `HttpException`，被 `http-exception.filter.ts:64-71` 兜成

```
500 服务器内部错误 / INTERNAL_ERROR
```

前端 `EffectSegmentRenderNodePage.vue:1560` 的 `catch` 原样显示这句，用户既不知道是并发冲突，也不知道重试就能好。实测 4.27s 那次成功、29.03s 那次失败，正好卡在 5 秒阈值两侧。

旁证：`commitValidatedBatch` 是所有渲染节点事务里唯一需要一次性写上百行的一个（其余事务最多改一条批次或一条任务），所以只有它会被这个默认值卡住。

## 设计

### 1. 提交事务显式给预算 + 有界重试（`effect-segment-render.repository.ts`）

```ts
// The validate commit writes every clip artifact plus the batch artifact — a hundred rows across four
// tables — and it takes a row lock on the batch first, so any concurrent writer can park it in lock
// waiting. Prisma's 5s default budget then aborts the transaction, and the abort surfaced as a bare
// 500 "服务器内部错误": the user could not tell a transient clash from a broken server. Give it a
// realistic budget and one retry, then report it as the conflict it is.
const COMMIT_TRANSACTION_OPTIONS = { maxWait: 10_000, timeout: 20_000 };
const COMMIT_TRANSACTION_ATTEMPTS = 2;
```

- `isTransientTransactionError(error)`：识别 `P2028`（事务过期）/`P2034`（写冲突或死锁）以及消息里含 `deadlock` / `could not serialize` / `Transaction already closed` / `Transaction API error` 的错误。
- 重试 `COMMIT_TRANSACTION_ATTEMPTS` 次，间隔 200ms；非瞬时错误立即抛出（不掩盖真 bug）。
- 重试用尽 → 返回新的 `{ kind: 'CONFLICT' }`，让服务层决定文案。
- 重试是安全的：`commitValidatedBatch` 幂等（内容哈希未变时 `unchanged: true`），且每次重试都重新做 `FOR UPDATE` + `revision` 复核。

### 2. 服务层把 CONFLICT 映射成 409（`effect-segment-render.service.ts`）

```ts
if (result.kind === 'CONFLICT') throw conflict('校验提交遇到并发写入，请稍后重试');
```

放在既有 `REVISION_CONFLICT` / `PROMPT_CONFLICT` / `SOURCE_CONFLICT` / `NOT_READY` / `NOT_FOUND` 旁边。前端 `validateBatch` 的 `catch` 会把这句显示出来，用户知道该重试而不是以为服务坏了。

### 3. 500 可诊断（`apps/api/src/common/http-exception.filter.ts`）

```ts
if (!(exception instanceof HttpException)) {
  new Logger(HttpExceptionFilter.name).error(exception instanceof Error ? exception.stack : String(exception));
}
```

现状是该 filter 对非 `HttpException` 既不记录也不透出堆栈（Nest 的默认 `ExceptionsHandler` 被它接管），所以这次 500 在终端里查不到任何痕迹，只能靠加锁复现反推。补上这一条后，再出现 500 就能直接看堆栈。

## 非目标

- 不缩短提交事务（101 个产物必须一起提交，拆开会让「批次已提交」出现中间态）。
- 不改 `validate()` 的校验项与 `commitValidatedBatch` 的判定顺序。
- 不给其它事务加同样的重试（`start` / `regenerate` / `export` 都只改单行，不在本次复现范围内）。
- 不改前端（409 文案走既有的 `safeMessage` 显示路径）。
- 不加 Prisma 迁移、不写存量数据。

## 验收

- 提交期间另一会话持有该批次行锁 8 秒：`validate` 仍返回 `201 valid:true`（等锁后成功），不再 500。
- 并发冲突持续到重试用尽：返回 `409` +「校验提交遇到并发写入，请稍后重试」，不是 500。
- 非瞬时错误（如 `NOT_FOUND`）不被重试、不被吞。
- 无竞争时行为与耗时不变（`201`，`~0.2s`）。
- 新增/既有单测与类型检查通过（对比既有失败集合只少不多）。

## 风险

- **超时变长**：`timeout` 从 5s 提到 20s，最坏情况下用户要多等 20s 才拿到 409；换来的是 5–20s 之间的等待能直接成功。重试只有 1 次，最坏总时长约 40s（此前是 29s 后 500）。
- **重试掩盖真实写冲突**：只在识别到瞬时错误码/消息时重试，其它错误照旧抛出；重试也只在 `revision` 复核通过时才会继续写。
- **filter 加日志**：`common/` 目前没有 spec，改动无测试覆盖，但只加一条 `Logger.error`，不改状态码与响应体。
- **并行会话**：本机 API 跑在 `nest start --watch`（PID 42564 → 8724）上，改 `apps/api/src` 会自动重建重启，验证前需确认进程已重启。

## 验证结果

实测时间 2026-09-25 04:57–05:03，本机 API 跑在 `nest start --watch` 上，改完 `apps/api/src` 后自动重建重启（`dist` mtime 04:57:54 / 04:58:17，监听进程 PID 8724 → 32612）。

### 真实错误形态（决定了 `isTransientTransactionError` 的匹配条件）

用编译后的 Prisma client 直接复现（临时探针，跑完已删）：1 秒超时的事务卡在行锁上时抛的是

```
name=PrismaClientKnownRequestError code=P2028 after=7357ms
Transaction API error: A commit cannot be executed on an expired transaction.
The timeout for this transaction was 1000 ms, however 7280 ms passed since the start of the transaction.
```

`code === 'P2028'` 与消息里的 `Transaction API error` 两条都能命中新加的判定。

### 端到端（持锁不放，只加锁不改数据）

| 施加条件 | 改前 | 改后 |
| --- | --- | --- |
| 无竞争 | `201`，`0.15s` | `201`，`0.15s` |
| 持锁约 4s | `201`，`4.27s` | — |
| 持锁约 7.6s | **`500 服务器内部错误`**（阈值 5s） | `201`，`7.58s` |
| 持锁约 50s | `500` | `201`，`50.56s` |

即用户那次点击所落的那类窗口（等锁超过 5 秒）现在不再 500。

`409 CONFLICT` 分支未能用「持锁」方式端到端触发：Prisma 判定事务过期发生在锁释放前后，重试那一次总能拿到锁并成功（上表 50s 那次就是重试成功的）。该分支由单测覆盖（见下），实际由死锁一类**当场中止**的瞬时错误触发。

### 单测与类型检查

- `npx tsc -p apps/api/tsconfig.json --noEmit` → **无输出（exit 0）**。
- `npx vitest run --maxWorkers=1 --root apps/api src/workflows/effect src/common` → **493 passed / 1 skipped**（改动前 effect 目录为 485 passed / 1 skipped，新增 4 条 + `common` 原有 1 条 + 新增 3 条 filter 用例，无回归）。
- 新增用例：
  - `effect-segment-render.repository.spec.ts` → `gives the validate commit a budget above the Prisma default and retries a transient clash`（断言第二次调用、且 `timeout > 5000`、`maxWait > 2000`）、`reports an unrecoverable clash as a conflict instead of letting it escape as an internal error`（两次 P2034 → `{kind:'CONFLICT'}`）、`does not retry or swallow a failure that is not a transient clash`（只调用一次并原样抛出）。
  - `effect-segment-render.service.spec.ts` → `reports a commit clash as a retryable conflict instead of an internal error`（`CONFLICT` → 抛「校验提交遇到并发写入，请稍后重试」）。
  - `common/http-exception.filter.spec.ts`（新建）→ HttpException 按自身状态码与文案返回且不记日志；普通 Error → `500 / 服务器内部错误 / INTERNAL_ERROR` 且 `Logger.error` 收到带堆栈的字符串。
