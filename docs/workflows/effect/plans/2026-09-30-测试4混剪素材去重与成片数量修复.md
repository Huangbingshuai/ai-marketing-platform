# 测试4混剪素材去重与成片数量修复

## 范围与已确认事实

- 测试4活动 Run 中有 40 个可用 `render-clip` 工作副本，但只对应 20 个不同的源视频 `FileObject`。智能填充把副本 ID 当成独立素材，首次任务生成 51 条成片工程；较早一次任务在归槽阶段报重复素材。
- 已有 51 条工程的原始工作副本和绑定仍存在。素材库读取必须继续展示其已绑定的 ID，不能因去重而让时间轴变空。
- 页面“模板配置或素材版本已变化”由 `needsAiFill` 汇总模板配置指纹和已绑定素材可用性；分支重挂接期间遗漏已绑定副本曾导致误报。

## 实施

1. 创建智能填充快照时按源 `FileObject` 去重，目标成片已绑定素材优先作为该文件的代表；现有工程的复用关系按文件映射到代表 ID。一个工程内仍禁止重复使用同一源文件。
2. 回调比较去重后的源文件集合及每个已选工作副本的 revision/内容哈希，避免同文件的别名数量变化误判为新增素材。
3. 已有工程保留原始素材 ID；工作台素材库继续展示所有被绑定的别名，以便旧工程可编辑。对测试4超额生成的工程仅在用户确定目标数量后做定向清理，并先核查是否有包装或导出依赖。

## 非目标与验证

- 不改变六槽位、视频画质、包装和成片输出契约；现有成片的数据清理不调用模型。
- 核查测试4现有工程绑定可解析、其他模板不受影响；执行 API 类型/构建检查与差异检查。用户后续要求付费测试后，再单独运行一次真实 AI 智能填充及相关自动测试。

## 实施记录

- 测试4异常批次实际读取了 40 个 `render-clip` 工作副本，只有 20 个不同 `FileObject`。按真实文件重新计算，现有归槽与截取结果最多组成 4 条符合六槽位去重规则的工程。
- 测试4没有包装任务、导出任务或成片资产依赖；保留前四条工程身份，清理多出的 47 条时间轴工作副本，并用同批已有 AI 结果修正第一条工程的一处重复源文件槽位。修复前的草稿已备份到系统临时目录。
- 修复后测试4草稿和版本树均为 4 条，24 个槽位全部可读取、revision/截取区间有效、每条的六个源文件互异，`needsAiFill=false`；测试1仍为 4 条，测试2仍为 4 条。
- API 素材库继续提供旧工程已绑定的副本 ID 以便时间轴解析；前端可选择素材按物理文件去重，归槽池按 20 个不同文件显示。
- 用户授权后，对测试4成片01发起真实付费重新智能填充：任务 `5f3b2d69-de52-456b-8e78-3ee5b8e4abbe`，输入快照 20 个真实源文件，单次尝试完成；新分支 `5271351e-5a1d-4057-8041-7f32d834e390` 已发布，仍有 4 条工程和 24 个有效槽位绑定，每条成片内 6 个源文件互异。原分支保持活动，revision 仍为 69；测试3分支数为 0，测试1、测试2及测试4模板仍在。
- 任务排队 196 秒，实际执行 23 秒。排队原因是旧 Worker 曾让租约心跳异常从 `finally` 逸出，消息未确认并占满队列预取窗口；重启 Worker 后任务立即执行。修复心跳清理，使其异常不阻断消息确认，并补充回归测试。更新容器镜像后队列待消费、未确认消息均为 0。
- 再从原分支发起完整批量付费测试：任务 `052d9b31-404f-47a0-941e-bed801d8b380`，排队 2 秒、执行 55 秒，一次成功。去重输入 20 个源文件，新生成 4 条工程；测试子分支 `20785faa-26aa-426b-bcaf-ab80b3699fda` 保留原有 4 条，因此共 8 条。48 个槽位均能映射到真实文件，每条六个源文件互异。该子分支未设为活动分支，原用户工作分支未切换。
