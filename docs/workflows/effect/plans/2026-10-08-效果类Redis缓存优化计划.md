# 效果类工作流 Redis 缓存优化

状态：已实施，2026-10-08 本地验证。覆盖效果类六节点的读取评估，按实测选择可验证的只读投影；PostgreSQL 为权威状态。性能数据为开发机样本，不是生产 SLA。

## 业务边界

| 节点     | 直接上游                               | 编辑/输出边界                                              | 缓存边界                                                       |
| -------- | -------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 资料导入 | 项目资料                               | 草稿；保存版本提交 source-package                          | 草稿与资料包继续直读；共用版本目录受益于缓存，不存原始资料正文 |
| 信息提炼 | source-package 实际 revision           | 提炼草稿；保存版本提交 marketing-insight                   | 非运行中的工作区投影                                           |
| Prompt   | marketing-insight 实际 revision        | 领域草稿；完整批次成功自动提交 prompt-batch                | 工作区与按参数分页的结果                                       |
| 视频渲染 | prompt-batch 实际 revision             | 批次与片段；成功校验提交 render-batch/render-clip          | 必要发布恢复后，稳定批次展示投影                               |
| 模板混剪 | render-batch/render-clip 实际 revision | TEMPLATE_MIX 草稿；填充/包装成功原位提交模板、时间轴与包装 | 工作区、素材目录、版本树；不缓存活动任务                       |
| 成片输出 | 时间轴及包装实际 revision              | 用户导出触发合成；整批成功发布交付                         | 稳定模板交付目录；进度接口保持实时                             |

六节点均保持 projectId + workflowType + workflowRunId 隔离。独立产品、批次、分页与查询参数进一步进入键；混剪和输出是完整目录投影，模板选择/路径由权威节点 revision 和 Run 元数据共同校验。读取缓存不提交产物、不推进业务 revision、不改变下游 stale 规则。

资料导入的 `getWorkspace/getDraft` 含既有初始化与整理操作，实测正常读取只需几十毫秒，绕过它们会改变行为，因此本期不包裹这两个接口。渲染节点保留批次加载和发布恢复，缓存仅包裹其稳定展示投影。原有前端去重、缩略图/波形缓存、提炼图片结果缓存继续复用。

## 方案

1. 测量目标请求 P50/P95、响应体积；缓存运行时记录版本校验、数据库加载、Redis、编解码和等待耗时。
2. 复用 redis 客户端，集中有界连接和命令等待、断连退避、JSON 编解码及错误指标。缓存异常回退数据库。
3. 每次命中前从 PostgreSQL 读取依赖版本摘要；加载后再次核对摘要，变动期间不写缓存。只存明确允许的投影，原始资料、二进制、签名 URL 不入缓存。
4. 采用短 TTL、有界条目大小、同键请求合并和有租期的跨进程填充锁。旧键自然过期，数据库已更新但 Redis 失效失败时也不能命中旧版本。
5. 暂不采用客户端侧缓存、RedisJSON、Streams 或语义缓存。维持现有 RabbitMQ 与 PostgreSQL 的任务和持久化边界。
6. 实测 Redis 7.4.10，standalone，初始使用约 1 MB，maxmemory=0/noeviction。为 Compose 提供可配置内存上限和 allkeys-lru；生产需按工作集与容器预算配置。

## 已实现结构与一致性

- [共享缓存模块](../../../../apps/api/src/platform/cache/redis-cache.module.ts)：同一个 Redis 连接供只读投影与原有任务进度缓存使用，禁用离线队列，默认连接/命令等待 150 ms；失败后冷却 5 秒，前台访问不延长冷却期。
- [版本摘要](../../../../apps/api/src/platform/cache/effect-cache-revision.service.ts)：每次读取先检查项目和效果类 Run；按资源清单，在一条 SQL 中汇总依赖行的 ID、业务 revision 和 PostgreSQL `xmin`。摘要覆盖新增、修改和删除，不下载大型产物正文。`xmin` 只作短期物理变化标记，不作为业务版本或排序依据。
- Run 元数据在数据库内计算内容摘要；普通导航的 `lastActiveAt/updatedAt` 不参与摘要。只有版本树展示 `currentNodeId`，其他业务投影排除该纯导航字段。草稿 revision、分支发布、父子路径、模板路径、编辑隔离字段和当前 Run 指针始终参与校验。
- 依赖清单包含同项目祖先/兄弟 Run，因为模板目录可能继承其他路径。当前实现采用保守的项目范围摘要；兄弟模板更新可能使整个目录失效，但不会把兄弟数据混入当前模板。相关依赖表存在活动任务时直接绕过缓存。
- [cache-aside 实现](../../../../apps/api/src/platform/cache/effect-read-cache.service.ts)：键为命名空间、projectId、EFFECT、解析后的 workflowRunId、资源、参数摘要、依赖版本；填充前后均核对权威版本。已完成写入之后发起的新读取不能命中旧版本；与保存重叠的旧请求仍受现有前端请求隔离规则约束。
- 同进程相同键合并加载，并为每个调用者返回独立 DTO；跨进程用 `SET NX PX` 建立 30 秒填充租期，最多等待 3 × 25 ms 后自行读数据库。Lua 只释放自己的锁。锁被淘汰或持有者崩溃最多造成重复读取，不决定业务成功与否。
- 默认 TTL 300 秒，附加 ±10% 抖动；响应体上限 2 MiB，过大或包含签名参数的响应不写缓存。JSON 信封记录版本和校验和，损坏、超时、断连、无法验证版本均回退数据库。所有普通条目和填充锁都有过期时间。
- 根据实测增加快速读取保护：原加载器耗时低于 50 ms 时不填充 Redis，后续同作用域请求直接走原加载器。进程内仅保留最多 256 个、60 秒有效的性能提示，不保存业务内容；任一直接读取变慢便撤销提示，下一次可再次填充共享缓存。首次测量仍有版本查询和 Redis 探测成本；跨进程冷启动会重新测量。
- 没有新增公共 API、Contracts 字段、数据库表或业务状态；已有文件/Worker 内容接口的 `private, no-store` 保持不变。实测本次工作区 JSON 读取端点原本没有显式 `Cache-Control`，本次没有新增浏览器或代理缓存。

## 配置、观测与回退

`.env.example` 已增加：

| 配置                          | 默认值             | 用途                                 |
| ----------------------------- | ------------------ | ------------------------------------ |
| EFFECT_READ_CACHE_ENABLED     | true               | false 后重启 API 可退回原读取路径    |
| EFFECT_READ_CACHE_TIMEOUT_MS  | 150                | Redis 连接与操作等待预算，毫秒       |
| EFFECT_READ_CACHE_TTL_SECONDS | 300                | TTL 基准秒数                         |
| EFFECT_READ_CACHE_MAX_BYTES   | 2097152            | 序列化响应体上限                     |
| EFFECT_READ_CACHE_MIN_LOAD_MS | 50                 | 原加载器低于此耗时则后续直接读数据库 |
| EFFECT_READ_CACHE_NAMESPACE   | amp:effect-read:v1 | 投影格式不兼容升级时更换命名空间     |
| EFFECT_READ_CACHE_LOG_METRICS | false              | 临时打开数值指标；不记录缓存正文或键 |
| REDIS_MAXMEMORY               | 256mb              | Compose 的 Redis 工作集上限          |

缓存指标含命中/未命中/合并/绕过/快速直读/失败/版本变化/超限/敏感 URL、损坏条目数，以及总耗时、版本查询、Redis、加载、编解码、等待和响应体积。进程内仅保留最近 500 条测量。`loadMs` 是 SQL 与投影组装的墙钟耗时，不冒充纯数据库时间。

打开指标后，[PrismaService](../../../../apps/api/src/database/prisma.service.ts) 通过官方 query event 记录实际查询 duration，每 100 次输出一组数量、累计时间、P50/P95；不输出 SQL、绑定参数或结果。该统计为进程级，包含嵌套读取和并行查询，累计时间不能当作单请求耗时。

只读观测命令（仓库根目录；连接配置通过环境变量传入，不打印连接串）：

```powershell
node apps/api/scripts/inspect-effect-read-cache.mjs
$env:EFFECT_BENCH_API_URL = 'http://localhost:3100/api'
node apps/api/scripts/measure-effect-read-cache.mjs <projectId> 11
```

诊断脚本报告 Redis 版本、内存、淘汰策略、命中/未命中、过期和淘汰计数；这些是整个 Redis 实例的计数。基准脚本只调用读取接口，不触发生成或导出；资料导入 GET 仍执行既有初始化整理逻辑。

本机已无重启应用 `maxmemory=268435456` 与 `allkeys-lru`；Compose 配置保证下次按该文件重建时继续使用同样设置。验收中使用约 8 MiB、峰值约 10 MiB、淘汰 0；生产须结合实际项目数、版本数和五分钟热点工作集调整预算。队列、任务结果和业务提交仍由 RabbitMQ/PostgreSQL 承担。

### 性能测量

2026-10-08 11:44–11:45 同构建开启/关闭缓存对照，单请求串行取 11 次；首个请求独立记录，后 10 次用于重复读取 P50/P95。数据集为当前「紫苏梅子酱」，混剪响应约 765 KiB、成片目录约 23 KiB、版本树约 34 KiB。这轮包含版本摘要与数据库观测，随后基于小请求表现补上快速读取保护；热点路径不受该保护影响。

| 读取          | 无缓存重复 P50/P95（ms） | 缓存重复 P50/P95（ms） | 开启缓存后的首请求（ms） | 结论                                                      |
| ------------- | ------------------------ | ---------------------- | ------------------------ | --------------------------------------------------------- |
| 导入工作区    | 19 / 25                  | 26 / 33                | 30                       | 未缓存，差异为环境波动                                    |
| 导入草稿      | 27 / 28                  | 29 / 36                | 35                       | 未缓存，差异为环境波动                                    |
| 提炼工作区    | 21 / 33                  | 18 / 74                | 83                       | 小请求收益不稳定，增加快速读取保护                        |
| Prompt 工作区 | 31 / 36                  | 18 / 21                | 148                      | P95 降低约 42%，快速场景由保护自动绕过                    |
| 渲染展示      | 39 / 360                 | 63 / 77                | 100                      | P50 变慢，不能按单个 P95 异常值宣称收益；增加快速读取保护 |
| 混剪工作区    | 694 / 788                | 49 / 64                | 1766                     | 热读取 P95 降低约 92%                                     |
| 成片目录      | 4113 / 4443              | 21 / 26                | 4579                     | 热读取 P95 降低约 99%                                     |
| 版本树        | 2001 / 2170              | 20 / 23                | 22                       | 热读取 P95 降低约 99%；首请求已由前面的成片目录读取预热   |

冷缓存依然需要原有 SQL/投影组装，部分首请求更慢，缓存不能解决首次读取的全部耗时。这是开发机小样本、顺序采样，存在其他工作负载，不代表统计稳定的生产分位数。热点目标达到 50% 降低；小请求通过自适应绕过避免长期承担不必要的 Redis 开销。

数据库数值观测已实际输出：100 查询一组的样本 P50 约 0.9–7.2 ms、P95 约 2.4–244 ms，说明原路径仍有较重 SQL；版本摘要热读取阶段通常约 10–20 ms。后续应继续优化冷读取 SQL，不能只追求 Redis 命中率。

**最终版复测（11:53，仍为每个端点 11 次）：**

| 读取              | 重复读取 P50/P95（ms） | 指标结果                             |
| ----------------- | ---------------------- | ------------------------------------ |
| 导入工作区 / 草稿 | 20 / 24；27 / 30       | 保持直接读取                         |
| 提炼              | 20 / 34                | 11 次 fast，首次探测后直接读库       |
| Prompt            | 28 / 33                | 11 次 fast，本数据集很小             |
| 渲染              | 40 / 49                | 11 次 fast，消除先前 P50 回退        |
| 混剪              | 28 / 32                | 1 次填充，10 次命中                  |
| 成片目录          | 17 / 23                | 1 次填充，10 次命中                  |
| 版本树            | 16 / 18                | 含成片嵌套预热共 1 次填充、11 次命中 |

本轮提炼、Prompt、渲染的原加载器均低于 50 ms，所以 Redis 不保存其响应；数据集变大时会重新评估，而不是永久停用这些接入点。

### 并行工作区与上线限制

本次过程中，同工作区的项目删除任务新增了 `projects.deletionState` 等模型字段，业务库未同步时导致一次集成测试失败，期间也出现该任务服务/测试的类型不匹配。后续使用独立的 `effect_redis_accept_20261008_a1` 测试库同步当前 schema 完成缓存验收；缓存任务没有对业务库执行迁移。并行任务同步完成后，业务库已有对应字段，API 生产构建和类型检查均再次通过。部署时仍需确认目标环境模型/迁移一致，并按开发指南在无活动任务时更新 API 进程。

最终再次在已同步的本地库运行 87 项相关测试，全部通过；ESLint、Prettier、`git diff --check` 通过。独立测试库和 3110/3111 API、5180 Vite 验收进程已清理。确认生成/清理任务均为 0 后，按原 Nest watch 模式更新 3100 API；11:59:38 启动成功，12:00 对六节点主要接口复测均成功，混剪/成片/版本树重复读取分别为 45/18/15 ms（每端点仅两次，是运行生效检查，不作为新的 P95 样本）。当前代码未自动提交 Git。
