# 混剪/成片改造：移除完成校验、包装即入待渲染区、导出成功才新增分支、成片局部更新

## 目标与边界

上一轮把「隔离编辑 + 分支」扩到六个节点时，把混剪节点做成了「智能填充 → 完成校验 → 发布分支」，并让成片节点的分支在「完成校验」时固化。真机回归后用户否掉了这个模型，给出明确需求：

1. **混剪节点的「完成校验」按钮不需要，移除**。当前是「点了完成校验才把成片放进成片节点的待渲染区」，改成 **智能成片包装成功后直接进入成片节点的待渲染区**。
2. **后续成片有所改动，成片节点的成片同步更新**（待渲染条目跟着刷新，而不是报错）。
3. **成片节点「导出成片」成功（整批渲染全部完成）之后才新增分支**；再次「重新导出成片」同样新增分支。
4. **混剪节点的智能填充/重新智能填充、智能成片包装/重新智能成片包装，只要执行成功都新增分支**（用户原话：「只要执行成功都新增啊」）。
5. **成片节点已有分支、上游成片工程改动时，成片节点需要「局部更新」**：标记「需要更新」→ 用户点「局部更新」→ 只重导受影响的成片、原地覆盖、不新增分支。
6. **精修工作台（成片工程）不走编辑会话**：改的时候不进入编辑/保存/校验，**退出工作台时才判断成片节点是否需要局部更新**。

一句话：分支只由「重新生成动作成功」产生（混剪填充/包装、成片导出），成片节点对上游改动走局部更新；两个「完成校验」按钮都消失。

已确认决策（用户答复）：成片分支时点 = 整批渲染全部成功后；成片「完成校验」一并移除；混剪分支 = 智能填充/重新智能填充、智能成片包装/重新智能成片包装只要成功都新增（含首版）；局部更新 = 标记「需要更新」+ 手动点「局部更新」重导。

## 数据与接口

- 契约 `packages/contracts/src/effect-final-output.ts`：删 `CompleteEffectPackagingRequest`；加 `SyncFinalOutputRequest` / `SyncFinalOutputData`（`refreshed` / `needsUpdate`）、`LocalUpdateFinalOutputRequest`；`FinalOutputRun.counts` 增加 `stale`。
- `EffectEditBeginOptions.always`：`beginEffectEditInTransaction` 的 `if (!confirmed && !options.always) return { runId: parent.id, created: false }`。只在三处传 `{ always: true }`：`EffectTemplateMixService.createAiRun`（智能填充）、`EffectPackagingService.create`（智能成片包装）、`EffectFinalOutputService.start`（导出成片）。前四个节点保持「首版不 fork」。
- `EffectPackagingService.finish`：`repo.finish` 额外返回 `{ accepted, status, workflowRunId, templateId }`；`COMPLETED` / `PARTIAL` 时调 `finalOutput.upsertFromPackaging(...)` + `publishMixBranch(...)`，`FAILED`（零条完成）跳过；`try/catch` + `Logger.warn`，包装回调不能因草稿过期而失败。worker HTTP 契约不变（Python 侧不改）。
- `EffectFinalOutputService`：
  - `complete()` → `outputPlan()`（共享构建器）+ `upsertFromPackaging()`（新，包装回调入口）+ `publishMixBranch()`。`upsertFromPackaging` 命中既有 `PENDING_RENDER` run 时**原地刷新 item**（按 `variantId` 匹配覆盖 snapshot；草稿新增但无包装的变体静默跳过；草稿删掉的变体删 item；item 清空则删 run），否则按确定性 `idempotencyKey = auto:${workflowRunId}:${templateId}:${inputHash}` 建 run。
  - `completeOutput()` → `finalizeDelivery()`（去掉尾部发布）；`finish()` 状态事务提交后，`COMPLETED` 才 `finalizeDelivery` + `publishEditBranch(..., 'FINAL_OUTPUT')`，`PARTIAL` / `FAILED` 不提交不发布。
  - 新增 `syncFromDraft()`（退出工作台用）与 `localUpdate()`（局部更新用）；`counts.stale` 由既有 `staleForItem` 统计。
- 控制器：删 `POST /final-output/:runId/complete` 与 `POST /template-mix/templates/:templateId/complete-packaging`；加 `POST /final-output/sync`、`POST /final-output/:runId/local-update`。
- Web：混剪页删 `validateDraft` / `completionKey` / `canValidate` / `validating` 与 footer 的校验按钮（改 `:show-validate="false"`），`leaveEditor()` / `returnToFinalOutput()` 调 `syncOutputOnExit()`；成片页删 `validateOutput`，加「局部更新（N）」按钮；导入页接 `notice` 事件。

## 关键实现说明

### 分支只由「重新生成成功」产生

`always: true` 让首版也 fork，所以「智能填充成功」「智能成片包装成功」「导出成片成功」各自对应一个新 Run。发布仍由既有 `publishEditBranch` 守卫（`parentWorkflowRunId && !branchPublishedAt && editSessionNodeId === nodeId`）决定时点：混剪在 `upsertFromPackaging` 末尾发布，成片在 `finish` 的 `COMPLETED` 分支发布。`!confirmed` 时 `stageSources` 为空，0-3 阶段照常从父 Run 克隆，`editBaselineHash` 是空摘要，重新生成后摘要变化 → `createdBranch: true`，逻辑自洽。

### 局部更新按「活草稿画面 + 冻结包装」重建

`localUpdate` 逐条用当前草稿变体 + 最新 `timeline-package:` 产物重建 `snapshot`，写回 `status: 'QUEUED'` / `progress: 0`，**保留 `fileObjectId` / `assetId`**（旧成片在替换前仍可下载，与 `renderItem` 一致），run 置 `QUEUED` 并 `enqueue`，不 fork、不发布。

## 顺带修掉的两个既有问题

1. **`current()` 把冻结源文件的可用性检查按 `workflowRunId` 收窄**（`effect-final-output.service.ts`）。`always: true` 让首次导出也 fork，而分支的 `snapshot` 引用的是祖先 Run 的 FileObject（导入/包装时上传），按本 Run 过滤必然查到 0 条 → 每次导出都会 409「输出源文件不可用」。改为只按 `projectId` 过滤，与同文件的 `content()` 和 `finalizeDelivery()` 口径一致；`workflowRunId` / `templateId` 两个已无用参数一并去掉。DB 里此前没有任何 `forkNodeId = 'FINAL_OUTPUT'` 的 Run，所以这条路径从未真正跑过。

2. **`effect-final-output.database.spec.ts` 两条早已腐烂的断言**（该文件受 `EFFECT_OUTPUT_DATABASE_TEST` 门禁，长期未执行；上一份计划文档已记录它在 HEAD 上同样失败）：
   - `.rejects.toThrow('过期')`：`current()` 在 1cfdabb 已从「依赖新鲜度」改为「冻结文件 ID」，上游改动**不应该**打断进行中的渲染（漂移只作为 `stale` 在 UI 上报），断言反了。改为断言 `progress` 成功。
   - 重渲染后旧 FileObject 断言 `ORPHANED`：`commitValidatedArtifactsInTransaction` 会为上一版写 `workingArtifactRevisionFile`，孤儿守卫因此**故意**保留该 FileObject。改为断言它仍是 `AVAILABLE` 且被 revision snapshot 引用。

同时给该文件里两条重用例补了显式 `60_000` 超时（`FINAL_OUTPUT` 克隆用例在冷库上实测 8.3 s，超过 vitest 默认 5 s）。

### 单测覆盖

- `effect-final-output.service.spec.ts`（52 用例）：`finish` 全完成 → 提交 `final-delivery:` 且 `publishEffectNodeEdit(..., 'FINAL_OUTPUT')`；`PARTIAL` / `FAILED` 都不做；交付清单失败被吞掉不影响 worker 回调；`syncFromDraft` 刷新 `PENDING_RENDER` 条目、删掉草稿里已消失的变体、已导出的只报 `needsUpdate`；`localUpdate` 只重建受影响条目、置 `QUEUED`、`enqueue`、不 fork；渲染中/未导出拒绝；变体消失或改动过大 409。
- `effect-packaging.service.spec.ts`（48 用例）：`finish` 在 `COMPLETED` / `PARTIAL` 触发 `upsertFromPackaging`，`FAILED` 不触发，草稿冲突被吞掉不失败。
- `effect-template-mix.service.spec.ts`：`createAiRun` 以 `('project','run','TEMPLATE_MIX','BATCH',{ always: true })` 调 `beginEffectNodeEdit`。
- `effect-edit-session.database.spec.ts` 新增 `forks the first version of a regenerated stage when the caller asks for a branch every time`：在「以 `TEMPLATE_MIX` 为 fork 点的已发布分支」上，不传 `always` 时 `created: false` 且写回自身，传 `{ always: true }` 时 `created: true`、`parentWorkflowRunId` 非空、子 Run 有 0-3 阶段的 `render-clip:`、没有 `mix-template:` / `timeline-project:` / `timeline-package:` / `final-video:` / `final-delivery:`。
- `effect-final-output.database.spec.ts`：首版导出断言 `run.workflowRunId !== 队列所在 Run`、原队列仍为 `PENDING_RENDER`、fork 出的子 Run 各 200 条 `TEMPLATE_MIX` 产物。
- Web layout spec（单行 `toContain`，规避本机 CRLF）：混剪页去掉 `completeEffectTemplateMixPackaging` / `validateDraft` 且带 `:show-validate="false"`；退出工作台调 `syncEffectFinalOutput` 并按结果发 `notice`；成片页无 `validateOutput` / `/complete`、有「局部更新（N）」按钮与 `.local-update-button` 样式；三个批量变更动作都过 `requestActionConfirmation`。

## 风险与取舍

- **「always fork」是语义变更**（首版也建分支），仅对混剪/成片三处生效。根 Run 因此成为「未发布的父 Run」，版本树会同时显示根 Run 的混剪节点与子分支（`listEffectRunBranches` 已包含 `parentWorkflowRunId: null` 的根）。
- **`localUpdate` 与计划文档的一处偏差**：计划里写「最新包装 `matchesVisualHash` 失败 → 409 请重新执行智能成片包装」。实装改为**按当前草稿的活画面重建、保留冻结包装**，只在包装结构上装不下新画面时（`requireSlotPackaging` 失败）才 409「…的成片工程改动过大，请返回模板混剪重新执行智能成片包装后再更新」。原因：`matchesVisualHash` 比对的是「活草稿 vs 冻结的 `sourceTimelineHash`」，只要在工作台动过时间轴就必然失败，那样「局部更新」永远不可用，与需求 5 直接冲突。
- **单条「重新渲染」现在会自动重提交交付清单**（节点不再「待校验」），是移除校验的连带结果，已接受。
- **版本树不反映纯草稿改动**（只靠产物 freshness 级联）；成片页的 `item.stale` 与退出提示负责该场景。
- `finish` 里状态事务、`finalizeDelivery`、publish 各开各的事务，不合并，避免 120 s 预算被撑爆。
