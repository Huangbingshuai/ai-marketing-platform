# 混剪/成片改造：移除完成校验、包装即入待渲染区、导出成功才新增分支、成片局部更新

> **已被后续改造取代（部分）**：本文的 `always: true` 只做了「首版也 fork」，fork 出的子 Run 仍挂着 `editSessionNodeId`，于是混剪节点上出现了「编辑草稿中」横幅；同时克隆节点状态时漏了产物 id 重映射，导致包装必然失败。两者见 `2026-09-29-混剪自动分支去除编辑会话与克隆绑定修复.md`。本文其余内容（分支时点、`always` 的引入、成片局部更新、两条既有腐烂断言的修正）仍然有效。

## 目标与边界

上一轮把「隔离编辑 + 分支」扩到六个节点时，把混剪节点做成了「智能填充 → 完成校验 → 发布分支」，并让成片节点的分支在「完成校验」时固化。真机回归后用户否掉了这个模型，给出明确需求：

1. **混剪节点的「完成校验」按钮不需要，移除**。当前是「点了完成校验才把成片放进成片节点的待渲染区」，改成 **智能成片包装成功后直接进入成片节点的待渲染区**。
2. **后续成片有所改动，成片节点的成片同步更新**（待渲染条目跟着刷新，而不是报错）。
3. **成片节点「导出成片」成功（整批渲染全部完成）之后才新增分支**；再次「重新导出成片」同样新增分支。
4. **混剪节点的智能填充/重新智能填充、智能成片包装/重新智能成片包装，只要执行成功都新增分支**（用户原话：「只要执行成功都新增啊」）。
5. **成片节点已有分支、上游成片工程改动时，成片节点需要「局部更新」**：标记「需要更新」→ 用户点「局部更新」→ 只重导受影响的成片、原地覆盖、不新增分支。
6. **精修工作台（成片工程）不走编辑会话**：改的时候不进入编辑/保存/校验，**退出工作台时才判断成片节点是否需要局部更新**。

一句话：分支只由「重新生成动作成功」产生（混剪填充/包装、成片导出），成片节点对上游改动走局部更新；两个「完成校验」按钮都消失。

已确认决策（用户答复）：成片分支时点 = 整批渲染全部成功后；成片「完成校验」一并移除；混剪分支 = 智能填充/重新智能填充、智能成片包装/重新智能成片包装只要成功都新增（含首版）；局部更新 = 标记「需要更新」+ 手动点「局部更新」重导。

## 关键实现说明

### 分支只由「重新生成成功」产生

`always: true` 让首版也 fork，所以「智能填充成功」「智能成片包装成功」「导出成片成功」各自对应一个新 Run。发布仍由既有 `publishEditBranch` 守卫（`parentWorkflowRunId && !branchPublishedAt && editSessionNodeId === nodeId`）决定时点：混剪在 `upsertFromPackaging` 末尾发布，成片在 `finish` 的 `COMPLETED` 分支发布。`!confirmed` 时 `stageSources` 为空，0-3 阶段照常从父 Run 克隆，`editBaselineHash` 是空摘要，重新生成后摘要变化 → `createdBranch: true`，逻辑自洽。

### 局部更新按「活草稿画面 + 冻结包装」重建

`localUpdate` 逐条用当前草稿变体 + 最新 `timeline-package:` 产物重建 `snapshot`，写回 `status: 'QUEUED'` / `progress: 0`，**保留 `fileObjectId` / `assetId`**（旧成片在替换前仍可下载，与 `renderItem` 一致），run 置 `QUEUED` 并 `enqueue`，不 fork、不发布。

## 顺带修掉的两个既有问题

1. **`current()` 把冻结源文件的可用性检查按 `workflowRunId` 收窄**（`effect-final-output.service.ts`）。`always: true` 让首次导出也 fork，而分支的 `snapshot` 引用的是祖先 Run 的 FileObject（导入/包装时上传），按本 Run 过滤必然查到 0 条 → 每次导出都会 409「输出源文件不可用」。改为只按 `projectId` 过滤，与同文件的 `content()` 和 `finalizeDelivery()` 口径一致；`workflowRunId` / `templateId` 两个已无用参数一并去掉。DB 里此前没有任何 `forkNodeId = 'FINAL_OUTPUT'` 的 Run，所以这条路径从未真正跑过。

2. **`effect-final-output.database.spec.ts` 两条早已腐烂的断言**（该文件受 `EFFECT_OUTPUT_DATABASE_TEST` 门禁，长期未执行；上一份计划文档已记录它在 HEAD 上同样失败）：
   - `.rejects.toThrow('过期')`：`current()` 在 1cfdabb 已从「依赖新鲜度」改为「冻结文件 ID」，上游改动**不应该**打断进行中的渲染（漂移只作为 `stale` 在 UI 上报），断言反了。改为断言 `progress` 成功。
   - 重渲染后旧 FileObject 断言 `ORPHANED`：`commitValidatedArtifactsInTransaction` 会为上一版写 `workingArtifactRevisionFile`，孤儿守卫因此**故意**保留该 FileObject。改为断言它仍是 `AVAILABLE` 且被 revision snapshot 引用。

同时给该文件里两条重用例补了显式 `60_000` 超时（`FINAL_OUTPUT` 克隆用例在冷库上实测 8.3 s，超过 vitest 默认 5 s）。

## 风险与取舍

- **「always fork」是语义变更**（首版也建分支），仅对混剪/成片三处生效。根 Run 因此成为「未发布的父 Run」，版本树会同时显示根 Run 的混剪节点与子分支（`listEffectRunBranches` 已包含 `parentWorkflowRunId: null` 的根）。
- **`localUpdate` 与计划文档的一处偏差**：计划里写「最新包装 `matchesVisualHash` 失败 → 409 请重新执行智能成片包装」。实装改为**按当前草稿的活画面重建、保留冻结包装**，只在包装结构上装不下新画面时（`requireSlotPackaging` 失败）才 409「…的成片工程改动过大，请返回模板混剪重新执行智能成片包装后再更新」。原因：`matchesVisualHash` 比对的是「活草稿 vs 冻结的 `sourceTimelineHash`」，只要在工作台动过时间轴就必然失败，那样「局部更新」永远不可用，与需求 5 直接冲突。
- **单条「重新渲染」现在会自动重提交交付清单**（节点不再「待校验」），是移除校验的连带结果，已接受。
- **版本树不反映纯草稿改动**（只靠产物 freshness 级联）；成片页的 `item.stale` 与退出提示负责该场景。
- `finish` 里状态事务、`finalizeDelivery`、publish 各开各的事务，不合并，避免 120 s 预算被撑爆。

## 后续补充：每次智能填充 / 智能成片包装都被踢出精修工作台

上面「待人工回归」跑完后用户反馈：**每次智能填充或智能成片包装，页面都会刷一下、退出「成片精修工作台」回到「混剪模板」页面**，得手动刷新才能回到工作台。本次只改 `apps/web`，不碰后端。

### 根因

是上面「always fork」的连带结果，一条链子：

1. `EffectTemplateMixService.createAiRun` / `EffectPackagingService.create` 带 `{ always: true }`，**每次**重新生成都 fork 出隔离子 Run。
2. 父页面 `EffectImportNodePage.vue:1849` 给本页的 `:key` 里带着 `workflowRunId`，Run 一变，**本页被销毁重建**。
3. `view`（`'CONFIG'` 模板列表 / `'EDITOR'` 成片精修工作台）是 `<script setup>` 里的状态，随旧实例一起消失，重建后回到初始值 `'CONFIG'`。
4. 旧 `load()` 只在「草稿里有这个模板，且它有一条 `QUEUED`/`RUNNING` 的填充任务」时才把 `view` 拉回 `'EDITOR'`。**成片包装 fork 出的子 Run 里根本没有填充任务**：

```
GET /api/projects/40d1273a…/workflows/effect/template-mix?workflowRunId=3d243481-9997-47e7-abf1-46e1d43cf9d2
→ success true / aiRuns 0 / templates 1 / packagingLocked [[7ec78e67…, true, false]]
```

所以包装路径必然掉回模板列表；而包装进度条（`WorkflowRunProgress`）只渲染在 `view === 'EDITOR'` 的分支里（`EffectTemplateMixNodePage.vue:5570` 是分支门禁，`:6446` 是进度条容器），用户既被踢出工作台、又看不到自己刚启动的包装进度。

智能填充路径的 `resumedRun` 本来能恢复 `'EDITOR'`，但同样要经历整页重建。

### 改法：模块作用域的一次性交接

新建 `apps/web/src/workflows/effect/template-mix/effect-template-mix-workbench-handoff.ts`：

- `rememberWorkbench({ workflowRunId, templateId, variantId })` —— 在宣布切换分支**之前**记下「用户本来在工作台的哪个模板/哪条成片上」。
- `takeWorkbench(workflowRunId)` —— 取一次即清（无论 Run 对不对得上），避免一次没落地的切换把这份交接留到用户之后手动切到那个分支时才生效。

能跨重建活下来的只有模块作用域，所以状态放这里而不是组件里。接线三处：

- `startAiFill` 的 fork 分支、`handlePackagingRunChange`（签名改为接收包装面板 `runChange` 带出的 `workflowRunId`）在 `emit('workflowRunChange')` 前写入；
- `load()` 里在既有 `resumedRun` 判断之后取回：`resumedRun` 优先（正在跑的填充任务带的 `targetVariantId` 比交接更准），没有才用交接恢复 `view = 'EDITOR'` 与模板/成片选择。

`load()` 里加 `let workbenchHandoffPending = true`，只有重建出来的新实例的**第一次**加载才去取：旧实例（已被 `KeepAlive` 缓存、正在退场）迟到的 reload 不能把它吃掉。取交接放在 `pageState.value = 'READY'` 之后，工作区加载失败时交接不会被消费，重试仍能恢复。

## 后续补充：包装失败不该新增分支、包装版本号沿链累加

真机回归后用户反馈（同一项目 `40d1273a…`，模板「测试1」）：

> 智能成片包装直接失败了：… 1 条成片包装失败：测试1 · 1。仍可完成校验，这些成片会以无包装成片提交，仅保留画面、没有口播字幕配乐。打开包装面板恢复；**而且新增的智能成片包装版本怎么是 01 又重复了啊，而且智能成片包装失败不应该新增分支啊**

### (a) 这次包装为什么失败

| 项 | 值 |
| --- | --- |
| 包装批次 | `cf5635ba`（挂在 Run `3d243481`，模板 `7ec78e67…`） |
| 起止 | 2026-09-29 12:42:23 → 12:43:57 UTC（本地 20:42–20:43） |
| 结果 | `PARTIAL`：4 条变体里 3 条 `COMPLETED`，1 条 `FAILED` |
| 失败条目 | `798ac5a2`，变体 `b273bdd0`（「测试1 · 1」），**卡在 `VISION` 阶段** |
| 错误 | `AI 返回结构无效` |

worker 日志同一阶段连报 3 次（1 次 + 2 次自动重试）后抛 `ProviderOutputError`：

```
packaging model invalid stage=packaging_vision type=ValidationError fields=['()']
```

即**画面分析模型这三次都没吐出符合结构的 JSON**（供应商侧抖动），不是本次改造的回归：同一批的另外 3 条变体在 12:43:24–12:43:28 正常跑完，其余阶段的产物也都写入了。包装面板的「恢复失败项」会**复用同一个包装 run** 重试，所以恢复成功后不会多出一个批次。

### (b) 包装版本号又读成 01 的根因

`timeline-package:` 与 `timeline-project:` 一样，`revision` 是**每个 Run 内**自增的：fork 不克隆第 4 阶段产物，所以**每条分支的包装产物都从 1 起**。而版本树当时用的是本 Run 的本地 revision：

```ts
template.packagingRevision = sharedRevision(packages);   // 只读本 Run 的 timeline-package:
```

于是 `f12f4df6`（第一次包装）和 `3d243481`（第二次包装）**都读成版本 01**，看上去就是「又出现一个 01」。

改法与既有的 `fillChainVersion` 同构：新增 `packagingChainVersion(run, templateId)`，沿祖先链累加——每个「该模板存在 `COMPLETED` 包装批次」的祖先，贡献它本地 `timeline-package:<templateId>:` 的最大 revision（无产物的祖先贡献 0，例如改造前只置了 run 状态的 `95c92da8`）。真机数据：

| Run | 该模板的包装批次 | 本地包装产物 | 树上的包装版本 |
| --- | --- | --- | --- |
| `65f5b90c`（根） | `5ec3217a` 等，模板是旧的 `0254fafe…` | — | 1（与当前模板 id 无关） |
| `95c92da8` | `10b209be` COMPLETED | 无 | — |
| `f12f4df6` | `98359b0e` COMPLETED | 4 条 @1 | **1** |
| `6d10e9fc`（填充分支） | 无 | 无（继承父分支） | 1（继承显示） |

所以「测试1」当前只有一次真正的包装 = 版本 01；下一次包装会沿链累加成**版本 02**，不再重复。

### (c) 包装失败不再新增分支

`EffectPackagingService.finish` 原来对 `COMPLETED | PARTIAL` 都调 `publishMixBranch`，于是 `3d243481` 在 12:43:58 被**旧规则发布**成一个版本。现在：

```ts
await this.finalOutput.upsertFromPackaging(projectId, result.workflowRunId, result.templateId, {
  publish: result.status === 'COMPLETED',
});
```

- **`COMPLETED`**：照旧提交产物 + 发布混剪分支（= 新增版本）。
- **`PARTIAL`**：**只**把已成功的成片同步进成片节点的待渲染区（`upsertFromPackaging` 内的产物提交与入队照做），**不发布**。子 Run 保持 active，包装面板照常列得到这个批次，「恢复失败项」重试同一个 run；恢复完成后整批 `COMPLETED` → 同一个子 Run 发布 → 才出现版本 02。
- **`FAILED`**（零条完成）：什么都不做。

### 版本树：未完成的包装 fork 不画出来

新规则只保证「以后不再发布失败的包装」，但 `3d243481` 已经被旧规则发布过了，真机树上仍会多出一个 01。所以 `drawn()` 再加一条自愈判据：

```ts
const packagingUnfinished = (run) =>
  run.forkNodeId === 'TEMPLATE_MIX' &&
  run.workingArtifacts.some((a) => a.artifactKey.startsWith('timeline-package:')) &&
  batches.length > 0 && batches.every((batch) => batch.status !== 'COMPLETED');
const drawn = (run) => !run.parentWorkflowRunId || (Boolean(run.branchPublishedAt) && !packagingUnfinished(run));
```

- 只对**混剪节点**的 fork 生效；**没有任何包装产物**的 fork 是填充分支，不受影响；**已有整批成功**的 fork 也不会被隐藏（一个分支里两个模板、其中一批失败时，用户已经拿到的那个版本仍然留在树上）。
- 隐藏的祖先不能把链断掉：父指针改由 `nearestDrawn()` 给出最近一个「树上画得出」的祖先，active 指针同样经它回落。`listEffectRunBranches` 因此改成**读全部 Run**（含未发布），树上只画该画的。

真机对比（同一项目，改动前 → 改动后）：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 分支列表 | … `95c92da8` → `f12f4df6` → `6d10e9fc` → `3d243481` | … `f12f4df6` → `6d10e9fc`（`3d243481` 不再出现） |
| `activeWorkflowRunId` | `6d10e9fc` | `6d10e9fc` |
| 「测试1」包装版本 | `f12f4df6` = 01、`3d243481` = 01（重复） | `f12f4df6` = 01，`6d10e9fc` 继承 01，无重复节点 |

**残留影响**：`3d243481` 这次失败包装同步进待渲染区的 4 条成片（输出 run `a293e470`）挂在被隐藏的分支上，成片节点看不到。用户重新点一次「智能成片包装」即可得到版本 02（同批次另外 3 条本来就已经包装成功，重跑只影响那一条失败变体）。

### 文案：删掉「仍可完成校验」

混剪页的包装失败横幅末句由「仍可完成校验，这些成片会以无包装成片提交…」改为：

> 本次包装暂不计入版本，恢复失败项后重新包装成功才会新增分支。

`effect-packaging-progress.spec.ts` 增加 `expect(page).not.toContain('仍可完成校验')` 与新的正向断言，防止旧文案回潮。

### 单测覆盖

- `workflow-working.service.spec.ts`：`keeps an unpublished packaging child out of the tree…` 的 `partial` 夹具补上 `branchPublishedAt`，把「旧规则已发布的未完成包装 fork」钉死；新增 `keeps a packaging fork that already has a whole batch in the tree`（同分支两个模板、一批成功一批失败时，成功的版本仍在树上，active 也指得着）。
- `effect-packaging.service.spec.ts`：`upsertFromPackaging` 以 `{ publish: status === 'COMPLETED' }` 调用。
- `effect-final-output.service.spec.ts`：`{ publish: false }` 时**提交产物但不发布**。
- `effect-packaging-progress.spec.ts`：`仍可完成校验` 不再出现 + 新文案存在。

### 风险与取舍

- **`packagingUnfinished` 是自愈补丁**：长期只对两类状态生效——旧规则遗留的失败包装分支、以及「一个分支里两批包装、其中一批失败」。后者会把已经成功的那批版本暂时从树上藏起来，等失败那批恢复完成后立刻回来（数字不变）。
- **版本号按「批次」而不是「变体」累加**：同一 Run 内多个模板各自包装，共享该 Run 的最大 revision，因此一个 Run 只贡献一个数字。
- **纯草稿改动不重写产物**，版本树不亮；「需要局部更新」仍由成片页的 `item.stale` 与退出工作台时的同步负责。
- 已发布的失败分支不会自动撤销它的产物，只是不再画成版本；真机残留的那批成片需要用户重新包装一次。
