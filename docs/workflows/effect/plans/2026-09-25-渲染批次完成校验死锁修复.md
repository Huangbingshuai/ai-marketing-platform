# 渲染批次「完成校验」死锁修复

## 范围

- 只改视频渲染节点 `stale` 的判定口径：`stale` 回到「这个批次是否还在渲染当前 Prompt」，不再把渲染工作副本自身的 freshness 算进去。
- 不改 `commitStatus`、不改 `refreshScope` 的 FULL/SELECTIVE 分档、不改 `validate()` 的校验项、不改前端。

## 现状问题

用户报：「都已经重新渲染完了，还显示按最新提示词重新渲染，明显有问题」。

实测（2026-09-25，直查 `ai_marketing` 库，项目 `40d1273a-e1cd-4cae-8f83-02fdaf324dc1`，产品 `2e31a4b1-0494-4a25-ab40-93846c9c98be`）：

也就是说 **这批渲染确实用的就是最新 Prompt**，`promptTaskNeedsUpdate` 对 100 条全为假，`validate()` 的 `stalePromptCount` 为 0；source package 的 revision/hash 也和快照一致，`upstreamStale` 为假。唯一为真的只剩 `artifact.freshness !== 'CURRENT'`。

## 根因

`effect-segment-render.service.ts` 的 `present()`：

```
stale = upstreamStale || taskIdsNeedingUpdate.size > 0 || artifact?.freshness !== 'CURRENT'
```

第三项是 commit `199d36f`（2026-09-24 15:15 +0800「功能：优化成片处理并支持上游素材定向更新」）加进来的，它把一个**只能由校验提交清除**的状态当成了**必须重新渲染**的理由，于是成环：

```
render-batch 工作副本 STALE
  → stale = true
  → 前端 currentProductReady 要求 !stale → 「完成校验」按钮 disabled
  → validate() 永不执行 → 永不 commit → 工作副本永远 STALE
```

同时 `startButtonLabel` 在 `stale` 时优先给出「按最新 Prompt 重新渲染」/「仅重新生成 N 个待更新素材」，所以用户看到的就是这句话，而点下去只会再花一次 100 条 Seedance 的费用换来一份同样无法提交的结果。

旁证：`effect_segment_render_batches.committedAt` 非空的批次只到 **2026-09-15** 为止；`199d36f` 之后新建的批次只有 `d689b4bc` 一条，且 `committedAt` 为空。既有单测之所以没拦住，是因为它们把 `repository.renderArtifact` mock 成 `freshness: 'CURRENT'`，这一项在测试里从不生效。

## 设计

```ts
// "Stale" means the batch no longer renders the current Prompt — that is the only thing a rerender
// can fix, and the only thing the rerender entry points are offered for. The artifact's own
// freshness must stay out of it: the committed working copies are marked STALE *by* an upstream
// change and are made CURRENT *by* a validation commit, so folding that flag in would make every
// rerendered batch read as stale forever — validation is gated on `!stale`, so the commit that
// would clear it could never run. `commitStatus` already reports the uncommitted working copies.
const stale = Boolean(upstreamStale || taskIdsNeedingUpdate.size > 0);
```

为什么这样安全：render-batch 工作副本的依赖只有两个（`artifactInputs` 里的 `promptDependency` + `sourceDependencies`，后者只含 source package），它们各自被 `taskIdsNeedingUpdate`（Prompt 项级）与 `upstreamStale`（source package 的 id/revision/hash 与快照一致）覆盖，所以「工作副本变 STALE」的原因一个都没漏；而「已重渲染但未提交」这个状态本来就该由 `commitStatus = 'STALE'` 表达，不该由 `stale` 表达。

修复后的链路：

```
重渲染完成（任务全部匹配当前 Prompt）
  → stale = false，refreshScope = 'NONE'
  → 按钮文案回落到 hasBatch → 「重新渲染」
  → currentProductReady = true → 「完成校验」可点
  → validate() → stalePromptCount 0 → commitValidatedBatch
  → render-batch / render-clip 全部 revision+1、freshness = CURRENT
  → 混剪节点 sourceArtifacts 重新看到 100 条 CURRENT 素材
```

## 非目标

- 不改 `validate()`：它独立算 `stalePromptCount`，本来就能通过。
- 不改 `commitStatus`：`stale || artifact.freshness !== 'CURRENT'` 里保留 freshness 判断是对的，「已重渲染未提交」应当继续报 `'STALE'`。
- 不改 `refreshScope` 的 FULL/SELECTIVE 分档（`stale` 变假时它取 `'NONE'`，语义正确）。
- 不动 Prompt 失效粒度（Prompt 项 id 每次跑都会变，`SELECTIVE` 跨运行仍走不到）——用户此前明确说先不要改。
- 不改前端任何文件；不加 Prisma 迁移；不写存量数据（用户点一次「完成校验」即可自愈）。

## 验收

- 批次已按最新 Prompt 渲染完、工作副本尚未提交时：`stale === false`、`refreshScope === 'NONE'`、`commitStatus === 'STALE'`。
- 上述状态下前端「完成校验」可点，点击后 100 条 render-clip + 1 条 render-batch 变为 `CURRENT`。
- Prompt 真变更时行为不变：全量变更 → `stale`、`refreshScope='FULL'`；单条变更 → `stale`、`refreshScope='SELECTIVE'` 且只标该条 `needsUpdate`。
- source package 变更或快照缺字段时仍为 `stale`（既有用例 `keeps legacy batches readable but marks snapshots without product images as stale` 继续为真）。
- 相关单测与类型检查通过（对比既有失败集合只少不多）。

## 风险

- **`stale` 少了一个兜底项**：若将来 render-batch 工作副本新增了 prompt / source package 之外的依赖，`stale` 不会自动跟着变真。届时需要在 `upstreamStale` 或 `taskIdsNeedingUpdate` 里补上对应判断，而不是把 freshness 加回来。
- **存量死锁批次**：本机库里 `d689b4bc` 仍是未提交状态。修复上线后用户点一次「完成校验」即可，不需要迁移脚本。
- **并行会话**：工作区仍有另一会话在改前端（`EffectTemplateMixNodePage.vue` 等），本次只动 `apps/api` 两个文件，不冲突。
