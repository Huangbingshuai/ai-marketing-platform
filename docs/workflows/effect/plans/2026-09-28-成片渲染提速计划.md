# 效果类成片渲染提速计划

## 范围与基线

紫苏梅子酱项目最近一次 100 条成片完成的墙钟时间为 37 分 42.9 秒。期间 RabbitMQ 连接错误约持续 8 分 15 秒，Worker 两次中断；稳定区间吞吐约 3.9 条/分钟。因此历史墙钟时间仅作参考，不能用作受控性能基线。该批按条目累计引用约 3.04 GiB 源文件，而 Run 内去重后约 806 MiB，涉及 779 个不同文件。

本次仅优化效果类成片输出的 Worker 执行与内部计时。直接上游是已确认的 `mix-template:<templateId>`、`timeline-project:<templateId>:<variantId>` 及包装工作副本，输入 revision 与快照仍由 API 校验。输出边界仍是逐条成片上传并提交 `final-video:<templateId>:<variantId>` 与项目交付资产。无公开 API、共享契约或数据库迁移；不改变画质、分辨率、帧率、x264 `fast`、CRF 20、音视频编码和前端操作。

## 实施

1. **计时与故障隔离**：记录 API 领取排队或恢复等待、Worker 领取、下载、ffprobe、FFmpeg 编码、上传及单条总耗时；日志只含项目、Run、条目 ID、阶段、耗时、读取字节数、缓存命中数、重试次数和异常类型，不含原始内容或签名 URL。网络和 HTTP 5xx 最多重试三次，退避 1、2、4 秒。条目重试耗尽后标记该条失败，其他条目继续；失败状态无法写回时交给租约恢复。旧 attempt 不能写回。上传响应丢失后重试依赖 API 已完成条目返回既有结果的幂等行为。
2. **Run 级缓存**：以项目 ID、工作流 Run ID、文件 ID 和下载所得 SHA-256 隔离源文件，先写 `.part`，校验长度并计算哈希后原子改名。再次读取先核验哈希；硬链接到条目临时目录以避免 LRU 淘汰影响正在渲染的文件。ffprobe 结果跟随文件哈希缓存。Run 结束清理，未完成缓存最多保留 24 小时，容量上限 2 GiB，超限按 LRU 淘汰。每条最多四个下载，总下载并发八个。
3. **并发候选**：现行默认值保持 2。固定输入先做 20 条代表样本的并发 2/3/4 预跑，再对 100 条冻结快照做并发 2/3 完整对照。只有并发 3 比 2 至少快 15%、100/100 成功且无 OOM，才把默认值改为 3；并发 4 仅作基准对照。4K 仍限制为单条。
4. **队列恢复**：在隔离环境模拟 Broker 短时不可用及 Worker 中断，记录 Broker 故障时长和租约到期后的恢复等待，确认已完成条目不会重渲染。当前日志不能判定既往 RabbitMQ 故障根因。

## 验收

- 缓存：并发相同文件只下载一次、SHA 不匹配拒绝使用、LRU 淘汰、完成及超期清理、跨项目和 Run 隔离。
- 故障：网络中断、HTTP 5xx、上传响应丢失、任务中断与租约失效；单条失败不终止同批，旧 attempt 不写回。
- 性能：在隔离副本用测试3模板的同一批 100 条冻结快照及源素材，输出仅写临时目录，不覆盖正式成片或新增正式资产；Broker 保持健康。比较墙钟时间、稳定吞吐、各阶段耗时、峰值内存、源文件读取字节数与重试次数。
- 正确性：100/100 完成，时长、分辨率、帧率、H.264/AAC 与冻结配置一致，没有跨模板或 Run 读取，没有重复资产。执行相关 Worker/API 测试、类型检查与 `git diff --check`。

## 实施记录

代码已补充阶段日志、条目级可重试故障隔离、受限下载和 Run 级文件/ffprobe 缓存。缓存实际以 `projectId + finalOutputRunId` 为目录隔离；最终输出 Run 唯一绑定一个工作流 Run 与模板，因此比只按工作流 Run 共享更窄，且不需要增加跨层字段。文件名再包含文件 ID 摘要与源文件 SHA-256。内部文件响应增加 `x-content-sha256`，Worker 在写入 `.part` 时逐块校验；这是受保护内部读取接口的响应头，不是公开 API 或共享契约字段。领取与终结操作会改变 attempt 状态，不能盲目重试；下载、进度、心跳、上传使用 1/2/4 秒有界退避。上传保留已完成条目的现有幂等返回。

Worker 启动后每分钟清理过期缓存，完成批次立即清理。压测数据只读提取自紫苏梅子酱测试3原有 100 条冻结快照和 779 个源文件，源文件 SHA-256 均与项目文件记录一致；所有渲染输出写入本机临时目录，不调用正式成片上传接口。该离线对照衡量缓存和编码受控条件下的并发差异；它不替代 RabbitMQ/API 完整链路的投产验收。

本机离线完整对照使用现有 x264 `fast` / CRF 20、720p / 30fps、9:16 和全部 47 秒的原时间轴。每轮从空缓存开始；源文件读取次数按文件 ID 去重，输出通过 `render()` 的时长、分辨率、帧率、H.264/AAC 校验后即删除临时成片。首轮结果：

| 冷缓存并发 |    成功 |                       墙钟 |          吞吐 |               源文件读取 | 缓存命中 | 峰值进程内存 |
| ---------- | ------: | -------------------------: | ------------: | -----------------------: | -------: | -----------: |
| 2          | 100/100 | 1049.0 秒（17 分 29.0 秒） | 5.719 条/分钟 | 845,104,310 B（806 MiB） |   500 次 |      1.82 GB |
| 3          | 100/100 | 1014.3 秒（16 分 54.3 秒） | 5.916 条/分钟 | 845,104,310 B（806 MiB） |   500 次 |      2.67 GB |

并发 2 的阶段均值：源文件准备 422 ms、源媒体探测 1659 ms、FFmpeg 编码 18466 ms；并发 3 分别为 728 ms、3031 ms、25668 ms。峰值内存是基准 Python 进程与子 FFmpeg 进程的采样和。并发 3 的墙钟时间仅缩短 34.8 秒，即 **3.3%**，远低于至少 15% 的门槛；峰值内存增加约 46%。因此**保留默认并发 2**，不改 `FINAL_OUTPUT_MAX_CONCURRENCY` 的默认配置。两轮源文件实际读取字节数与 500 次缓存命中相同，证明完整对照均从冷缓存开始。该离线对照不含 API/队列/上传往返，因此不能把历史 37 分 42.9 秒与本次墙钟差额全部归因于本次缓存改动。

20 条等间距样本的冷缓存预跑均为 20/20 成功：并发 2 为 188.4 秒 / 峰值 1.80 GB，并发 3 为 250.6 秒 / 2.61 GB，并发 4 为 175.8 秒 / 3.47 GB。三档并不单调，不能由小样本单独推断生产最优并发；第一次并发 3 预跑曾误用中断后的温缓存，其 179.1 秒结果已废弃，以上 250.6 秒是清空专用缓存后的复跑。

- API `effect-final-output.service.spec.ts` **37 项通过**，含租约到期重新入队且不重置已完成条目的回归；API TypeScript 类型检查通过。测试里的存储适配器模拟已改为真正消费上传流，避免临时文件清理后异步打开造成测试进程错误。

- `git diff --check`、计划文档和内部 Controller 的 Prettier 检查通过。API service/spec 两个已有大量并行工作区编辑的文件仍有整体 Prettier 差异，本次新增行已按 Prettier 样式整理，未批量重排别人的改动。
