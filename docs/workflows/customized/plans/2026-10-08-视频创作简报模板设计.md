## 1. 范围与输入输出边界

- 工作流 / 节点：定制类 `SOURCE_IMPORT`，固定七节点保持不变。
- 直接输入：用户上传的简报、补充文档和可选图片，无直接上游 WorkingArtifact。不得把其他项目草稿作为输入。
- 当前草稿：schemaVersion 3，文件引用含 assetId、assetVersion、category 和可选 imageUsage；requirements 仅保留历史文字。页面下载模板不写草稿或业务 revision。
- 当前确认：用户保存版本后，API 校验草稿 revision、同项目定制资料库的真实文件与版本，提交 `customized-source-package`。相同内容不增加业务 revision，已确认内容的实际编辑遵循现有分支规则。
- 直接下游：尚未实现的标准化提炼应消费资料包的 artifactId + revision，再形成经审阅的标准化 Brief；其他节点只按实际消费依赖判断更新。
- 本次修改：下载模板原文、对应内容检查、设计说明与填写示例；保留左右上传区域和现有上传、保存、编辑、阅读、版本树组件。
- 本次不扩展 API、契约、Worker，也不增加必填表单、图片绑定字段或付费任务。

## 2. 从项目需求推导模板的职责

依据为[README 模块二](../../../../README.md#模块二定制类-ai-素材生成)、[当前业务指南](../agent-guide.md)以及本会话用户提供的原始模块二需求。当前 README 已将原始需求整理为蓝图，不能将其表格当作专用 API 已完成的证明。

定制类需要围绕同一意图形成完整叙事，并在不同镜头中保持人物、产品和场景一致。效果类强调可混剪的独立片段，两者可以共享上传与版本交互，却不能共享同一套创作目标。尤其不能把效果类片段的无口播规则迁入定制类：原始定制需求明确允许台词 / 口播、音效 / 音乐。

简报应提供后续创作的判断依据，而不是提前要求使用者完成下游工作。用户负责说明目标、真实主体信息、已有创意和限制；AI 在后续节点提出结构、分镜、运镜和视觉方案，经人工确认后再执行。三视图、镜头数、逐镜时长和供应商 Prompt 均不放进用户必填清单。

现有旧模板只有三个概括栏目，合并文档方向正确，但缺少这些语义区分：

| 缺口                               | 对后续工作的影响                   | 新模板的处理                     |
| ---------------------------------- | ---------------------------------- | -------------------------------- |
| “产品有什么”与“想表达什么”混在一起 | 希望表达的效果可能被误当作产品事实 | 表达重点与已确认事实 / 依据并列  |
| 目标过于宽泛                       | 相同产品容易得到泛化广告           | 说明观看情境及最希望记住的一件事 |
| 所有内容都叫要求                   | AI 难以区分不变项与创作空间        | 明确必须出现、已有创意和允许发挥 |
| 风格只有形容词                     | 镜头、人物、产品的外观容易各自解释 | 全片方向与主体不变细节分开描述   |
| 图片只有分类                       | 场景图中的产品、文字可能被错误采用 | 文件级说明参考范围与可变化部分   |
| 文字与声音混在“交付规格”中         | 不清楚是否需要口播、字幕或音乐     | 分别描述声音、画面文字、输出意图 |
| 多份文档没有作用说明               | 存在矛盾时容易按上传顺序取舍       | 注明主简报、补充范围与待确认冲突 |

模板无法单独保证成片质量。这些区分还需要后续标准化、脚本、资产与审片真正消费并验证。

## 6. 后续标准化消费建议

以下为未来实现建议，不新增共享 DTO，也不声称当前上传 API 会自动完成这些理解：

1. 读取已确认资料包及其锁定文件版本，生成目标、主体事实、表达重点、叙事方向、共享视觉规则、音画与交付意图、附件用途、待确认项。
2. 每项保留原文位置及来源。区分已给定、AI 建议、待确认；不要用“空白”推导确定产品事实或自动接受 AI 方案。
3. 对“必须”“希望”“请 AI 提方案”保持不同约束强度。模型负责理解，程序检查来源与结构，不靠标题和关键词填表来替代理解。
4. 多文档无明确权威关系时保留冲突，不按文件名、日期或上传顺序自动覆盖。主简报规定创作意图，详细说明可规定产品事实；二者冲突仍要审阅确认。
5. 图片分类不等于完整语义。比如“场景参考”不代表采用里面的杯子；文件名说明仅用于人工对照和提炼，正式绑定仍需要同项目 assetId / assetVersion。同名歧义需要提示，不能猜测。
6. 缺少时长、画幅等信息可以导入并形成待确认项；执行前应按实际任务需要补齐、校验。准确时长与建议范围不能混用。
7. 产品包装文字与标识需保持真实；字幕、标题、旁白作为独立内容处理。不能把所有文字一律塞进生成画面，也不能把定制类一律改成无台词片段。
8. 期望完整成片、多个画幅或多个创意属于输入意图，不承诺当前节点已支持。成片合成原需求与目前素材交付边界的差距要在后续实施中解决，不额外添加固定节点。

## 7. 设计检查与验证

已用以下情境检查填写负担与后续解释边界：

- 重点单品片：产品事实引用规格文件，拍摄意图与性能声明分离；不用写完整分镜。[虚构 Word 填写示例](../templates/视频创作简报填写示例.docx)展示这一情境。
- 纯品牌片：主体可写品牌理念，产品表不要求虚构参数，结尾不强制购买行动。
- 极简输入：写清主体、受众和核心信息即可开始提炼，留空形成待确认项，而非强制补完所有部分。
- 已有创意：明确哪些内容必须原样保留，AI 只对授权范围提方案。
- 参考范围：只参考某图光线时不采用其人物 / 商品；没有图片仍可导入。
- 多文档矛盾：主简报写一个型号，附件写另一个型号，不能直接按上传顺序决断。
